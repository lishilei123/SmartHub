| 项目 | 内容 |
|---|---|

| 阶段 | Phase 3：技术方案分析 |

本文所称“技术分析”特指**对已有技术方案进行知识库辅助评审**。第三期个人 Demo 不涉及 Git、代码仓库或代码 Diff，也不负责生成可直接实施的代码和部署产物。

## 2. 背景、目标与范围

### 2.1 背景

一期已经提供项目资料接入、版本、检索和原文定位；二期已经提供多文档需求点提取、Finding 评审、人工处置、固定 Evidence 和受控 Agent 执行能力。

需求评审完成后，项目通常还会形成技术方案。人工评审技术方案时，需要反复对照需求文档、架构说明、接口资料和数据字典，容易遗漏需求、忽略异常流程，或者提出无法定位来源的意见。第三期使用独立的 `TechnicalSolutionAnalysisAgent`，在固定需求评审结果和固定技术方案资料上完成一次可追溯的技术方案评审。

### 2.2 本期目标

1. 在当前项目版本中选择一个成功的需求评审运行，作为技术方案评审的需求基线。
2. 选择一份或多份已进入知识库的技术方案资料，固定到明确的资产版本。
3. 使用独立 `TechnicalSolutionAnalysisAgent` 分析需求覆盖、方案完整性、接口与数据设计、异常流程、非功能要求和主要风险。
4. 输出结构化技术评审 Finding、建议和待确认问题，并能够定位到需求或技术方案原文。
5. 支持查看运行状态、历史结果、原文证据、简单人工处置和 Markdown 报告导出。
6. 复用二期的模型配置、Agent 配置、工具治理、取消和运行记录，不建设新的通用 Agent 平台。

### 2.3 本期交付范围

- 技术方案评审入口和工作台；
- 成功需求评审运行的选择与固定；
- 从知识库选择固定版本的技术方案资料；
- 独立 `TechnicalSolutionAnalysisAgent` 及其 Prompt、工具和结果协议；
- 技术方案摘要、需求覆盖、技术 Finding、风险、建议和待确认问题；
- 需求原文与技术方案原文的固定 Evidence 定位；
- 评审运行、历史结果、简单 Finding 处置和 Markdown 报告导出；
- 模型失败、工具失败、结果校验失败和取消状态的真实展示。

### 2.4 非目标

个人 Demo 不交付以下能力，验收不依赖它们：

- Git、代码仓库、Commit、Pull Request、代码 Diff 或静态代码分析；
- 自动编写或修改技术方案原文；
- 自动生成生产代码、数据库脚本、部署脚本、测试脚本或流水线；
- 自动执行部署、数据库变更、测试、压测或安全扫描；
- 动态多 Agent 协作、Agent 自由委派或通用工作流编排；
- 复杂多人审批、组织角色、ACL、SSO、成本结算或企业审计；
- Jira、Wiki、Webhook 等外部系统的双向同步；
- PDF、Word、Excel、图片等一期尚未支持格式的专用解析；
- 自动将 AI 结果写回需求原文、技术方案原文或知识库活动版本。

## 3. 核心对象与原则

### 3.1 核心对象

```text
项目版本
  ├─ 需求基线
  │    └─ 成功 ReviewRun
  │         ├─ 冻结需求点与需求 Evidence
  │         └─ Finding 与人工处置快照
  ├─ 技术方案输入
  │    └─ 固定 technical_design 资产版本
  └─ 技术方案评审
       └─ TechnicalSolutionReviewRun
            ├─ TechnicalSolutionAnalysisAgent 执行
            ├─ 技术评审 Finding
            └─ 技术方案 Evidence
```

| 对象 | 定义与规则 |
|---|---|
| 需求基线 | 当前项目版本中一个成功 ReviewRun 的冻结引用，包括需求点、需求 Evidence、Finding 和人工处置快照。 |
| 技术方案输入 | 用户从知识库选择的一份或多份 `technical_design` 类型的固定 `assetVersionId`。 |
| 技术方案评审 | 需求基线与技术方案输入组成的一次逻辑评审，可有多次独立运行。 |
| 技术方案评审运行（`TechnicalSolutionReviewRun`） | 一次可取消、可追溯的 Agent 分析尝试；重新评审创建新运行，不覆盖旧结果。 |
| 技术评审 Finding | 对技术方案缺口、风险、歧义或不一致的结构化评审结论。 |
| Evidence | 指向固定需求资产版本或技术方案资产版本的原文摘录、Chunk 和定位。 |
| `TechnicalSolutionAnalysisAgent` | 第三期独立业务 Agent，只读取本次运行的固定输入并提交技术评审候选。 |

### 3.2 技术 Finding 类型

| 类型 | 说明 |
|---|---|
| `requirement_coverage_gap` | 需求点未被技术方案覆盖或仅部分覆盖。 |
| `architecture_gap` | 系统边界、模块职责、依赖或关键流程说明不足。 |
| `interface_gap` | 接口输入输出、错误、幂等、兼容或调用关系不明确。 |
| `data_gap` | 数据实体、状态、约束、一致性、迁移或保留策略不明确。 |
| `exception_gap` | 失败、超时、重试、降级、补偿或回滚流程缺失。 |
| `non_functional_gap` | 性能、容量、可用性、安全、可观测性或维护性要求缺失。 |
| `conflict` | 技术方案与需求基线或固定项目资料存在冲突。 |
| `risk` | 当前方案可能带来的实施、兼容、数据或运行风险。 |
| `other` | 不属于以上分类但需要人工确认的问题。 |

严重度沿用二期：`blocker`、`high`、`medium`、`low`。人工处置沿用二期的 `open`、`confirmed`、`dismissed`、`resolved`、`needs_follow_up`，个人 Demo 不增加复杂审批状态。

### 3.3 全局原则

- **固定输入**：运行创建后不得切换到最新需求、最新方案或最新索引。
- **项目版本隔离**：需求基线、技术方案输入、运行、Finding 和报告必须属于同一 `projectVersionId`。
- **证据优先**：项目事实和问题依据必须能定位到固定需求或技术方案原文；证据不足时标记为待确认，不得伪装为事实。
- **模型提交语义，服务端生成引用**：模型提交问题、影响、建议和原文线索；服务端生成 Finding ID、Evidence ID、资产/Chunk 引用、定位和覆盖统计。
- **Agent 结果不是直接成功**：只有服务端完成 Schema、Evidence、输入范围和一致性校验后，运行才可成功。
- **历史不覆盖**：重新评审创建新运行；旧运行、结果、证据和人工处置继续可查看。
- **单 Agent**：每次运行只启动一个 `TechnicalSolutionAnalysisAgent`，不引入多 Agent 编排。
- **只读分析**：Agent 只读取固定资料和调用已授权只读工具，不修改需求、技术方案或知识资产。

## 4. 用户流程与页面

### 4.1 主流程

```text
选择 open 项目版本
  → 进入技术方案评审
  → 选择一个 succeeded 需求评审运行
  → 上传技术方案资料或从知识库选择 ready 的技术方案资产版本
  → 检查输入、索引、模型和 Agent 配置
  → 创建 queued TechnicalSolutionReviewRun
  → TechnicalSolutionAnalysisAgent 分析固定输入
  → Agent 提交结构化候选和原文线索
  → 服务端生成 Evidence、需求覆盖关系和 Finding ID
  → 服务端校验并保存正式结果
  → 查看结果、处置 Finding 或导出报告
```

失败或取消时保留运行记录和脱敏错误，不显示模拟结果、示例 Finding 或“未发现问题”的伪成功。

### 4.2 运行前检查

- 只允许在 `open` 项目版本中启动新评审；`locked`、`archived` 版本只读查看历史。
- 需求基线必须是当前项目版本中 `succeeded` 的 ReviewRun。
- 至少选择一份当前项目知识库中 `ready` 的 `technical_design` 资产版本。
- 创建页左侧提供 Markdown、TXT 和 ZIP 上传；资料进入当前知识库的 `版本文档/{项目版本名}/技术方案/`，ZIP 保留包内安全相对目录，处理完成后刷新候选并自动勾选已进入活动索引的资产版本。
- 页面显示需求资产、需求点数量、技术方案名称/版本、索引版本和可能过期提示。
- 若需求基线仍有未处置的 blocker/high Finding，个人 Demo 只做醒目提示，不阻止启动技术方案评审；结果中必须保留该风险背景。
- 启动前校验固定正文可读取、内容 Hash 一致、活动索引可用、模型配置可用、Agent 已发布且工具权限有效。

### 4.3 工作台布局

页面沿用二期易理解的三栏结构：

| 区域 | 用户可见能力 |
|---|---|
| 顶部操作区 | 显示项目版本、运行 ID、状态、进度、需求基线、技术方案版本、模型/检索降级；提供开始评审、取消、重新评审和导出。 |
| 左侧资料区 | 创建态展示技术方案目录、上传/索引进度及知识库入口；运行态展示固定需求资料和技术方案目录并打开固定原文。 |
| 中间评审区 | 创建态选择需求基线、确认固定输入并启动；运行态提供评审概览、需求覆盖、技术 Finding、风险与待确认、Evidence、运行历史视图。 |
| 右侧详情区 | 创建态展示历史评审和启动条件；运行态展示当前 Finding 的问题、影响、建议、关联需求点、Evidence 和简单人工处置。 |

点击需求点、Finding 或 Evidence 时，系统按固定 `assetVersionId` 打开对应原文并滚动到证据位置；定位失败时显示错误，不跳转到最新版本。

### 4.4 结果展示

成功运行至少展示：

- AI 技术方案摘要；
- 需求覆盖概览：已覆盖、部分覆盖、未覆盖、待确认；
- 按类型和严重度归类的技术 Finding；
- 关键技术风险与待确认问题；
- 每条 Finding 的影响、建议、关联需求点和固定 Evidence；
- 输入、模型、Agent、Prompt、工具和索引快照摘要；
- 运行时间、Token、工具调用和失败/降级摘要。

## 5. 功能需求

### 5.1 输入与运行

#### FR-501：项目版本与输入选择

- 每次评审必须显式携带 `projectVersionId`；客户端不得选择或提交任意 `projectId`。
- 只允许选择同项目版本的成功 ReviewRun 和当前知识库中 `ready` 的技术方案资产版本。
- open 版本支持在技术方案评审创建页上传 Markdown、TXT 或 ZIP；客户端必须以 `technical_design` 类型写入当前项目知识库的版本技术方案目录，并等待任务完成、刷新活动索引后才能把资产加入本次固定输入。
- 一次运行可评审一份或多份属于同一技术方案范围的资料；页面明确列出全部固定输入。
- 资产产生新版本不会自动替换历史运行输入；用户重新评审时显式选择新版本。

#### FR-502：运行快照与状态

- 创建运行时固定：项目版本、来源 ReviewRun、需求点/Evidence/Finding 处置快照、技术方案资产版本/Hash、索引版本、模型配置、Agent/Prompt/工具/Skill/MCP/网络/权限/限制版本和创建时间。
- 状态至少包括 `queued`、`running`、`succeeded`、`failed`、`cancelled`。
- 页面进度至少覆盖输入校验、正文组装、Agent 分析、结果提交、Evidence 解析、结果校验和保存。
- 用户可取消未完成运行；取消后的迟到模型或工具结果不得保存为正式结果。
- 重新评审创建新运行，不覆盖历史。

#### FR-503：固定正文投递

- 需求点、需求 Evidence、Finding 处置摘要和技术方案正文是强制输入，不能只把搜索工具交给 Agent 后让其自行猜测范围。
- 输入在模型安全预算内时直接投递完整固定正文；超出预算时由服务端按资产、标题和 Chunk 边界确定性分段，不静默截断。
- 每份输入记录投递状态和内容 Hash；存在未投递正文时不得宣称完成全部技术方案评审。
- 文档、检索、Skill、MCP 和网络返回内容均视为不可信数据，不能修改 Prompt、权限或结果规则。

### 5.2 Agent 与评审结果

#### FR-504：独立技术方案分析 Agent

- 使用独立 `agent_type=technical_solution_analysis`、Agent 定义、Prompt、模型场景和结果协议，不让二期 Agent 修改 Prompt 后兼任。
- 每个运行只创建一个 Agent 执行实例。
- 默认工具仅包括知识检索、固定正文补读、Evidence 辅助校验和 `technical_solution_review.submit_result`。
- Agent 只能调用运行快照内已授权的只读工具；资源已登记不代表自动获得运行权限。

#### FR-505：结果结构

默认结果协议为 `technical-solution-review/v1`，候选至少包含：

| 输出 | 要求 |
|---|---|
| 评审摘要 | 总体评价、主要缺口、主要风险和建议处理顺序。 |
| 需求覆盖候选 | 针对冻结需求点说明已覆盖、部分覆盖、未覆盖或待确认及其理由。 |
| 技术 Finding | 类型、严重度、问题、影响、建议、置信度和原文线索。 |
| 风险与待确认 | 当前资料无法证明但会影响方案可实施性的事项。 |

- 模型只提交语义内容以及 `requirementSourceTexts`、`solutionSourceTexts` 原文线索，不生成正式 Finding ID、Evidence ID、资产版本 ID、Chunk ID 或覆盖统计。
- 总体结论、覆盖状态、Finding 类型和严重度属于模型语义字段；提交入口允许有长度上限的字符串进入服务端，服务端将规范值和已知近义值确定性归一化，正式结果只保存规范枚举。近义值不得在业务归一化前被底层 Schema 以不可读的 `anyOf/constant` 错误反复拦截。
- 服务端从固定输入生成正式引用和定位；无法解析、越界或存在歧义时要求模型修正，最终仍不合格则运行失败。
- `sourceTexts` 应提交逐字原文；同组中只要存在可唯一定位的逐字片段，服务端可忽略标题、描述等无法定位的冗余文本。带章节提示或省略号的输入仅可作为修复容错，正式 Evidence 必须截取并保存固定正文中的连续原文；多处匹配仍按歧义拒绝。
- Finding 必须至少关联一个需求点或一条技术方案 Evidence；需求覆盖缺口必须关联需求点。

#### FR-506：评审维度

Agent 至少检查以下维度；不适用时可以明确说明，不强制为了数量生成 Finding：

1. 需求点是否被方案覆盖，覆盖是否具体；
2. 系统边界、模块职责、依赖和关键流程是否清楚；
3. 接口输入输出、错误、幂等、兼容和调用关系是否明确；
4. 数据实体、状态、一致性、迁移和回滚是否说明；
5. 异常、超时、重试、降级、补偿和恢复流程是否完整；
6. 性能、容量、可用性、安全和可观测性是否满足已知需求；
7. 是否存在与需求或固定项目资料冲突的描述；
8. 是否存在影响实施或验收的风险、假设和待确认问题。

#### FR-507：服务端校验与覆盖统计

- 服务端按“基础 Schema → 模型语义归一化 → 原文线索/Evidence → 需求关系与覆盖完整性”的顺序校验；必填字段、输入范围、Evidence 可定位性和需求点关系仍是严格门禁。
- 需求覆盖状态为 `covered`、`partially_covered`、`not_covered`、`needs_confirmation`。
- 正式覆盖数量和比例由已持久化关系计算，不采信模型自报数值。
- 不要求个人 Demo 达到固定覆盖率阈值；验收关注是否真实识别样例中的已知覆盖与缺口。
- 非法候选不得生成成功统计或正式 Finding。

### 5.3 查看、处置与导出

#### FR-508：Finding 查看与简单处置

- Finding 展示类型、严重度、问题、影响、建议、关联需求点、Evidence 和 AI 置信度。
- 人工处置沿用二期状态和操作，追加保存说明、操作者和时间，不覆盖 AI 初始内容。
- 支持按严重度、类型、状态、需求覆盖状态筛选。
- 个人 Demo 不要求多人会签、审批流、处置时限或外部工单联动。

#### FR-509：历史、定位与导出

- 列表和路由显式使用 `projectVersionId + technicalReviewId + runId`，刷新后恢复同一运行。
- 历史运行展示输入版本、状态、摘要和创建时间；新运行不覆盖旧运行。
- Evidence 必须打开固定需求或技术方案资产版本并定位原文。
- 支持导出 Markdown 报告，包含输入摘要、评审摘要、需求覆盖、Finding、Evidence、风险、处置状态和运行快照摘要。
- 报告不包含候选原始响应、模型隐藏思维、明文凭据或未脱敏日志。

#### FR-510：模型、工具与安全边界

- 复用二期模型路由、Agent 配置、Tool Runtime、Skill/MCP 和网络治理。
- 默认只读，不开放 Shell、宿主文件系统、任意 HTTP 或外部写操作。
- Tool Runtime 校验工具名称/版本、参数 Schema、固定输入范围、权限、超时、取消、结果大小和脱敏规则。
- 页面、API 和普通日志不得返回 API Key、Authorization、签名或秘密环境变量。

## 6. 最小数据与一致性规则

### 6.1 最小记录字段

| 实体 | 最小字段 |
|---|---|
| 技术方案评审 | ID、项目版本、名称、来源 ReviewRun、技术方案资产版本列表、创建时间。 |
| TechnicalSolutionReviewRun | ID、评审 ID、状态/进度、固定输入与 Hash、索引、模型/Agent/Prompt/工具快照、起止时间、错误摘要。 |
| 技术 Finding | ID、运行、类型、严重度、问题、影响、建议、置信度、需求点关系和 Evidence。 |
| Evidence | 运行、来源类型、资产/版本/Chunk、内容 Hash、标题路径、摘录和定位。 |
| 人工处置 | Finding、前后状态、操作、说明、操作者、版本和时间。 |

### 6.2 一致性规则

1. 评审、运行、来源 ReviewRun、技术方案输入、Finding 和 Evidence 必须属于同一项目版本。
2. 运行创建后，输入、Hash、索引、模型、Agent、Prompt、工具和权限快照不可原地修改。
3. 模型提交的 ID、资产版本、Chunk、Evidence 和覆盖统计不直接采信，由服务端生成。
4. 成功运行必须具有完整输入记录、合法结果、可解析 Evidence 和正式需求覆盖统计。
5. 取消、失租约或达到执行限制后的迟到结果不能成为正式 Finding。
6. 人工处置只追加，不改写 AI 初始 Finding 或历史 Evidence。
7. 查询、筛选、定位和导出必须校验显式项目版本和运行归属，不默认到最新运行。

## 7. 个人 Demo 验收标准

### AC-301：创建并完成一次真实评审

**操作**：在 `open` 项目版本中选择一个成功需求评审运行和一份 `ready` 技术方案，启动评审并等待完成。

**预期**：系统创建真实运行并展示状态；成功后能够查看评审摘要、需求覆盖、技术 Finding、风险和输入快照，不使用前端模拟数据代替后端结果。

### AC-302：需求覆盖与已知问题识别

**操作**：使用一份包含“已覆盖需求、明确遗漏需求和一个接口/异常流程缺口”的小型固定样例运行评审。

**预期**：结果能区分已覆盖、部分/未覆盖或待确认需求，并识别样例中的主要接口或异常缺口；不要求固定准确率或生产级质量指标，但结果必须可人工理解和复核。

### AC-303：Evidence 原文定位

**操作**：从一个需求覆盖项和一个技术 Finding 分别打开需求 Evidence 与技术方案 Evidence。

**预期**：两者都打开运行时固定的 `assetVersionId` 并定位原文；不能定位时明确报错，不跳转到最新资料，也不伪造引用。

### AC-304：失败、取消和重新评审

**操作**：分别触发模型失败、非法结果和运行中取消，然后重新发起评审。

**预期**：失败/取消显示真实状态和脱敏原因，不展示模拟成功结果；迟到结果不发布；重新评审创建新 runId，历史运行仍可查看。

### AC-305：简单处置与报告导出

**操作**：确认或驳回一条 Finding 并填写说明，然后导出 Markdown 报告。

**预期**：处置追加保存且不覆盖 AI 原始内容；报告包含固定输入、摘要、覆盖、Finding、Evidence 和处置状态，不含秘密或模型隐藏思维。

### AC-306：范围边界

**操作**：检查页面、Agent 配置、默认工具和验收流程。

**预期**：个人 Demo 只围绕知识库中的需求和技术方案资料完成只读评审，不依赖 Git、代码、Diff、部署、测试执行、多 Agent 或复杂审批能力。

## 8. 前置条件、待确认事项与后续衔接

### 8.1 前置条件

- 一期知识库可提供 `ready` 技术方案资产版本、固定正文、Chunk、活动索引和原文定位；
- 二期可提供同项目版本成功 ReviewRun、冻结需求点/Evidence、Finding 和人工处置；
- 至少存在一个可用生成式模型和已发布 `TechnicalSolutionAnalysisAgent`；
- 已准备一组小型技术方案评审样例，包含少量已知覆盖和缺口。

### 8.2 待确认事项

1. 个人 Demo 首批技术方案模板和样例资料；
2. 单次最多选择的技术方案文件数和输入 Token 上限；
3. 首批模型、最大运行时长、回合数和工具调用数；
4. 技术 Finding 类型和严重度是否需要根据试用结果继续精简；
5. Markdown 报告的标题、章节顺序和默认文件名。

### 8.3 后续衔接

第三期个人 Demo 只完成知识库技术方案评审。以后如需要方案自动编写、代码影响分析、测试多 Agent、多角色审批或外部系统发布，应分别补充需求和技术设计，不能把本期预留能力解释为已经交付。
