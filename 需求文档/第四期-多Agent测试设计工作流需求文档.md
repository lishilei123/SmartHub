本文所称“测试设计”是将已确认需求与已评审技术方案，或用户显式选择并冻结的知识库资料，转换为可追溯的测试范围、测试点、结构化测试用例和覆盖矩阵。本期不生成或修改自动化代码，不连接真实测试环境，不执行功能测试、压测、故障注入或安全扫描。

## 2. 背景、目标与范围

### 2.1 背景

前三期已经形成知识资产、需求点、技术方案要点、Finding 及其上游 Evidence，项目也可能已经沉淀历史测试用例。多数存量项目并不具备完整的 SmartHub 需求评审和技术方案评审运行，但通常已经拥有产品说明、接口资料、架构设计、操作手册、测试资料和问题复盘。若测试设计强制依赖前两阶段，存量项目将无法直接使用。

无论采用评审基线还是知识库资料，如果缺少固定输入、职责分离和人工门禁，都容易出现以下问题：

- 功能主流程被覆盖，但异常、边界、状态转换和权限规则遗漏；
- 性能、稳定性、兼容性和安全要求被泛化成口号，缺少可测量条件；
- 测试用例无法说明来自哪条需求、技术方案或知识资料；
- 功能与非功能分支重复生成相同用例，覆盖率由模型自报且不可复核；
- 缺少 SLA、容量、兼容矩阵或恢复目标时，模型自行编造阈值；
- AI 结果直接成为正式测试资产，缺少人工评审和版本边界；
- 历史有效用例被重复设计，或旧用例被直接覆盖，无法说明哪些内容被复用、修改或废弃；
- 原始知识资料存在冲突、过期或缺少判定标准时，被模型误当成已确认需求。
- 测试点和用例一次性生成，测试人员没有机会先调整测试思路，导致遗漏被固化到大量用例中；
- 测试数据条件散落在步骤文本中，后续执行 Agent 无法稳定识别需要准备什么数据。
- 新功能测试设计、项目级用例库和冒烟/回归基线混在一起，无法区分“本次新增什么”与“提测时需要执行什么”；
- 冒烟用例集长期固定或被原地修改，既不能吸收稳定的新功能核心链路，也无法复现历史提测实际使用的冒烟范围；
- 全量回归用例被复制进每个新功能用例集，造成成员重复、后续维护分叉和统计失真。

第四期采用服务端定义的 `TestDesignWorkflow`，并提供 `review_baseline`（评审基线）与 `knowledge_assets`（知识库资料）两种互斥的主测试依据模式。工作流在固定骨架内依次完成依据解构与受控知识召回、测试点发散、测试用例具象化、测试数据资产定义和覆盖反向审计；测试点树人工调整与批准位于测试点发散和用例具象化之间，是阶段门禁而非第六阶段。SmartHub 负责工作流拓扑、节点状态、快照、交接、ID、树版本、来源关系、覆盖统计、校验、人工评审和发布，Agent 不自行编排或委派任务。

### 2.2 本期目标

1. 支持用户选择评审基线或知识库资料作为主测试依据；知识库模式不要求存在需求评审或技术方案评审运行，两种模式都形成不可漂移的输入快照。
2. 通过四个职责独立的 Agent 角色完成依据解构、功能/非功能测试点发散和用例具象化；非功能角色统一覆盖性能、稳定性、兼容性和安全。
3. 支持基于固定索引和固定召回语料的知识库向量/混合召回；召回结果作为补充上下文冻结，不把相似内容自动提升为已确认规则。
4. 输出可在线调整并独立批准的测试点树；树批准前不得生成正式用例候选，树变化后不得静默沿用旧用例。
5. 将已批准测试点具象化为结构化测试用例和独立测试数据需求，明确每条用例与测试点、数据条件及依据的关系。
6. 对没有明确指标或支持矩阵的非功能要求，生成待确认项和阻塞状态，不编造 SLA、容量、时长、版本或安全结论。
7. 支持历史用例适用性分析、原样复用、复制并修改、废弃标记和新旧差异比较；任何操作均不覆盖历史版本。
8. 通过服务端覆盖审计检查依据项、测试点、用例、数据需求和反向来源链，Agent 只提交语义补漏建议，不自报正式覆盖率。
9. 支持在线修改、逐条/批量审核、版本 Diff，以及 JSON、Markdown、Excel 导出；审核通过后发布不可变 `TestCaseSetVersion`。
10. 通过版本化机器契约为下一阶段测试执行 Agent 提供可直接读取、无需重新解析自然语言报告的用例和数据需求输入。
11. 提供项目级测试用例库和测试用例集聚合视图，明确区分本次新功能用例集、冒烟基线、回归基线和功能域用例集；同一已发布用例通过固定引用进入多个集合，不复制或改写内容。
12. 支持在本次新功能用例中标记冒烟候选，输出“当前冒烟基线 + 本次候选”的组合建议和标准/快速/直接全量三种执行交接，不在第四期创建真实测试计划或发布新的冒烟基线。

### 2.3 本期交付范围

- 测试设计创建页、工作台和历史运行；
- 需求基线与技术方案基线的同版本选择、关联校验和固定快照；
- 知识库驱动模式下，一至多份 `ready` 知识资产版本的显式选择、范围设置、完整投递和固定快照；
- 两种主依据模式均可选的受控知识召回，以及查询、模型/索引、召回 Chunk、分数和 Hash 快照；
- 同一项目内历史 `TestCaseSetVersion` 或固定 `test_case` 资产版本的显式选择、适用性分析和来源冻结；
- 固定 DAG 测试设计工作流及四个 Agent 节点的独立配置、执行与交接记录；
- 功能设计与非功能设计两个并行分支；非功能分支覆盖性能、稳定性、兼容性和安全；
- 可扩展的可用性/无障碍、数据完整性、可观测性等补充维度；
- 依据解构、测试范围、风险、结构化测试点树、测试用例、测试数据需求、覆盖矩阵和待确认项；
- 知识资料中的可测试规则、行为、约束和冲突归并，以及知识基线覆盖统计；
- 服务端结果校验、去重、覆盖统计和来源关系追溯；
- 按专项、优先级、状态、需求点/知识基线项和自动化候选筛选；
- 测试用例在线结构化编辑、草稿保存、字段校验、修订 Diff 和冲突处理；
- 测试点树在线新增、删除、移动、拆分、合并、不适用标记、revision/ETag 冲突处理和批准门禁；
- 历史用例原样复用、复制并修改、废弃/冲突标记及新旧字段比较；
- 单条/批量提交审核、通过、驳回、要求修订和追加说明；
- 机器可读 JSON、Markdown、Excel 导出，以及人工确认后的版本化测试用例集发布；
- 项目级测试用例库、测试用例集和成员来源/版本的只读聚合视图；
- 本次新功能用例集的新增、修改、原样复用、影响回归引用和冒烟候选统计；
- 冒烟候选标记、候选理由与人工确认，以及基于当前冒烟/回归固定版本的执行交接建议；
- 失败专项重试、测试点树修订、重新具象化用例、全部重跑和运行取消。

### 2.4 非目标

本期不交付以下能力，验收不得依赖它们：

- Playwright、API、性能或安全测试脚本生成；
- Git 仓库、分支、Commit、Pull Request、Patch 或 Diff 写入；
- 浏览器、接口、压测、故障注入、安全扫描或真实测试环境执行；
- 测试账号、凭据、环境、数据构造与清理的自动操作；
- 执行日志、截图、视频、Trace、覆盖率采集、失败聚类和根因分析；
- 构建/提测单、环境、执行策略的正式 `TestPlanVersion` 创建，冒烟/新功能/回归任务调度，以及基于执行结果自动晋级冒烟基线；
- 定位器自愈、脚本自修复、缺陷自动创建或 CI/CD 发布；
- Agent 自由委派、自由对话决定流程或面向用户的通用 DAG 编排器；
- 组织级角色、多人会签、复杂审批、ACL、SSO 和外部工单同步；
- Excel、PDF、Word、OpenAPI 等新增输入解析器或 Excel 用例导入；本期 Excel 仅为固定模板导出。

脚本编写和测试执行保留为后续独立需求。资源目录中存在代码执行 Tool、Skill 或 MCP，不代表本期 Agent 可以使用。

## 3. 核心对象与原则

### 3.1 核心对象

```text
项目版本
  ├─ 主测试依据（二选一）
  │    ├─ review_baseline：成功 ReviewRun + TechnicalSolutionReviewRun
  │    └─ knowledge_assets：一至多份固定 Knowledge AssetVersion
  ├─ 可选历史用例输入：TestCaseSetVersion / test_case AssetVersion
  ├─ 项目测试资产聚合
  │    ├─ ProjectTestCaseCatalog（已发布用例只读目录）
  │    └─ TestSuiteVersion（既有冒烟/回归/功能域固定版本）
  └─ 测试设计
       └─ TestDesignWorkflowRun
            ├─ TestBasisSnapshot
            ├─ KnowledgeRetrievalSnapshot（必有；可为 disabled 空快照）
            ├─ KnowledgeBasisItem（knowledge_assets 模式）
            ├─ HistoricalCaseSnapshot
            ├─ TestAnalysisCheckpoint
            ├─ FunctionalDesignArtifact
            ├─ NonFunctionalDesignArtifact
            ├─ TestPointTreeDraft / Revision / Version
            ├─ TestCaseSynthesisCheckpoint
            ├─ TestPoint / TestCase / TestDataRequirement
            ├─ CoverageRelation / CoverageAuditResult
            ├─ DesignFinding / ConfirmationItem
            ├─ TestCaseDraft / TestCaseRevision / TestCaseReuseRelation / TestCaseSetVersion
            ├─ SmokeCandidateRelation / ImpactedRegressionReference
            └─ TestExecutionHandoff
```

| 对象 | 定义与规则 |
|---|---|
| 测试设计（`TestDesign`） | 同一测试目标的逻辑实体，可拥有多个独立运行和多个人工发布版本。 |
| 工作流运行（`TestDesignWorkflowRun`） | 一次固定输入、固定 DAG、可取消、可追溯的多 Agent 执行尝试。 |
| 测试依据快照（`TestBasisSnapshot`） | 保存 `basisMode` 及对应固定输入。`review_baseline` 固定需求/技术方案运行、需求点、方案要点、Finding 处置和结果 Hash；`knowledge_assets` 固定所选知识资产版本、正文/Chunk、内容 Hash、索引版本、投递清单、范围和排除项。 |
| 知识召回快照（`KnowledgeRetrievalSnapshot`） | 每次运行必有的补充知识召回快照；固定召回模式、语料范围、索引/Embedding/检索配置、需求特征/查询 Hash、命中 Chunk、分数、内容 Hash 和分类，不在下游重新检索。关闭召回时保存 `mode=disabled`、空查询/命中集合及其规范化 Hash，不使用 `null`。 |
| 知识基线项（`KnowledgeBasisItem`） | 知识库模式下从固定资料归并出的最小可测试规则、行为、约束或风险；模型提交语义和原文线索，服务端生成 ID、固定定位、内容 Hash、冲突状态和覆盖关系。 |
| 历史用例快照（`HistoricalCaseSnapshot`） | 固定用户显式选择的历史用例集版本/用例或 `test_case` 资产版本、规范化结构化内容/固定文本、内容 Hash、Schema、来源项目版本和定位信息；运行期间不依赖或跟随“最新版本”变化。 |
| Agent 任务运行（`AgentTaskRun`） | 工作流中的一个节点执行，记录 Agent、依赖、输入产物、输出产物、状态、重试和执行快照。 |
| 交接产物（`HandoffArtifact`） | Agent 节点之间传递的不可变结构化产物；通过服务端校验后才可被下游读取。 |
| 测试点（`TestPoint`） | 针对一个规则、风险、状态、接口或非功能目标的最小可验证意图。 |
| 测试点树（`TestPointTreeDraft/Revision/Version`） | 功能/非功能测试点的可编辑层级投影；服务端以稳定节点、父子/排序和独立来源关系保存，人工批准的不可变 `TestPointTreeVersion` 是用例具象化的唯一输入。 |
| 测试用例（`TestCase`） | 包含目标、测试维度、一至多种 UI/API 执行方式、验证检查点、优先级、共享前置条件/数据/清理、各方式独立步骤与期望、指标或判定条件及来源关系的结构化设计。 |
| 测试数据需求（`TestDataRequirement`） | 描述执行用例所需的数据实体、特征、约束、规模、初始状态、敏感级别、隔离、重置和清理要求；不保存或创建真实账号、秘密和生产数据。 |
| 覆盖关系（`CoverageRelation`） | 评审基线模式保存需求点/方案要点与测试点/用例的覆盖；知识库模式保存知识基线项与测试点/用例的覆盖，两类统计不得混称。 |
| 设计依据关系（`BasisRelation`） | 说明测试点/用例来自需求、方案、Finding、知识基线项、风险推导、通用实践或人工假设；前四类引用相应冻结对象，后三类保存推导说明。 |
| 设计 Finding | 测试依据中的缺口、矛盾、不可测项、环境依赖或发布阻塞项。 |
| 覆盖审计结果（`CoverageAuditResult`） | 绑定依据、测试点树、当前用例 revision 集合和数据需求 Hash 的服务端审计产物，记录覆盖缺口、孤立节点、无依据用例、缺失 oracle/数据、重复冲突和发布阻塞项。用例内容/成员或数据需求变化后立即过期。 |
| 待确认项（`ConfirmationItem`） | 缺少阈值、版本、范围、环境或业务决策时形成的明确问题。 |
| 测试用例草稿（`TestCaseDraft`） | 基于 AI 生成、历史复用或人工创建的已校验初始候选形成在线可编辑工作副本，保存当前字段值、修订号、编辑者和脏状态。 |
| 测试用例修订（`TestCaseRevision`） | 每次有效保存形成的不可变字段快照和 Diff；初始候选作为 revision 0 永久保留，并通过 `origin` 区分来源。 |
| 用例复用关系（`TestCaseReuseRelation`） | 记录当前用例来自哪个历史版本/用例、采用原样复用还是修改后复用、源内容 Hash、当前内容 Hash 和修改摘要。 |
| 测试用例集版本（`TestCaseSetVersion`） | 人工审核后发布的不可变、机器可读本次功能用例集合，是第四期测试设计的正式产物；Markdown/知识资产是其展示投影。后续执行必须引用明确版本和成员。 |
| 项目测试用例目录（`ProjectTestCaseCatalog`） | 对同一项目已发布、可读取用例 revision 及其集合成员关系的只读聚合，不创建副本，不拥有独立可编辑正文，也不把草稿或未就绪用例混入正式目录。 |
| 测试套件版本（`TestSuiteVersion`） | 项目级冒烟、全量回归或功能域套件的不可变成员快照；成员引用明确 `testCaseSetVersionId + caseId + executionMethods[]`。第四期读取既有版本，不原地修改，也不负责发布新套件版本。 |
| 冒烟候选关系（`SmokeCandidateRelation`） | 当前功能用例进入未来冒烟基线的候选建议，保存候选理由、关键链路、预计耗时、稳定性/依赖条件和人工决定；候选不等于正式冒烟成员。 |
| 影响回归引用（`ImpactedRegressionReference`） | 本次变更可能影响的既有回归用例固定引用及影响理由；用于执行交接，不复制进入本次功能用例集。 |
| 执行交接快照（`TestExecutionHandoff`） | 第四期基于已发布功能用例集、既有冒烟/回归套件版本、冒烟候选和影响回归引用生成的不可变建议，包含标准、快速、直接全量策略；不是 `TestPlanVersion`，不能创建任务或表示已经执行。 |

### 3.2 全局原则

- **依据模式显式互斥**：每次运行必须明确 `basisMode`。`review_baseline` 固定同一 `projectVersionId` 的成功需求/技术方案评审且引用链一致；`knowledge_assets` 固定用户选择的知识资产版本且不要求两个评审运行。
- **知识资产显式固定**：知识库模式不读取“整个知识库”或 `latest`；必须选择具体 `ready assetVersionId`，固定正文/Chunk、Hash、索引、投递清单、范围和排除项。
- **召回受控且可复现**：知识召回是两种主依据模式都可启用的补充能力；只能使用运行创建时固定的语料/索引和检索配置，命中内容按来源角色分类，不能覆盖或冒充主依据。
- **历史输入显式固定**：历史用例只能由用户显式选择并冻结到运行，允许来自同一项目的其他项目版本；不得自动读取 `latest` 或用相似用例替换已选来源。
- **显式 DAG**：任务拓扑、依赖、并发、超时、重试和汇总规则由服务端版本化，不由 Agent 临时协商。
- **专项独立**：不同专项使用独立 Agent 定义、Prompt、模型路由、工具集、执行限制和会话，不共享隐藏消息历史。
- **结构化交接**：下游只读取服务端校验并冻结的交接产物，不读取上游自由对话或候选草稿。
- **先测试点、后用例**：功能/非功能 Agent 先发散测试点，服务端归并为可编辑树；只有人工批准的 `TestPointTreeVersion` 可以进入用例具象化。
- **来源可解释**：需求/方案驱动项关联冻结需求点、方案要点或 Finding，并可经上游对象间接查看其 Evidence；知识驱动项关联 `KnowledgeBasisItem` 并定位固定资产原文，但该定位只证明资料内容，不代表资料已经过需求评审或事实确认；风险推导、探索性场景和通用测试实践可没有原文来源，但必须标明推导类型、理由和假设。
- **不编造指标**：资料没有给出性能阈值、恢复目标、兼容版本或安全标准时，Agent 不得补写成已确认事实。
- **模型提交语义，服务端拥有标识**：模型提交设计语义、推导类型和输入内引用；服务端生成 ID、来源关系、覆盖关系、统计和正式版本号。
- **完整性由服务端计算**：评审基线覆盖、知识基线覆盖、专项数量、用例数量和重复关系不采信模型自报结果；知识库模式不得展示为“需求覆盖率”。
- **审计与生成分权**：综合 Agent 可提交语义遗漏和补充建议，正式覆盖、孤立关系、Hash 一致性和发布阻塞状态由服务端 `CoverageAuditResult` 计算。
- **人工发布**：工作流成功只表示 AI 候选通过机器校验，不代表已成为正式测试资产；发布必须经过人工确认。
- **复制后复用**：复用历史用例时在当前测试设计中创建新的服务端 `caseId` 和 revision；原样复用保持测试语义不变，复制并修改必须保存 Diff，历史来源永不覆盖。
- **集合只保存引用**：同一正式用例可被明确版本的功能、冒烟、回归或功能域集合引用；不得为组合执行而复制正文、改变 `caseId` 或把全量回归成员写入本次功能用例集。
- **基线版本不可变**：既有 `TestSuiteVersion` 永不原地增删成员；第四期只提出冒烟候选。后续执行阶段只有在组合快照完成真实执行、稳定性证据满足规则且人工确认后，才能发布新的冒烟套件版本。
- **历史不覆盖**：重试、树修订、重新具象化、全部重跑、历史复用和人工修订均创建新执行、新草稿或新产物版本。
- **机器契约优先**：正式用例以版本化 JSON Schema 保存；页面表单和 Markdown 只是同一结构化数据的编辑/展示方式，不通过自然语言反向解析重建正式字段。
- **面向后续执行**：用例必须包含明确入口、前置条件、数据、步骤、逐步期望、检查点、清理、依赖和就绪状态，使执行 Agent 无需猜测操作对象或判定标准。
- **只读设计**：本期 Agent 不执行代码、Shell、任意 HTTP、浏览器、压测或外部写操作。

## 4. 多 Agent 测试设计工作流

### 4.1 Agent 角色

| Agent | 职责 | 主要输出 | 明确禁止 |
|---|---|---|---|
| `TestAnalysisAgent` | 按 `basisMode` 解构固定依据，提取实体/术语/规则/约束/状态/接口/风险，生成受控召回查询并评估历史用例 | `TestAnalysisCheckpoint`、`KnowledgeRetrievalSnapshot` | 直接生成正式用例、改变工作流拓扑、读取固定召回语料外知识 |
| `FunctionalTestDesignAgent` | 使用等价类、边界值、判定表、状态迁移、场景法、错误推测等方法发散功能测试点树候选 | `FunctionalDesignArtifact` | 直接生成完整用例、编造业务规则、直接改写历史用例 |
| `NonFunctionalTestDesignAgent` | 发散性能、稳定性、兼容性和安全测试点树候选，分别说明方法、适用性、指标和待确认项 | `NonFunctionalDesignArtifact` | 直接生成完整用例、编造 SLA/兼容基线，执行压测、故障注入或安全攻击 |
| `TestCaseSynthesisAgent` | 只读取已批准测试点树，将节点具象化为结构化用例和测试数据需求，提交语义遗漏/重复建议 | `TestCaseSynthesisCheckpoint`、`TestDataRequirementSet` | 绕过树新增孤立用例、修改固定事实/历史来源，或生成正式 ID/覆盖统计 |

四个 Agent 角色均为本期固定必跑节点；人工范围确认、测试点树批准和服务端覆盖审计是工作流门禁/确定性阶段，不伪装成 Agent。`NonFunctionalTestDesignAgent` 必须分别提交性能、稳定性、兼容性和安全四个维度的结果；某维度不适用时提交“不适用”的依据和已检查范围，不能通过省略维度伪装为完成。

### 4.2 固定 DAG

```text
选择并固定一种 basisMode
固定并校验 TestBasisSnapshot
可选固定召回语料及 HistoricalCaseSnapshot
             ↓
      TestAnalysisAgent
  依据解构 + 受控知识召回
             ↓ 服务端校验
        人工确认测试范围
             ↓ 冻结分析检查点
        ┌────┴────┐
        ↓         ↓
     功能设计   非功能设计
        └────┬────┘
             ↓ 全部校验并冻结
      服务端归并测试点树草稿
             ↓
      人工编辑并批准测试点树
             ↓ 冻结 TestPointTreeVersion
      TestCaseSynthesisAgent
          测试用例具象化
             ↓ 服务端校验用例候选
       同一综合任务定义数据需求
             ↓
  服务端 CoverageAuditResult
 Schema / 来源 / 树映射 / 数据 / 覆盖校验
             ↓
       AI 候选结果原子发布
             ↓
       人工评审与测试资产发布
             ↓
  审核冒烟候选并生成执行交接快照
```

- 功能与非功能设计节点只依赖已通过人工确认的测试分析检查点，可在配额允许时并行。
- 功能/非功能节点只输出测试点树候选，不输出正式完整用例；服务端保留专项来源后归并为 `TestPointTreeDraft`。
- `knowledge_assets` 模式只有在全部所选正文完成确定性投递、知识基线项来源定位通过且阻断冲突已处理后，才能冻结分析检查点；不得只用检索 Top-K 代替完整固定输入理解。
- 范围门禁不要求逐条确认全部合法知识基线项。来源可定位、无冲突且满足范围规则的项可自动纳入；用户一次确认总体范围，只逐条处理冲突、来源歧义、缺少关键判定标准和高风险假设。
- 测试分析检查点必须对每个选中历史用例给出 `reusable`、`reusable_with_changes`、`obsolete`、`conflict` 或 `needs_confirmation`；按默认规则批量处置并完成例外确认后，只有前两类进入设计节点的复用候选，不要求全部逐条确认。
- 测试点树未批准时综合节点保持 `blocked`；树批准后再次编辑会使批准失效，并将已有下游候选标记为过期。
- 综合节点必须等待两个设计节点都进入 `succeeded` 且存在已批准 `TestPointTreeVersion`；非功能产物内某个维度“不适用”是合法结果，不是跳过或失败。
- 覆盖审计绑定依据快照、召回快照、树版本、规范用例 revision 集合和数据需求 Hash；Hash 不一致、审计已过期或存在 blocker 时不得发布。
- 执行交接只能在当前 `TestCaseSetVersion` 发布后生成，必须固定既有冒烟/回归套件版本和所有成员引用；该确定性步骤不创建执行计划、不调度任务，也不回写既有套件版本。
- 任一必跑节点失败时，工作流不得生成正式候选统计或伪成功结果。
- 各节点最多按固定策略有限重试；Worker 重领必须使用租约、运行令牌和 fencing 防止重复发布。
- 取消从工作流向全部运行节点传播；取消后的迟到结果只可保留为过程记录。

### 4.3 失败恢复语义

| 操作 | 适用条件 | 行为 |
|---|---|---|
| 修订测试范围 | 测试分析已完成但人工要求修改范围或历史用例处置 | 使用相同固定输入创建新的测试分析任务尝试，携带公开的修订意见；旧分析产物和门禁决定继续保留，专项节点不得提前启动 |
| 重新执行失败设计节点 | 测试分析已冻结，功能或非功能设计节点失败 | 创建新的节点任务执行，复用并重新校验原测试分析检查点；不重跑已成功节点 |
| 修订测试点树 | 树草稿需要人工调整，或已批准树被再次编辑 | 创建新 `TestPointTreeRevision` 并保存 Diff；批准失效，已有用例/数据/审计结果标记过期但保留，综合节点不得自动启动 |
| 重新具象化用例 | 已批准树可用，综合或覆盖审计失败，或树产生新批准版本 | 创建新的综合任务执行，只读取指定 `TestPointTreeVersion`；生成新候选用例/数据需求/审计，不覆盖旧候选和人工修订 |
| 全部重跑 | 任意状态 | 使用当前有效 Agent 配置创建新 `workflowRunId`，按原 `basisMode` 重新固定当前用户显式选择的评审基线或知识资产版本，并从测试分析开始 |

上述操作均不得覆盖原运行。若模式对应输入的内容、Hash、投递清单或归属校验失败，只允许修正输入后全部重跑。

### 4.4 五阶段内部产物链

| 阶段 | 责任主体 | 固定输入 | 正式产物/门禁 |
|---|---|---|---|
| 1. 依据解构与知识召回 | `TestAnalysisAgent` + 检索运行时 | 依据快照、可选固定召回语料、历史用例快照 | `TestAnalysisCheckpoint`、`KnowledgeRetrievalSnapshot`、范围确认 |
| 2. 测试点智能发散 | 功能/非功能 Agent 并行 | 已确认分析检查点 | 两个专项测试点树候选产物 |
| 阶段间门禁：测试点树调整与批准 | 服务端归并 + 用户 | 两个已冻结专项产物 | `TestPointTreeDraft/Revision`、批准后的 `TestPointTreeVersion`；未批准不得进入第三阶段 |
| 3. 测试用例具象化 | `TestCaseSynthesisAgent` | 指定已批准树版本 | 结构化 `TestCaseSynthesisCheckpoint`、测试点/历史用例映射 |
| 4. 测试数据资产定义 | 同一 `TestCaseSynthesisAgent` 任务 + 服务端规范化 | 已校验用例候选与树版本 | `TestDataRequirementSet`；只定义数据模型和准备约束，不创建真实数据 |
| 5. 覆盖反向审计 | 服务端 Coverage Auditor | 依据/召回/树/用例/数据 Hash | `CoverageAuditResult`、发布阻塞项和现有用例审核/发布门禁 |

## 5. 测试设计维度与测试方式

### 5.1 通用输出要求

每个专项至少输出：

- 维度适用性及理由；
- 测试风险与优先级依据；
- 测试点标题、目标、类型、依据类型及必要的上游引用；
- 使用的 `designTechniques[]` 及选择理由，至少从等价类、边界值、判定表、状态迁移、场景法、错误推测、因果图、正交/Pairwise 中选择适用项；
- 一个或多个 UI/API 执行方式及各自选择理由；
- 测试点级前置/数据条件、验证意图和可判定 oracle 摘要，不在专项阶段展开完整步骤；
- 环境、账号、依赖、隔离和清理要求；
- 自动化候选等级及理由；
- 假设、限制、待确认项和阻塞原因；
- 与其他专项重复或冲突的候选关系。

### 5.2 测试方式

测试维度回答“验证哪类质量目标”，执行方式回答“通过哪些入口完成验证”。第四期每条测试用例通过非空 `executionMethods[]` 声明 `ui`、`api` 或二者组合；同一业务目标、前置条件和数据一致时可在一条用例内保留两种方式，各方式拥有独立步骤、期望和专属参数。数据、异步任务和外部集成等结果作为检查点记录，不作为第三种执行方式。

| 执行方式 | `executionMethods[].method` | 适用内容 | 该方式必须描述 |
|---|---|---|---|
| UI 测试 | `ui` | 页面、表单、导航、交互、视觉状态、响应式和无障碍行为 | 起始路由/页面状态、用户角色、浏览器/视口条件、语义化操作对象、操作步骤、页面状态/提示/可访问性期望 |
| API 测试 | `api` | HTTP/RPC 接口、鉴权、参数、Schema、错误、幂等和副作用 | 协议、方法、路径模板、身份角色、Header/Path/Query/Body 输入、期望状态码/响应 Schema/业务结果/副作用 |

- UI 用例只描述用户可理解的元素、状态和交互意图，不生成 CSS/XPath 定位器或自动化代码。
- API 用例不得保存明文 Token、Cookie、API Key 或真实个人数据；使用凭据引用、角色和数据占位符。
- 每个方式条目保存自己的 `steps[]`、`verificationChecks[]`、`executionReadiness` 和 `automationHint`；跨方式共同检查项可放在顶层 `sharedVerificationChecks[]`，不得把 UI 步骤复用成 API 步骤或反向复用。
- 同一业务目标、依据、数据和最终判定一致时，优先使用一条包含 `ui + api` 的组合用例；若两种入口的目标、前置条件、生命周期或缺陷归属明显不同，则拆成两条关联用例。综合 Agent 应说明组合/拆分理由并消除无意义重复。
- 无法确定测试入口时标记 `needs_confirmation`，不得随意选择 UI 或 API。

### 5.3 功能测试设计

功能专项至少分析：

1. 正常业务流程、替代流程和中断后继续；
2. 输入等价类、边界值、空值、格式、长度和组合约束；
3. 状态转换、非法状态、重复提交、幂等和并发操作；
4. 角色、权限、数据范围和跨项目版本隔离；
5. 接口输入输出、错误码、超时、重试和兼容行为；
6. 数据创建、更新、删除、一致性、事务和历史保留；
7. 异常提示、降级、取消、恢复和审计可见性；
8. 需求 Finding 与技术 Finding 中尚未关闭的高风险事项。

功能专项还必须判断每个场景适合通过 UI 还是 API 方式验证，并覆盖：

- UI：页面状态、表单校验、反馈提示、导航、刷新恢复、键盘操作和响应式行为；
- API：成功/失败响应、鉴权、参数组合、Schema、幂等、并发、分页和副作用；
- 验证检查点：事务一致性、异步状态、重试、取消、恢复、审计记录和集成副作用。

### 5.4 性能测试设计

性能专项不得只写“进行压测”，至少描述：

- 业务事务、调用链和关键资源；
- 并发用户、到达率、数据量、预热、持续时间和负载模型；
- 响应时间分位数、吞吐、错误率、队列时间和资源指标；
- 基准、阶梯、峰值、突发、容量上限和退化场景；
- 测试环境与生产等效性、监控点和停止条件；
- 结果判定阈值的来源。

若固定依据未给出量化目标，相关用例标记 `blocked_by_confirmation`，并生成需要业务或技术负责人确认的指标问题。

### 5.5 稳定性测试设计

稳定性专项至少分析：

- 长时间运行、重复执行和资源泄漏；
- 依赖超时、断连、限流、部分失败和慢响应；
- 进程重启、Worker 失租约、任务重领和迟到结果；
- 重试、退避、熔断、降级、补偿和恢复；
- 重复消息、乱序、并发更新和幂等；
- 数据一致性、未完成事务、恢复点和历史可追溯；
- 容量耗尽、磁盘/内存/连接池压力和告警；
- 恢复时间目标、恢复点目标及其来源。

### 5.6 兼容性测试设计

兼容性专项使用显式矩阵设计，至少考虑：

- 浏览器内核与支持版本；
- 操作系统、设备类型、屏幕尺寸和输入方式；
- Node.js、PostgreSQL、pgvector、模型 Provider 和 Agent Runtime 版本；
- API/Schema 向前、向后兼容与未知字段；
- 历史数据迁移、旧快照读取和新旧版本并存；
- 网络代理、编码、时区、区域格式和中文路径；
- 升级、降级和回滚边界。

只有产品或技术基线明确声明的组合才可标记为“受支持”。未声明组合进入待确认项，不能由 Agent 自行扩展支持承诺。

### 5.7 安全及补充维度

安全专项至少覆盖身份伪造、越权、跨版本访问、输入校验、Prompt injection、SSRF、凭据泄露、重放、危险工具、日志脱敏、数据保留和审计完整性。

测试分析 Agent 还应判断以下补充维度是否适用，并允许专项结果携带相应标签：

- 可用性与无障碍；
- 数据完整性与迁移；
- 可观测性与可诊断性；
- 可维护性与配置治理；
- 本地化、时区和编码。

补充维度在本期不增加新的必跑 Agent；高风险项目可在后续工作流版本中新增独立 Agent，历史运行继续绑定原拓扑版本。

### 5.8 测试用例机器契约

正式测试用例使用 `test-case/v1`，正式用例集使用 `test-case-set/v1`。`TestCaseSetVersion` 至少包含 `schemaVersion`、用例集 ID/版本、项目版本、`basisMode`、依据/召回快照 Hash、`testPointTreeVersionId + treeHash`、`approvedCaseRevisionSetSha256`、数据需求集版本/Hash、覆盖审计 Hash、来源工作流、内容 Hash、发布时间和 `cases[]`。

每条 `TestCase` 至少包含：

| 字段 | 规则 |
|---|---|
| `caseId`、`caseKey` | 服务端生成且在同一用例集生命周期内稳定；标题变化不改变标识。 |
| `title`、`objective` | 标题唯一清晰；目标说明要验证的行为和成功判定。 |
| `testPointRefs[]` | 至少引用一个已批准树版本中的有效测试点；服务端拒绝孤立用例和跨树版本引用。 |
| `dimension`、`executionMethods[]`、`priority` | 维度为功能/性能/稳定性/兼容性/安全等规范枚举；执行方式为非空、按 `method` 唯一的 `ui`/`api` 判别联合，可同时包含两项；优先级为 `P0`～`P3`。 |
| `preconditions[]` | 每项包含类型、描述和必须满足的状态，不把多个条件塞进一个不可拆分段落。 |
| `testDataRequirementRefs[]`、`parameterSets[]` | 引用独立测试数据需求，使用命名参数和值类型；秘密只保存引用或占位符。 |
| `executionMethods[].uiSpec/apiSpec` | 每个方式条目按 `method` 判别：UI 保存起始路由、角色、浏览器/视口和语义对象；API 保存协议、方法、路径、身份、Header/Path/Query/Body 模板。 |
| `executionMethods[].steps[]` | 每种方式使用独立稳定序号、明确动作、输入引用和本步骤 `expectedResults[]`；禁止跨方式用“同上”替代可独立执行的描述。 |
| `executionMethods[].verificationChecks[]`、`sharedVerificationChecks[]` | 每项包含目标类型、观察对象、断言和期望值，可覆盖页面、响应、数据、任务和集成副作用；共享检查点只放跨方式共同结果。 |
| `postconditions[]`、`cleanup[]` | 描述执行后应保留的状态、数据清理和失败后的恢复要求。 |
| `dependencies[]` | 引用必须先完成的用例或环境能力；服务端拒绝不存在引用和循环依赖。 |
| `executionMethods[].executionReadiness` | 每种方式分别为 `ready`、`blocked` 或 `needs_confirmation` 并保存原因；正式发布要求全部已声明方式为 `ready`。 |
| `executionMethods[].automationHint` | 每种方式分别为 `recommended`、`optional` 或 `manual` 及理由；仅供下一阶段决策，不包含脚本。 |
| `basisRelations`、`reviewStatus` | 保存模式匹配的设计依据关系以及当前审核状态。 |
| `origin`、`reuseMode` | `origin` 为 `ai_generated`、`historical_reuse` 或 `manual_created`；历史复用时 `reuseMode` 为 `unchanged` 或 `modified`。 |
| `historicalSources[]`、`changeSummary` | 保存来源类型、来源项目版本、`testCaseSetVersionId + caseId` 或 `assetVersionId + locator`、源内容 Hash；修改后复用必须说明差异及其当前依据。 |

- `executionMethods[]` 至少一项且同一 `method` 不得重复；`ui` 条目必须且只能包含 `uiSpec`，`api` 条目必须且只能包含 `apiSpec`。删除唯一方式应被拒绝。
- `unchanged` 只适用于来自结构化 `TestCaseSetVersion` 且测试语义 Hash 未变化的复制；知识资产文本映射、多个历史用例归并或任一字段修改均记为 `modified`。
- 历史来源字段和复用关系由服务端从 `HistoricalCaseSnapshot` 生成；Agent 与用户不得填写任意版本、`caseId`、定位或 Hash。
- `review_baseline` 用例依据可使用 `requirement`、`solution`、`finding`；`knowledge_assets` 用例依据使用 `knowledge_basis` 或 `user_objective`。两种模式都可使用 `derived_risk`、`external_practice`、`assumption` 和独立的历史复用关系。
- `knowledge_basis` 必须引用冻结 `KnowledgeBasisItem`；`user_objective` 引用快照中的用户目标且不得伪造原文。模式不匹配的引用由服务端拒绝。
- 字段可包含自然语言描述，但结构、枚举、引用、步骤顺序和断言含义必须由 Schema 确定。
- 服务端为发布版本生成规范化 JSON 和内容 Hash；字段顺序、空值处理和枚举表示必须确定，保证人、AI 和后续服务读取一致。
- Schema 升级必须生成新版本并提供显式迁移/兼容策略；不得静默改变历史 `TestCaseSetVersion` 语义。
- 下一阶段执行 Agent 只接收指定 `testCaseSetVersionId + {caseId, executionMethods[]}[]` 及其中冻结的结构化用例/数据需求，不从最新草稿、Markdown/Excel 报告或知识检索结果推断执行入口与内容。

### 5.9 测试点树与测试数据需求契约

`TestPointTreeDraft/Revision/Version` 使用 `test-point-tree/v1`：

- 节点至少包含服务端 `nodeId`、`parentId`、稳定顺序、节点类型、标题、维度、目标、优先级、适用性、`designTechniques[]`、UI/API 候选、oracle 摘要、依据关系、历史用例映射和状态；
- 服务端规范存储稳定节点与父子/排序关系，JSON 树只是传输和页面投影；来源、覆盖和历史复用关系保持独立多对多，不因拖拽而改写；
- 支持一个叶子测试点生成零、一或多条用例，也支持多个高度重合测试点归并为参数化用例；零用例或归并必须保存明确状态和理由，不能强制“一叶一用例”制造重复；
- 每次新增、删除、移动、拆分、合并、改名、调整优先级或标记不适用都生成不可变树 revision 和字段/结构 Diff。

`TestDataRequirementSet` 使用 `test-data-requirement-set/v1`。每条 `TestDataRequirement` 至少包含：

| 字段 | 规则 |
|---|---|
| `dataRequirementId`、`name` | 服务端生成 ID；名称描述数据用途，不使用真实个人标识。 |
| `testPointRefs[]`、`caseRefs[]` | 关联需要该数据的测试点和候选/正式用例，服务端校验同树/用例集归属。 |
| `entityType`、`featureTags[]` | 描述账号、订单、设备等实体及状态标签，例如 `AccountStatus=Expired`。 |
| `fieldConstraints[]`、`relationships[]` | 字段类型、范围、枚举、组合约束和实体关系，不保存真实秘密。 |
| `quantity`、`initialState` | 数据规模、初始业务状态、时间条件和唯一性/并发要求。 |
| `preparationHint` | 仅描述未来生成、导入、Mock 或人工准备建议，不在本期执行。 |
| `sensitivity`、`isolation` | 敏感级别、脱敏、租户/项目版本隔离和禁止使用生产数据的要求。 |
| `resetAndCleanup`、`readiness` | 重置/清理语义，以及 `ready`、`blocked`、`needs_confirmation` 和原因。 |

发布版本冻结数据需求及其与用例关系。下一阶段可以据此设计造数动作，但本期不连接数据库、调用造数接口或创建真实测试数据。

### 5.10 测试用例库、用例集与冒烟演进契约

- 项目测试用例库是已发布测试资产的只读检索投影，可按功能域、来源版本、UI/API、优先级、审核/就绪状态和所在集合筛选；一个用例出现在多个集合时仍指向同一固定来源版本，不生成重复正文。
- 当前测试设计发布的 `TestCaseSetVersion` 定位为“本次新功能用例集”，成员只包含本次新增、修改后复用和原样复用的批准/ready 用例；“受影响回归”通过 `ImpactedRegressionReference` 独立保存，不作为该功能集成员。
- 项目级 `TestSuiteVersion` 使用 `test-suite/v1`，`suiteType` 至少支持 `smoke`、`regression`、`domain`；每个版本固定名称、版本号、成员引用、内容 Hash、发布人和发布时间。历史版本只读，第四期没有发布或变更套件成员的接口。
- 冒烟候选必须来自当前已发布功能用例集，默认要求 `P0/P1`、覆盖关键可用链路、候选选择的 `executionMethods[]` 均为 `ready`、执行时间可控、结果确定、外部依赖少且失败可诊断；不满足时必须保存例外理由，候选可由 Agent 建议但须人工确认。
- “本次冒烟执行快照”按 `当前 smoke TestSuiteVersion + 已确认 SmokeCandidateRelation` 解析为固定成员引用并去重，保存基础套件版本、候选来源和组合内容 Hash。它仅用于下一阶段创建计划，不产生新的 `TestSuiteVersion`。
- 例如当前冒烟基线为 v6、包含 18 条，用例设计确认 3 条候选时，交接快照固定为“v6 的 18 条 + 本次 3 条候选 = 21 条”；v6 始终保持 18 条。后续阶段完成真实执行并积累稳定性证据后，才可经人工决定发布包含合格成员的 v7。
- `TestExecutionHandoff` 至少提供三种固定顺序：标准提测为“冒烟组合快照 → 本次新功能集 → 影响回归引用 → 全量回归基线”；快速验证为前三段、明确跳过全量回归；直接全量为指定全量回归基线。各段保存集合版本、成员选择、去重规则和进入/退出条件。
- 执行交接只表达建议和精确输入。后续执行阶段据此创建正式 `TestPlanVersion`、绑定构建/环境、调度任务并记录结果；不得把交接状态、候选确认或页面演示解释为测试已执行。

## 6. 用户流程与页面

### 6.1 主流程

```text
选择 open 项目版本
  → 进入测试设计
  → 可先查看项目测试用例库、功能/冒烟/回归/功能域用例集及固定版本
  → 选择测试依据模式
      ├─ 评审基线：选择 succeeded 需求评审及引用它的 succeeded 技术方案评审
      └─ 知识库资料：选择一至多份 ready 固定资产版本并填写测试目标/范围
  → 可选历史用例集/用例或 test_case 资产版本
  → 可选启用受控知识召回并固定语料/索引范围
  → 查看固定输入、历史来源、模式对应阻断项和 Agent 就绪状态
  → 创建 queued TestDesignWorkflowRun
  → 查看依据解构、召回内容并确认测试范围及历史用例处置
  → 查看功能与非功能 Agent 并行发散测试点
  → 在测试点树中增删、移动、拆分、合并并批准树版本
  → 查看基于已批准树具象化的用例和测试数据需求
  → 查看覆盖审计并处理阻断项
  → 在线修改用例并提交审核
  → 人工通过、驳回或要求修订
  → 导出 JSON/Markdown/Excel 或发布新的新功能 TestCaseSetVersion
  → 标记并人工确认冒烟候选，关联受影响回归用例
  → 选择标准/快速/直接全量策略并生成 TestExecutionHandoff
```

### 6.2 运行前检查

- 只允许 `open` 项目版本创建新测试设计运行；`locked`、`archived` 只读查看历史。
- `review_baseline` 模式下，需求运行和技术方案运行必须为 `succeeded`，属于同一项目版本，且技术方案运行的来源需求运行与所选需求运行一致；固定需求点、方案要点、Finding 处置和结果 Hash 必须可读取。
- `knowledge_assets` 模式下，至少选择一份当前项目知识库中正文可读的 `ready` 固定资产版本并填写测试目标；服务端固定资产/Chunk 清单、内容 Hash、索引范围和完整投递清单，不要求需求或技术方案运行存在。
- 两种模式均提供 `knowledgeAugmentation`：不需要补充召回时显式选择 `disabled`，需要时选择 `selected_assets` 或 `fixed_index`。启用时必须在运行创建前固定召回语料/索引、Embedding 与检索配置；不得把执行时的活动索引或 latest 当作语料。
- 两种模式的输入字段严格互斥；空选择、跨项目资产、`latest`、草稿/处理中资产、Hash 不一致或无法完整投递时拒绝创建。
- 历史用例为可选输入；选择后必须固定具体版本、具体用例/定位和内容 Hash。结构化历史用例必须通过其保存时的 Schema 校验，知识资产必须为 `ready` 的固定 `test_case` 版本。
- 四个工作流 Agent 都必须存在已发布版本，并通过模型与资源门禁。
- 评审模式展示尚未处置的 blocker/high Finding；知识库模式展示冲突、来源歧义、缺少关键判定标准和高风险假设。本期允许用户确认非阻断风险后继续，但运行快照和报告必须保留风险背景。
- 任一固定输入、Agent 或必需协议不可用时拒绝启动并显示真实原因。

### 6.3 工作台布局

| 区域 | 用户可见能力 |
|---|---|
| 顶部操作区 | 项目版本、测试设计、`workflowRunId`、`basisMode`、五阶段进度、主依据/召回/历史用例摘要、Agent 就绪、范围/树门禁和过期提示；开始、取消、恢复、导出和发布。项目级入口提供“测试设计 / 测试用例库 / 用例集”视图切换。 |
| 左侧依据区 | 按模式展示固定需求点/方案要点/Finding，或知识基线项及固定资产原文；同时展示历史用例来源、用户目标和推导依据。 |
| 中间设计区 | 概览、工作流、依据解构、知识召回、测试点树、测试用例、测试数据、覆盖审计、历史复用、待确认项、历史版本和“用例集”标签页；用例集标签展示当前功能集、影响回归、冒烟候选、组合快照与执行交接。 |
| 右侧详情区 | 随当前视图展示依据/召回原文、树节点编辑器、用例结构化编辑器、数据需求或覆盖缺口；支持查看来源、revision 和 Diff。 |

工作流视图必须区分四个 Agent 节点、两个用户门禁和服务端归并/覆盖审计阶段，展示依赖、状态、尝试次数、开始/结束时间、实际模型、降级和脱敏错误；不展示模型隐藏思维。

### 6.4 依据、召回与测试点树编辑

- 创建页使用分段选择器选择“评审基线”或“知识库资料”；切换模式清空另一分支的未提交字段，服务端仍执行独立 `oneOf` 校验。`TestDesign` 创建后不得原地切换模式。
- 知识库选择器展示资产类型、名称、逻辑路径、版本、状态、内容 Hash 和选择状态，支持按类型/路径筛选；主依据不自动选择整个知识库。需要全库补充召回时，用户必须显式选择并冻结一个具体索引版本。
- 依据解构视图展示实体、术语、业务动作、规则、约束、状态、接口、风险、依据类型和来源；召回视图展示查询意图、命中 Chunk、相关分数、资料角色和固定原文。
- 测试点树按维度/业务域分层展示，提供新增同级/子级、移动、拆分、合并、删除、标记不适用、调整优先级和测试方法操作；使用稳定节点 ID，拖拽不得改写来源关系。
- 树保存使用 revision/ETag 乐观锁，每次结构或字段修改生成 `TestPointTreeRevision` 和 Diff；并发冲突提供刷新、比较和重新应用。
- 树门禁保存批准/驳回/要求修订、说明、操作者、目标 revision 和时间。只有批准版本形成不可变 `TestPointTreeVersion` 并解锁综合 Agent。
- 已批准树再次编辑时批准立即失效，已有用例、数据需求和覆盖审计标记为过期；页面提供明确“重新具象化用例”，不自动覆盖人工修订。

### 6.5 用例在线编辑与人工审核

- 测试用例支持按维度、包含 UI/包含 API 执行方式、优先级、状态、需求点/知识基线项、自动化候选和阻塞状态筛选；组合用例同时命中 UI 与 API 筛选。
- 测试数据视图支持按实体类型、关联测试点/用例、敏感级别和 readiness 筛选，只展示条件/占位符，不展示真实秘密或生产数据。
- 覆盖审计视图以“依据项 → 测试点 → 用例”双向展开，突出未覆盖依据、无用例测试点、无树节点/无依据用例、缺失 oracle/数据、重复冲突和 Hash 过期。
- 历史用例选择器支持按来源项目版本、用例集版本、UI/API、维度、审核状态和执行就绪状态筛选；默认不预选任何历史版本。
- 对结构化历史用例提供“复用”和“复制并修改”；前者复制测试语义并建立 `unchanged` 关系，后者创建当前草稿并进入差异编辑。对 Markdown/TXT 等 `test_case` 资产只提供“参考并生成草稿”，结果按 `modified` 管理和审核。
- 历史比较视图并列展示冻结来源与当前 revision 的字段差异、来源 Hash、修改摘要和适用性结论；源版本后续新增、更新或删除不得改写已经冻结的快照或当前草稿。
- 点击用例来源时按模式打开冻结上游 Evidence，或固定知识资产版本的原文定位。
- 在线编辑器按 `test-case/v1` 展示结构化表单，UI/API 使用可多选控件；每个已选方式独立展示专属参数、步骤、逐步期望、检查点、就绪与自动化提示，同时维护共享数据、检查点、清理项和依赖。取消某方式只删除该方式分支且必须二次确认，至少保留一种方式。
- 草稿支持显式保存和可见的自动保存状态；保存失败时保留本地未提交内容并提示重试，不显示虚假“已保存”。
- 保存携带 `revision`/ETag 乐观锁；检测到其他会话已更新时禁止覆盖，提供刷新、比较和基于最新版本重新应用修改。
- 每次保存生成不可变 `TestCaseRevision` 和字段级 Diff；支持查看初始 revision 0、任意两个修订及当前草稿的差异。
- 审核状态为 `draft`、`in_review`、`approved`、`rejected`、`needs_revision`；提交审核后普通编辑被锁定，要求修订后重新进入草稿。
- 支持逐条和批量提交审核、通过、驳回、要求修订；批量操作必须展示影响范围并为每条用例产生独立审核记录。
- 审核记录追加保存决定、说明、操作者、时间和目标 revision；新修订会使旧批准失效并重新进入 `draft`。
- 服务端保护 `caseId`、依据快照归属和内容 Hash；用户只能从本次冻结输入中选择模式匹配的有效来源关系，不能录入任意 ID。
- 当前用例新增、删除或内容 revision 变化后，绑定旧用例 revision 集合 Hash 的 `CoverageAuditResult` 立即过期；测试数据需求集合发生变化时同样过期。用户必须在当前内容上重新执行覆盖审计，不得只重新审核后沿用旧审计。
- 只有 `approved`、全部已声明 `executionMethods[].executionReadiness=ready` 且不含未解决发布阻塞项的当前 revision 可以进入发布版本。

### 6.6 用例库、用例集与执行交接

- “测试用例库”按项目聚合已发布用例，展示稳定 `caseId`、来源 `TestCaseSetVersion`、当前可读 revision 摘要及所属集合；点击成员必须回到固定版本详情，不跳转 `latest`。
- “用例集”目录区分本次新功能集、冒烟基线、全量回归和功能域集合，展示类型、版本、成员数、内容 Hash、发布状态和时间；历史版本可比较但不可编辑。
- 工作台“用例集”标签按新增、修改、原样复用、影响回归引用和冒烟候选分组统计；影响回归与候选关系允许填写理由并由服务端校验固定引用。
- 冒烟演进区并列展示当前基线、待确认候选和去重后的本次组合快照，清楚标识“当前基线不会被修改”；没有固定冒烟基线或存在不可读成员时，不生成标准/快速交接并显示阻断原因。
- 执行策略使用单选分段控件，选择后展示各阶段的顺序、精确集合版本、成员数量、去重数量和退出条件。生成交接前必须再次确认所有引用和内容 Hash 未变化。
- 页面可复制或下载机器可读交接信息，但“创建执行计划”“开始冒烟”“发布新冒烟版本”均属于后续阶段，本期不得提供可造成真实执行或基线变更的可用操作。

## 7. 功能需求

### 7.1 输入、快照与运行

#### FR-601：测试依据模式与固定输入

- 创建测试设计时必须显式提交 `projectVersionId`、`basisMode`、名称、测试目标和可选 `historicalCaseSelections[]`；`basisMode` 只能为 `review_baseline` 或 `knowledge_assets`。
- 两个主依据分支均必须提交公共 `knowledgeAugmentation` 严格判别联合：`disabled` 只能提交 `mode`；`selected_assets` 必须且只能额外提交非空去重 `assetVersionIds[]`；`fixed_index` 必须且只能额外提交固定 `indexVersionId` 及可选范围过滤。错误分支字段即使为空或 `null` 也拒绝，三种模式都不接受运行时默认 active/latest。
- 创建请求使用严格 `oneOf`：`review_baseline` 必须且只能提交 `sourceReviewRunId + sourceTechnicalSolutionRunId`；`knowledge_assets` 必须且只能提交非空 `knowledgeAssetVersionIds[]`、测试目标以及可选包含/排除范围、关注维度和用户覆盖目标。错误分支字段即使为空或 `null` 也拒绝。
- `review_baseline` 模式由服务端校验项目版本、成功状态及需求到技术方案的引用链，不接受客户端提交任意需求点/方案要点作为可信范围。
- `knowledge_assets` 模式由服务端校验资产属于当前项目知识库、版本 ID 去重、`ready`、正文/Chunk 可读、Hash 一致且可进入固定投递范围；不要求、也不接受需求/技术评审运行 ID。
- 知识库主依据不接受隐式“整个知识库”、`latest`、动态目录或仅检索关键词作为固定输入；显式 `fixed_index` 只作为补充召回语料快照，不替代主依据。资产后续更新、活动索引切换或知识库新增内容不得改变已创建快照。
- 历史来源必须属于当前 SmartHub 项目；允许显式引用其他 `projectVersionId` 的已发布用例，但拒绝跨项目来源、`latest`、未发布草稿、未通过审核用例和已失效定位。
- 创建运行时按模式固定双评审结果及其对象/Hash，或固定知识资产版本、正文/Chunk、内容 Hash、索引范围、`KnowledgeInputPackage`、`InputDeliveryManifest`、用户目标/范围；启用召回时另固定语料/索引、Embedding/检索配置和范围，关闭时生成规范空 `KnowledgeRetrievalSnapshot`；同时固定历史用例内容、工作流配置和创建时间。
- `basisMode` 在一个 `TestDesign` 生命周期内不可修改；切换模式或替换主依据必须创建新的 `TestDesign`，不覆盖原设计。
- 上游产生新运行、资产产生新版本或 Finding 后续被处置，均不得改写历史测试设计运行。

#### FR-602：工作流快照与状态

- 运行快照必须包含工作流定义版本、拓扑 Hash、五阶段、四个 Agent 定义/Prompt/模型/工具/Skill/MCP/权限/限制版本、两个门禁、服务端归并/审计阶段、节点依赖、并发和重试策略。
- 每个运行、任务和交接产物必须保存 `basisMode + basisSnapshotSha256`；不同模式或不同依据快照的产物不得串接。
- 工作流状态至少包括 `queued`、`running`、`waiting_approval`、`succeeded`、`failed`、`cancelled`；每个任务节点独立记录状态和尝试。
- 页面进度基于已持久化节点状态计算，不使用前端计时模拟。
- 工作流成功必须拥有已批准测试点树，并经过用例/数据需求 Schema、树映射、来源关系、重复关系和覆盖审计校验后原子保存正式候选。

#### FR-603：工作流调度与交接

- 服务端按固定 DAG 创建任务；Agent 不能创建新 Agent、改变依赖或自行跳过必跑节点。
- 每个 Agent 使用独立会话，只接收本节点需要的固定输入和已冻结上游交接产物。
- `HandoffArtifact` 必须记录 Schema 版本、阶段、来源任务、依据/召回/树/上游产物 Hash、输入引用和校验状态。
- 未校验候选、自由对话、隐藏推理和临时工具结果不得作为下游正式输入。
- 并行专项彼此不读取未冻结结果；服务端只在两者均冻结后归并树候选，保留重复/冲突和专项来源供人工处理，不让某一分支静默覆盖另一分支。
- 测试分析检查点只有在范围门禁批准后才能冻结并解锁专项节点；门禁拒绝、超时或要求修订不得自动继续。
- `TestCaseSynthesisAgent` 只能读取指定已批准 `TestPointTreeVersion`；树门禁拒绝、超时、要求修订或批准失效时不得启动。

### 7.2 Agent 输出与服务端校验

#### FR-604：依据解构与受控知识召回协议

`TestAnalysisAgent` 使用独立版本化协议，至少提交：

- 范围摘要、测试目标和排除范围；
- 实体、参与者、术语、业务动作、规则、约束、状态/迁移、输入输出、接口和可判定 oracle；
- 模式对应依据的可测试性分析；
- 风险、优先级依据，以及功能、性能、稳定性、兼容性和安全维度的适用性说明；
- UI 与 API 测试方式的适用性、范围和预计用例分布；
- 每个历史用例的适用性结论、理由、受当前测试依据变化影响的字段以及建议处置；
- Happy Path、关键判断节点和候选测试域框架；
- 缺失指标、环境、数据和兼容矩阵形成的待确认项。

模式专属规则：

- `review_baseline`：模型只引用固定输入内的 `requirementPointRef`、`solutionPointRef` 和 `findingRef`。
- `knowledge_assets`：模型从完整固定输入提交 `KnowledgeBasisItemCandidate`，至少包含类型、标题、描述和逐字 `sourceTexts[]`，并报告重复、冲突、术语差异、缺失前提和可能过期项；不得提交 `RP-*`、`TSP-*` 或伪装成已评审需求。
- 服务端仅在所选固定正文中定位原文，生成 `KBP-*`、`assetVersionId`、Chunk/标题路径/行字符范围和内容 Hash；无法定位、越界或歧义未解决的候选不得成为正式 `KnowledgeBasisItem`，也不得回退到相似文本或 `latest`。
- 原文定位成功只表示“资料中存在该表述”，不表示事实正确。无冲突且符合范围规则的知识基线项可按策略自动纳入；影响测试预期的冲突、低置信来源、缺少关键 oracle 或 P0/P1 高风险假设进入人工处理。
- 所选正文未完整投递、没有任何有效知识基线项或阻断冲突未解决时，分析检查点不得冻结为空成功。

召回专属规则：

- `knowledgeAugmentation.mode=disabled` 时不调用 Embedding/检索服务，服务端保存包含空查询、空命中、固定规范版本和规范化 Hash 的空 `KnowledgeRetrievalSnapshot`。
- `selected_assets` 或 `fixed_index` 模式下，Agent 根据固定主依据提交去重后的需求特征和查询意图；检索运行时只在对应固定语料 allowlist 中执行向量/混合召回。
- 服务端保存 `KnowledgeRetrievalSnapshot`：模式、查询/特征 Hash、Embedding/检索配置版本、固定索引/资产版本、命中 `assetVersionId + chunkId`、相关分数、内容 Hash 和时间；重试直接复用快照，不重新查询 active/latest。
- 命中内容按 `normative_reference`、`historical_defect`、`domain_practice` 或 `context_only` 分类。召回的缺陷/实践用于 `derived_risk` 或 `external_practice`，不能自动升级为已确认需求、方案或业务 oracle。
- 没有召回结果是合法状态，不得伪造上下文；主依据完整投递仍是分析成功前提。

服务端生成测试分析检查点 ID、知识基线项 ID、固定定位和正式引用。

#### FR-605：测试点发散与测试点树协议

- 功能与非功能设计节点分别使用独立版本化协议，只提交职责范围内的测试点树候选，不提交完整步骤化用例。
- `review_baseline` 节点只引用冻结需求/方案/Finding；`knowledge_assets` 节点只引用范围门禁批准的 `knowledgeBasisRef` 或 `userObjectiveRef`，不得重新定义知识依据或读取快照外资产。
- 设计节点接收人工确认的历史复用候选和冻结召回上下文；召回内容只能按已分类角色使用。
- 两个设计节点都提交父级临时引用、候选测试点、`designTechniques[]`、UI/API 候选、验证意图、oracle 摘要、数据条件摘要、风险、假设、待确认项和输入内引用。
- 功能节点至少对 Happy Path、每个关键判断、等价类、边界、状态、异常、权限、并发/幂等和历史缺陷风险说明采用或不采用的设计方法。
- 非功能设计产物必须分别包含性能、稳定性、兼容性和安全四个分区，并为每个分区给出适用性。
- 非功能用例的量化阈值必须注明来自当前冻结评审对象/知识基线项、已批准策略或基线；否则明确标记为待确认，无依据的确定数值不得通过正式校验。
- 不适用结果必须包含理由和已检查范围，不得提交空成功。
- 服务端校验临时父子引用，生成稳定 `nodeId`，保留两个专项原始候选和关系后形成 `TestPointTreeDraft`；重复/冲突节点不得静默丢弃。
- 模型不得提交正式 TestPoint/树 revision/TestCase ID、资产版本 ID、覆盖率或发布状态。

#### FR-606：用例与测试数据需求具象化协议

综合 Agent 只读取指定已批准 `TestPointTreeVersion`，在同一固定任务中按顺序提交 `TestCaseSynthesisCheckpoint` 和 `TestDataRequirementSet` 两个独立产物。服务端必须先校验并固定用例候选 Hash，再允许数据需求引用这些候选；数据需求校验失败不改变已冻结用例候选，也不新增第五个 Agent 节点。

两个产物合计至少提交：

| 字段 | 要求 |
|---|---|
| 标题与目标 | 描述唯一验证意图，不以步骤编号充当标题。 |
| 测试点映射 | 引用输入树中的一个或多个 `testPointRef`；不得提交树外临时节点或孤立用例。 |
| 维度与类型 | 规范维度、测试类型和补充标签。 |
| 执行方式 | `executionMethods[]` 至少包含一个按 `method` 唯一的 `ui`/`api` 条目，可同时包含二者并说明组合理由。 |
| 优先级 | `P0`、`P1`、`P2`、`P3` 及可解释理由。 |
| 前置与数据 | 环境、账号角色、状态、数据需求临时引用和隔离要求。 |
| 步骤与期望 | 每个执行方式分别保存步骤；每个动作对应可观察、可判定的结果。 |
| 方式特定参数 | UI 条目保存路由/角色/视口/语义对象，API 条目保存协议/方法/路径/参数/响应；组合用例同时具备两套参数。 |
| 验证检查点 | 各方式 `verificationChecks[]` 记录自身页面/响应判定，`sharedVerificationChecks[]` 记录共同数据、任务或集成结果及其可判定期望。 |
| 专项判定 | 性能指标、恢复条件、兼容组合或安全判定；不适用时省略。 |
| 清理与恢复 | 数据清理、状态恢复和残留风险。 |
| 自动化候选 | 每个执行方式分别提交 `recommended`、`optional`、`manual` 及理由，不生成代码。 |
| 来源关系 | 按 `basisMode` 标明 `requirement`、`solution`、`finding`、`knowledge_basis`、`user_objective`、`derived_risk`、`external_practice` 或 `assumption`；对象类来源引用冻结对象，推导类来源给出理由。 |
| 历史沿革 | 对历史候选提交输入内历史引用、建议复用方式和变更摘要，不提交任意历史 ID、Hash 或正式复用关系。 |
| 数据需求 | 提交实体、特征标签、字段/关系约束、数量、初始状态、准备提示、敏感/隔离、重置/清理和 readiness；不提交真实数据。 |
| 审计建议 | 提交可能遗漏的依据/异常分支、孤立测试点、重复冲突和缺少 oracle/数据提示；不提交正式覆盖率或发布结论。 |
| 执行就绪 | 每个 `executionMethods[]` 条目的 `executionReadiness` 为 `ready`、`blocked` 或 `needs_confirmation`，非 ready 必须给出原因。 |

综合 Agent 可建议一个测试点生成多条参数化用例，或多个高度重合测试点归并为一条用例；必须保存映射和理由，不强制一叶一用例。最终 TestCase/数据需求 ID、历史复用关系、覆盖关系和统计由服务端生成。

#### FR-607：覆盖反向审计、去重与校验

- 服务端按“阶段/Hash 一致性 -> 基础 Schema -> 树/数据映射 -> 语义规范化 -> 测试方式及专属字段 -> 依据引用 -> 用例可判定性 -> 重复/冲突 -> 双向覆盖”顺序生成 `CoverageAuditResult`，并对按 `caseId` 排序的当前 `{caseId, revision, contentSha256}` 集合计算 `auditedCaseRevisionSetSha256`。
- 评审基线模式的覆盖分母为范围内冻结需求点；知识库模式的覆盖分母为范围门禁批准的 `KnowledgeBasisItem` 和用户覆盖目标，不以文档数、Chunk 数或模型自报数量代替。
- 任一已声明 UI 分支缺少起始页面、操作对象或页面期望，或任一已声明 API 分支缺少方法、路径、输入或响应判定时，整条用例不得进入可接受状态；组合用例必须分别通过两套分支校验。
- 每个范围内依据项必须可追溯到测试点和已审核/就绪用例；每个叶子测试点必须有用例、明确排除/归并理由或待确认状态；每条用例必须关联已批准树节点及合法依据/推导说明。
- 数据需求引用必须存在且归属一致；用例依赖未就绪数据时，其任何依赖该数据的执行方式不得标记为 `executionReadiness=ready`。
- 同一验证目标、前置、动作和期望高度重合的候选应建立重复组；自动合并不得丢失专项来源、模式化依据关系或更严格的判定条件。
- `unchanged` 历史复用必须验证来源 Schema、源语义 Hash 与复制后语义 Hash；`modified` 必须存在可复核字段 Diff 和修改摘要，`obsolete`/`conflict` 不得进入当前用例集。
- 每个模式对应的正式覆盖目标必须具有 `covered`、`partially_covered`、`not_covered`、`not_testable` 或 `needs_confirmation` 状态。
- `covered` 必须至少关联一个通过校验的测试点和用例；`not_testable`、`needs_confirmation` 必须有理由或待确认项。
- 正式覆盖数量、比例、专项分布和阻塞数量只从持久化关系计算；页面、报告和 API 分别命名为“评审基线覆盖”或“知识基线覆盖”。
- 审计同时列出未覆盖依据、孤立测试点、无树节点/无依据用例、缺失 oracle/数据、树/用例/审计 Hash 过期、重复冲突和未解决待确认项；Agent 审计建议仅作为候选提示。
- 当前用例成员/内容 revision 或 `TestDataRequirementSet` 发生变化时，原 `CoverageAuditResult` 立即标记为 `stale`；重新审核不能恢复其有效性，必须基于当前集合重新审计。
- 历史用例的原样复用、修改后复用、废弃、冲突和待确认数量只从快照、门禁决定及正式复用关系计算，不采信 Agent 自报汇总。
- 非法候选不得生成正式 ID、成功统计或可人工接受的用例。

### 7.3 查看、评审、导出与发布

#### FR-608：历史、固定路由与来源追溯

- 页面和 API 显式使用 `projectVersionId + testDesignId + workflowRunId`，刷新后恢复同一运行。
- 历史列表展示 `basisMode`、主依据/召回/历史输入摘要、五阶段状态、测试点树版本、用例/数据/覆盖摘要和创建时间。
- 需求/方案类来源通过冻结上游对象间接打开其原有 Evidence；知识来源打开 `KnowledgeBasisItem` 对应的固定资产版本原文定位。定位失败时显示错误，不跳到最新资产、其他运行或相似文本。风险推导、通用实践、用户目标和人工假设按各自规则展示说明，不伪造原文入口。
- 若上游出现新运行或新资产版本，历史测试设计只显示“可能过期”，不自动替换。

#### FR-609：历史测试用例参考、复用与修改

- 创建运行前可从同一项目的已发布 `TestCaseSetVersion` 按用例选择，也可选择 `ready` 的固定 `test_case` 知识资产版本；选择结果写入 `HistoricalCaseSnapshot`。
- 历史用例输入独立于 `basisMode`，两种模式均可使用；历史用例不能替代评审基线或知识资产主依据。
- `TestAnalysisAgent` 对每个历史用例输出 `reusable`、`reusable_with_changes`、`obsolete`、`conflict` 或 `needs_confirmation`。用户不需要逐条确认全部结果：`reusable` 可默认进入批量复用候选，`reusable_with_changes` 可批量确认修改方向，`obsolete` 默认排除；只有 `conflict`、`needs_confirmation` 或用户主动改判时必须逐条处理。
- 可复用历史用例必须先映射到 `TestPointTreeDraft` 节点；无法映射时不得绕过树直接进入当前用例集。用户认为其代表遗漏场景时，必须先新增/修改树节点并批准。
- 树批准后，“复用”从一个结构化历史用例复制语义字段，在当前测试设计中生成新的服务端 `caseId` 和 revision 0，并保存 `reuseMode=unchanged`；不得直接引用历史用例作为可编辑当前用例。
- 树批准后，“复制并修改”或“参考并生成草稿”创建当前用例和 `reuseMode=modified`，必须保存来源版本、来源用例/定位、源 Hash、字段级 Diff 和修改摘要；知识资产文本不得标记为 `unchanged`。
- 用户后续在线修改原样复用用例时，系统自动将其复用方式转为 `modified` 并补充 Diff；原历史 `TestCaseSetVersion`、资产版本和原用例保持不可变。
- 历史来源更新、被归档或产生新发布版本时，仅提示当前用例来源可能过期；不得自动切换来源、同步字段或撤销已完成审核。
- 同一 `test_case assetVersionId` 不得同时作为知识库主依据和历史用例输入；需要复用沿革时应通过历史用例入口选择，服务端拒绝重复角色。

#### FR-610：测试点树、用例在线编辑与审核

- 树编辑 API 接受目标树 revision、结构化节点操作和说明；完成父子/循环/依据/历史映射校验后，原子生成 `TestPointTreeRevision` 和结构 Diff。
- 树批准使用追加式 `GateDecision` 并绑定明确 revision；新树 revision 自动使旧批准、候选用例、数据需求和覆盖审计失效，但不得删除旧产物。
- AI 综合结果和用户确认的历史复用结果通过服务端校验后，为每条候选创建 revision 0 和可编辑 `TestCaseDraft`；revision 0 不可修改，并通过 `origin` 区分 AI 生成、历史复用或人工创建。
- 编辑 API 接受结构化字段、期望 revision 和操作说明，完成 Schema/引用/依赖校验后原子生成新 `TestCaseRevision`。
- 新建、删除用例或生成新 `TestCaseRevision` 时，服务端同时使绑定旧用例 revision 集合 Hash 的覆盖审计失效；测试数据需求集合变化遵循相同规则。
- 页面支持在线结构化编辑、保存状态、修订历史和字段级 Diff，不以整段 Markdown 编辑代替用例字段。
- 单条或批量审核均使用追加式 `TestCaseReviewAction` 和乐观锁；审核决定绑定明确 revision。
- 要求修订不直接重新调用任意 Agent；用户可在线修改形成新 revision，或选择明确的工作流重跑操作。
- 新 revision 自动使旧审核通过失效，防止“审核后内容被修改但仍显示通过”。

#### FR-611：机器可读发布与执行交接

- 发布前服务端按 `test-case-set/v1` 全量校验当前依据/召回快照、已批准树版本、当前批准用例 revision、测试数据需求、覆盖审计 Hash、非空 UI/API 执行方式联合、各方式步骤/期望/检查点/就绪状态、依赖、设计依据和历史沿革；当前批准/全部方式 ready 用例的规范 `approvedCaseRevisionSetSha256` 必须与 `CoverageAuditResult.auditedCaseRevisionSetSha256` 完全相等，当前数据需求 Hash 也必须与审计输入相等。
- 发布时固定依据/召回快照、测试点树版本、批准用例、测试数据需求、`CoverageAuditResult`、覆盖/设计依据/历史复用关系、审核记录和人工修订，生成定位为本次新功能集的不可变 `TestCaseSetVersion`；成员统计必须区分新增、修改和原样复用。
- 受影响既有回归用例保存为独立 `ImpactedRegressionReference`，不得复制到当前 `TestCaseSetVersion`。冒烟候选只允许引用当前功能集成员，保存候选理由、预计耗时、稳定性/依赖判断和人工确认状态。
- `TestCaseSetVersion` 提供规范化 JSON 读取/导出接口；下一阶段按固定版本和 caseId 读取，不访问草稿或 latest。
- 同一内容 Hash 重复发布应幂等；任一用例内容变化必须重新审核并创建新的用例集版本。
- 功能集发布且候选确认后，服务端可按选定策略生成不可变 `TestExecutionHandoff`：固定当前冒烟/回归套件版本、冒烟组合成员、本次功能集、影响回归引用、顺序、去重结果和条件。相同输入与策略重复生成应幂等。
- 交接生成不得修改既有 `TestSuiteVersion`，不得创建 `TestPlanVersion`、执行任务或结果。冒烟候选晋级新基线必须由后续执行阶段基于真实结果和人工决定完成。
- 发布不得修改 AI 原始运行结果，不得自动关闭上游 Finding，也不得生成或执行测试脚本。

#### FR-612：报告与知识资产发布

- 支持导出指定 `TestCaseSetVersion` 的 JSON、Markdown 与固定模板 Excel；三者必须携带相同版本、caseId、树/数据/审计版本摘要和内容 Hash。
- Markdown 报告包含 `basisMode`、主依据/召回/历史输入、五阶段、测试点树、测试用例、测试数据需求、模式化覆盖审计、风险、待确认项、设计依据类型、固定来源、历史复用/变更摘要、修订和审核状态。
- Excel 以用例为主表，至少包含用例字段、测试点引用、数据需求引用、来源摘要、审核/就绪状态；复杂树、数据约束和审计详情使用独立工作表，不用扁平化文本取代规范 JSON。
- 报告排除模型隐藏思维、自由对话、候选原始响应、明文凭据和未脱敏日志。
- 人工发布后，系统通过 Phase 1 受控流程创建或更新 `test_case` 知识资产，逻辑路径默认为 `版本文档/{项目版本名}/测试设计/`；该资产是 `TestCaseSetVersion` 的 Markdown 展示投影。
- 入库任务失败不回滚已发布的 `TestCaseSetVersion`；页面显示失败并允许按同一内容 Hash 幂等重试。

#### FR-613：模型、工具与安全边界

- 四个 Agent 分别配置和发布，不允许用修改 Prompt 的方式让一个万能 Agent 兼任全部角色。
- 本期默认只允许固定依据读取、受控知识检索、树/用例/数据/审计读取和各阶段结构化提交工具。
- 知识检索工具必须校验固定索引/资产 allowlist、Embedding/检索配置和结果大小；重试复用已冻结召回结果，不访问 active/latest。
- 禁止 Shell、宿主文件系统、浏览器、任意 HTTP、代码执行、压测、安全扫描和外部写操作。
- Tool Runtime 必须校验工具/版本、参数 Schema、固定输入范围、权限、超时、取消、结果大小和脱敏。
- 页面、API、报告和普通日志不得返回 API Key、Authorization、签名、测试凭据或秘密环境变量。

### 8.2 一致性规则

1. 测试设计、工作流、任务、当前用例、覆盖和当前产物版本必须属于同一 `projectVersionId`；评审基线还必须属于该项目版本。项目级知识资产可被当前版本显式选择，历史用例可来自同一项目其他版本，但都只能通过冻结快照只读引用。
2. `basisMode` 与输入必须满足严格判别联合；评审模式的技术方案基线必须引用所选需求基线，知识库模式不得保存这两个运行 ID。模式切换必须新建 `TestDesign`。
3. 知识库模式的所选固定正文必须全部出现在 `InputDeliveryManifest`；投递不完整、资产 Hash 变化、无有效 `KnowledgeBasisItem` 或关键冲突未解决时不得冻结分析检查点。
4. `knowledgeAugmentation` 必须满足自身严格判别联合；每次运行都保存 `KnowledgeRetrievalSnapshot`。`disabled` 保存规范空快照，其他模式只在固定语料/索引中执行；重试、恢复和下游不得重新检索 active/latest。召回为空可继续，召回越界或 Hash 不一致必须失败。
5. 运行创建后，模式、输入、召回语料/配置、Hash、工作流拓扑、Agent、Prompt、模型、工具、权限和执行限制快照不可原地修改。
6. 下游任务只能读取阶段匹配、依赖节点已校验且依据/召回/树 Hash 一致的固定交接产物。
7. `TestCaseSynthesisAgent` 启动前必须存在已批准 `TestPointTreeVersion`；新树 revision 使旧批准和全部下游产物过期，不得静默重绑。
8. 成功运行必须拥有已批准范围和树门禁、四个 Agent 的合法终态、完整五阶段交接链、合法数据需求、Hash 一致且无 blocker 的 `CoverageAuditResult` 和原子保存的综合结果。
9. 模型提交的 ID、资产/Chunk、固定定位、树 revision、覆盖统计和发布状态不直接采信。
10. 取消、失租约、超时或达到执行限制后的迟到结果不能进入交接产物或正式结果。
11. 树/用例在线修改、审核、历史复用和修订只追加；初始 revision、AI 原始候选、上游引用、历史 `TestCaseSetVersion` 和历史资产版本不可覆盖。
12. 用例成员/内容 revision 或数据需求集合变化后，绑定旧 Hash 的覆盖审计必须失效；发布时当前批准/ready 用例的 `approvedCaseRevisionSetSha256`、当前数据需求 Hash 必须与有效审计输入完全一致。
13. 查询、筛选、统计、导出和发布必须校验显式项目版本、`basisMode`、五阶段版本/Hash 和运行归属，不默认到最新。
14. 已发布测试资产固定发布时的树、用例 revision、数据需求、审计、模式化依据引用、历史沿革与推导说明；上游、知识资产或历史来源更新只产生过期提示。
15. 当前用例使用新的服务端 `caseId`；来源 caseId/定位只能出现在复用关系中，删除当前草稿、重新设计或发布新版本均不得级联修改历史来源。
16. `HistoricalCaseSnapshot` 和知识依据/召回快照保存运行所需的独立固定内容；源版本归档、不可访问或按规则删除后，已冻结运行和已发布当前用例仍可读取来源摘要和比较内容，且不得回退检索相似文本。
17. 后续执行只能引用不可变 `TestCaseSetVersion` 中的批准用例、该用例内已声明且 ready 的明确 `executionMethods[]` 及对应数据需求；草稿、未通过审核、方式非 ready、过期审计或 Schema 不兼容内容不得进入执行输入。
18. `ProjectTestCaseCatalog` 只聚合已发布可读成员；同一固定用例出现在多个集合时不得生成内容副本，集合统计按成员引用去重或明确标注重复口径。
19. `TestSuiteVersion` 成员和内容 Hash 永不原地变化；页面和交接必须引用明确版本，禁止把 `latest` 解析结果保存为正式输入。
20. 当前 `TestCaseSetVersion` 只包含本次新增、修改或复用用例；影响回归和全量回归通过固定引用参与交接，不得改变当前功能集成员和覆盖审计分母。
21. 冒烟组合快照必须由基础 `smoke TestSuiteVersion` 与已确认候选确定性解析、去重并计算 Hash；候选撤回或任一输入版本变化时，原交接保持不可变，新内容创建新交接。
22. 第四期不得根据候选或交接自动发布新冒烟基线；后续阶段没有固定执行结果、稳定性证据和人工批准时，不得将候选声明为正式冒烟成员。

## 9. 非功能要求

### NFR-401：性能与容量

- 创建运行的同步 API 只完成校验、快照和入队，不等待模型执行。
- 列表、详情、覆盖矩阵和筛选使用服务端分页/聚合；不得要求浏览器一次加载全部用例和执行事件。
- 个人 Demo 验收集至少支持 200 个需求点、100 个方案要点或 500 个知识基线项、2,000 个测试点树节点、1,000 条候选用例、2,000 条历史用例、1,000 条数据需求和四个 Agent 节点，页面筛选和切换不出现不可操作的长时间阻塞。
- 模型耗时、排队耗时、每节点用量和总耗时分开记录；性能阈值在实施技术文档中结合基准环境定量化。

### NFR-402：稳定性与恢复

- 工作流和节点状态必须持久化；API、Worker 或浏览器重启后可恢复查看和继续调度。
- 测试点树草稿/revision/批准版本、数据需求和覆盖审计结果必须持久化；刷新或进程重启不能丢失人工树修改或错误恢复到旧批准版本。
- 节点领取使用租约、心跳、运行令牌和 fencing；相同任务重领不得重复发布交接产物。
- 相同幂等键和快照 Hash 的重复请求不产生多个逻辑运行。
- 单个并行专项失败不得删除其他已冻结专项产物；恢复操作遵循 4.3 的明确语义。
- 取消在可控时间内传播到尚未开始或正在运行的模型/工具调用，并阻止新下游节点启动。

### NFR-403：兼容性与可访问性

- Web 端首期支持项目确认的 Edge 与 Chrome 基线；具体主版本和分辨率矩阵在实施前固定，不以“最新”作为可复现验收条件。
- API 与交接 Schema 必须版本化；新增可选字段不破坏旧历史读取，不兼容变更使用新版本。旧 `TestCaseSetVersion` 只有在兼容适配器验证通过后才可选为复用来源。
- 历史 Phase 2/3 运行缺少第四期新增字段时仍可只读选择或明确提示不满足前置条件，不能静默补造数据。
- 中文文件名、中文路径、UTF-8、Asia/Shanghai 时区显示和固定 UTC 存储必须通过专项验收。
- 核心操作可通过键盘访问，状态不只依靠颜色表达。
- 测试点树的新增、移动、层级调整、展开/折叠和状态查看必须提供键盘等价操作及可理解的焦点/层级语义。

### NFR-404：安全与隐私

- 本期全部 Agent 为只读设计权限；代码执行和外部写能力在服务端硬拒绝。
- 文档、模型、Skill、MCP 和检索内容均视为不可信输入，不能改变工作流拓扑、权限、路由或发布门禁。
- 知识库中的 Prompt 指令、链接和代码块只作为被分析内容；检索和补读必须受依据快照的资产/Chunk allowlist 约束，不能访问未选择资料。
- 跨项目版本访问、伪造输入引用、提示词注入、SSRF、路径穿越和敏感日志必须有自动化安全测试。
- 运行记录采用公开执行事件，只保留用户可见文本、工具事实、状态、ID 和脱敏错误，不保存隐藏思维或秘密。

### NFR-405：可观测性与质量

- 每次运行可按 `workflowRunId -> taskRunId -> executionId -> model/tool call` 追踪。
- 至少记录 `basisMode`、五阶段/门禁、固定输入/召回规模和投递方式、队列、节点耗时、重试、降级、Token、工具调用、知识基线项/树节点/用例/数据需求数量、去重数量、历史复用/修改/废弃数量、审计缺口、模式化覆盖和阻塞统计。
- 健康检查必须区分 API、Worker、数据库、模型和工作流积压，不能用 API 存活代表完整可用。
- 发布前质量门禁至少保证 Schema 合法、`basisMode` 与依据类型匹配、依据/召回/树/数据/审计 Hash 一致、`approvedCaseRevisionSetSha256 = auditedCaseRevisionSetSha256`、模式对应覆盖状态完整、审核 revision 一致、执行就绪且发布阻塞项为零。

## 10. 验收标准

### AC-401：两种主依据模式与固定知识召回

**操作**：分别以 `review_baseline` 和 `knowledge_assets` 创建测试设计；在两种模式下分别使用 `disabled`、`selected_assets` 和 `fixed_index` 补充召回。再提交主依据模式混合字段，以及增强模式空资产、重复资产、`disabled` 携带资源字段、`selected_assets` 携带索引、`fixed_index` 携带资产列表、跨项目/非 `ready`/`latest` 资产、活动索引别名和无关联双评审组合，并尝试在原 `TestDesign` 切换主依据模式。

**预期**：两种合法主依据均创建真实 `workflowRunId`；`disabled` 形成带规范 Hash 的空 `KnowledgeRetrievalSnapshot`，另外两种模式将召回范围、索引/资产版本、检索配置、查询与结果冻结。历史用例输入独立可选。服务端拒绝所有错误分支字段、非法组合和原地切换模式；资产、评审运行或活动索引后续变化不修改当前运行，重试不回读 `active/latest`。

### AC-402：五阶段产物链与四 Agent 工作流

**操作**：分别用评审基线和知识资产样例运行完整设计流程，观察任务图、人工门禁和服务端阶段。

**预期**：页面依次呈现“依据解构与知识召回、测试点智能发散、测试用例具象化、测试数据资产定义、覆盖反向审计”五阶段；工作流仍只包含测试分析、功能设计、非功能设计、用例综合四个 Agent。功能/非功能设计并行执行，测试范围确认和测试点树批准显示为人工门禁，树归并与覆盖审计显示为服务端确定性阶段，不伪装成额外 Agent。

### AC-403：依据解构与受控召回

**操作**：输入 PRD、API 契约或固定知识资产，样例包含实体、术语、业务规则、状态约束、接口约束、历史缺陷、冲突资料和行业实践。

**预期**：`TestAnalysisAgent` 形成结构化实体、角色、动作、规则、约束、状态、接口、风险和历史适用性；召回只访问固定 allowlist，并将结果标记为规范依据、历史缺陷、领域实践或上下文。召回内容不会自动升级为已确认需求；无法定位、存在冲突或缺少判定标准时形成待确认项，固定来源可从页面打开。

### AC-404：测试点发散与测试点树门禁

**操作**：让功能和非功能 Agent 使用等价类、边界值、判定表、状态迁移、场景法、错误推测、因果图或 Pairwise 产生正常、异常和风险测试点；随后在线新增、移动、拆分、合并、删除节点并标记不适用。

**预期**：服务端保留专项来源和重复关系后归并为 `TestPointTreeDraft`；每次编辑产生 revision、ETag 和字段/结构 Diff。树未批准时用例综合保持阻塞；批准后形成不可变 `TestPointTreeVersion`。再次编辑已批准树会使批准和下游候选失效，并明确要求“重新具象化用例”，旧树及旧候选不被覆盖。

### AC-405：用例具象化与 UI/API 组合执行方式

**操作**：批准包含页面交互、HTTP API、异步任务和数据副作用的测试点树后生成用例；创建一条同时选择 UI 和 API 的登录用例，分别编辑两套步骤/检查点，再按“包含 UI”和“包含 API”筛选并检查测试点到用例的映射。

**预期**：`TestCaseSynthesisAgent` 只读取已批准树；每条当前用例至少关联合法 `testPointRefs`。测试点允许零、一或多条用例，用例也可合并多个测试点，但零映射和合并必须给出可审计理由。`executionMethods[]` 可为 `[ui]`、`[api]` 或 `[ui, api]` 且不得为空/重复；组合用例共享目标、前置、数据和清理，同时保存 UI 的起始页面/语义操作/页面期望与 API 的方法/路径/参数/响应，步骤和检查点互不覆盖。组合用例同时出现在两个方式筛选中，套件/交接引用明确要执行的方式。

### AC-406：历史测试用例映射、复用与修改

**操作**：选择上一项目版本的结构化 UI/API 用例和固定 `test_case` 文档，让 AI 判断 `reusable`、`reusable_with_changes`、`obsolete`、`conflict` 或 `needs_confirmation`，再执行复用、复制修改和参考生成。

**预期**：历史用例必须先映射到测试点树；无法映射的历史用例不能直接进入当前用例集，代表缺失场景时应先补树节点。当前用例获得新 `caseId`，原样复用记录 `unchanged`，修改复用记录 `modified` 并保存来源、源 Hash、字段 Diff 和修改摘要；旧版本保持不可变，废弃/冲突项不自动进入当前用例集。

### AC-407：非功能专项不编造指标

**操作**：样例一提供明确性能阈值、恢复目标和兼容矩阵；样例二只写“高性能、稳定、兼容主流浏览器”。

**预期**：样例一生成带固定来源的负载、指标、恢复与兼容测试点/用例；样例二生成待确认项并阻塞相应用例，不编造并发数、响应时间、恢复时长或浏览器版本。

### AC-408：测试数据需求资产

**操作**：使用“已过期且有未结清账单的 VIP 账户”、批量边界、权限角色和故障状态等测试点生成用例与数据需求。

**预期**：系统生成结构化 `TestDataRequirementSet`，包含关联测试点/用例、实体与特征标签、约束关系、数量、初始状态、准备提示、敏感与隔离等级、复用、重置、清理及就绪状态；不创建真实数据，不保存明文凭据或生产个人数据。未满足的强制数据条件使相关用例为 `blocked` 或 `needs_confirmation`，不得标记为 `ready`。

### AC-409：安全设计、召回和工具边界

**操作**：输入包含跨版本访问、提示词注入、SSRF、凭据和高风险工具场景，并尝试让 Agent 扩大召回范围、调用代码执行或外部写工具。

**预期**：安全专项形成对应设计；召回不能越过固定资产/Chunk allowlist，越权工具从未实际执行；外部内容不能改变 DAG、权限或发布门禁；记录和报告不包含秘密或隐藏思维。

### AC-410：覆盖反向审计与服务端统计

**操作**：构造未覆盖依据项、无用例测试点、无树节点/无依据用例、缺失 oracle、缺失数据需求、重复候选及过期 Hash，并让 Agent 同时提交自报覆盖数字。

**预期**：服务端生成绑定依据、召回、树、数据 Hash 和规范 `auditedCaseRevisionSetSha256` 的 `CoverageAuditResult`，准确列出覆盖缺口、孤立关系、缺失项、重复项和发布 blocker；按“依据项 -> 测试点 -> 用例”双向展示追溯矩阵。正式统计只从持久化关系计算，不采用文档/Chunk 数或 Agent 自报数量；Agent 审查建议仅作语义补充。

### AC-411：失败、取消与分层恢复

**操作**：分别触发分析失败、一个测试点设计节点失败、用例综合失败、覆盖审计阻断和运行中取消，再执行“重新执行失败设计节点”“修订测试点树”“重新具象化用例”和“全部重跑”。

**预期**：每个操作只重跑声明范围并创建新执行或新运行；成功检查点经 Hash 校验后复用，树修订保留旧版本并使对应下游候选过期；原运行不覆盖；取消停止后续节点，迟到结果不发布；失败状态和脱敏原因真实可见。

### AC-412：在线审核、导出与发布

**操作**：完成覆盖审计后在线修改一条 UI 用例，在另一会话制造 revision 冲突；逐条/批量审核但不重新审计并尝试发布，再重新审计后导出 JSON、Markdown 和 Excel。发布 `test_case` 知识资产投影时模拟一次入库失败并按相同内容 Hash 重试。

**预期**：树与用例编辑均使用 revision/ETag 和 Diff 防止并发覆盖；审核决定绑定具体 revision，新修改使旧批准和旧 `CoverageAuditResult` 失效。即使用例已重新审核，当前 `approvedCaseRevisionSetSha256` 未与有效审计完全相等时仍不得发布；存在 blocker、未批准树、未通过审核或未就绪用例时同样阻止。合法发布形成不可变 `TestCaseSetVersion`，三种导出的版本、caseId 和内容 Hash 一致，Excel 分页呈现测试点、用例、数据需求和覆盖审计；知识资产入库失败不回滚用例集，按相同 Hash 重试只生成一个逻辑投影版本。

### AC-413：机器可读用例集与下一阶段 AI 交接

**操作**：将包含 UI、API、参数化数据、逐步期望、验证检查点、用例依赖和历史沿革的 28 条已审核用例发布为本次新功能集，其中标记 3 条冒烟候选并引用 12 条受影响回归用例；选择既有冒烟 v6（18 条）和全量回归固定版本，分别生成标准、快速、直接全量交接，并用测试执行输入校验器加载指定版本。

**预期**：规范化 JSON 通过 `test-case-set/v1`/`test-case/v1` 校验，项目用例库可查到固定来源、组合执行方式和集合归属；本次功能集仅含 18 条新增、4 条修改和 6 条原样复用用例，12 条影响回归不被复制为成员。冒烟组合快照固定为“v6 的 18 条 + 3 条候选 = 去重后 21 条”，v6 仍为 18 条且不可编辑；三种交接均固定精确版本、成员、每个成员的执行方式、顺序、条件和 Hash。下一阶段 AI 无需解析 Markdown、回读 `latest` 或重新推断来源/入口；第四期未创建 `TestPlanVersion`、执行记录或冒烟 v7。

### AC-414：历史隔离与兼容

**操作**：刷新固定路由、切换项目版本、打开两种模式的历史运行；上传新资产版本并切换活动索引，再使用中文路径、UTF-8 内容和旧上游运行验证。

**预期**：页面始终绑定 `projectVersionId + testDesignId + workflowRunId` 并显示原 `basisMode`，不混入其他版本、活动索引或最新结果；历史树、用例、数据需求、审计结果和固定来源可读；缺失模式必需数据时明确阻止新运行，中文与时间显示正确。

### AC-415：本期范围边界

**操作**：检查页面、Agent 配置、默认工具、API 和验收流程。

**预期**：本期只完成多 Agent 测试设计、测试数据需求定义、覆盖审计、人工发布、项目测试资产只读聚合、冒烟候选确认和执行交接；不创建真实测试数据、`TestPlanVersion` 或测试任务，不生成或执行脚本，不访问 Git，不执行浏览器、接口、压测、故障注入或安全扫描，不发布新冒烟基线，不创建缺陷，不宣称测试执行已交付。

15. 冒烟/全量回归/功能域套件的维护责任人、版本命名、成员去重和归档规则；
16. “受影响回归”的选择边界、影响分析责任人，以及标准/快速策略是否允许跳过某些功能域；
17. 后续执行阶段将候选晋级新冒烟基线所需的连续通过次数、失败率/波动率、观察周期和人工批准角色。

### 11.3 后续衔接

脚本编写与测试执行属于后续独立阶段。该阶段读取固定 `TestExecutionHandoff`，创建绑定构建、环境和成员快照的正式 `TestPlanVersion`，按所选策略执行冒烟组合、本次新功能、影响回归和全量回归，并保存结果。只有组合快照经过真实执行、稳定性规则验证和人工批准后，后续阶段才能基于原冒烟版本发布新 `TestSuiteVersion`；原版本永久可复现。本文不定义该阶段的 Agent、调度、执行接口或结果验收，不能把第四期候选、交接或页面预览解释为脚本编写、测试执行或冒烟基线升级已经交付。
