## 2. 项目背景

项目资料通常分散在需求文档、技术方案、接口说明、测试用例、测试报告和缺陷复盘中，缺少统一的版本、来源、同步状态和检索入口。后续 AI 需求分析与技术方案分析若没有稳定、可追溯的资料基础，就无法可靠引用项目事实。

SmartHub 采用“先知识库基础、后智能分析”的建设顺序：先将独立维护的项目资料沉淀为可版本化、可检索的知识资产，再以固定资产版本和证据定位作为后续 AI 能力的输入。

## 3. 产品目标

### 3.1 总体目标

建设一个以项目知识资产为基础的分析平台，使后续能力能够在明确资料范围内输出带来源引用的结论。

```text
项目资料
  ↓
项目知识库：接入、版本、同步、检索、定位
  ↓
Phase 2：运行固定双阶段需求评审工作流
  ↓
Phase 3：运行技术方案提取与评审双阶段工作流
  ↓
Phase 4：服务端工作流编排多个测试设计 Agent 完成用例设计与人工发布
  ↓
后续：Git/代码、诊断、自愈、治理与企业集成
```

### 3.2 分阶段目标

- **Phase 1**：建立可靠、可恢复、可追溯的项目知识库和知识库配置能力。
- **Phase 2**：在 Pi Agent Framework 上运行固定的 `RequirementAnalysisWorkflow`，依次执行 `RequirementPointExtractionAgent` 与 `RequirementReviewAgent`，基于固定知识资产和证据完成需求分析、结构化 Finding 与人工处置闭环。
- **Phase 3**：在同一框架上依次运行 `TechnicalSolutionExtractionAgent` 与 `TechnicalSolutionReviewAgent`，基于已确认需求、固定方案正文和冻结方案要点完成技术方案分析与评审。
- **Phase 4**：通过服务端显式工作流编排测试分析、功能设计、非功能设计和用例综合四个 Agent；主测试依据可选择成功需求/技术方案评审，或直接选择固定知识资产版本而不依赖前两阶段，并可在固定范围内补充知识召回。两种模式沿“依据解构与知识召回 -> 测试点智能发散 -> 测试用例具象化 -> 测试数据资产定义 -> 覆盖反向审计”产物链完成测试点树编辑、历史用例复用/修改、在线审核和本次新功能用例集发布；提供项目用例库/用例集聚合、影响回归固定引用、冒烟候选和执行交接，但不包含真实造数、脚本编写、测试计划、测试执行或冒烟基线发布。
- **后续阶段**：创建绑定构建、环境和固定成员的测试计划，按冒烟、新功能、影响回归和全量回归策略执行；积累稳定性证据并由人工决定是否发布新冒烟基线，再逐步接入 Git/代码影响、失败诊断、自愈、权限治理和企业集成。

### 3.3 产品原则

- **资料优先**：先保证资料来源、版本和检索定位正确，再建设 AI 分析能力。
- **版本优先**：检索、分析和引用必须指向确定的资产版本，不能以“当前最新内容”代替历史事实。
- **项目版本隔离**：项目知识库与系统配置是项目级共享资源；需求评审、技术方案、测试执行和报告等项目空间数据必须归属明确的项目版本。未创建或未选择项目版本时，不得进入需求分析工作台或启动分析。
- **单平台单项目**：当前产品形态固定为一个 SmartHub 平台实例服务一个项目，不提供项目创建、项目选择和跨项目切换。平台初始化时自动建立当前项目及其默认知识库，用户只管理该项目下的项目版本。
- **独立维护优先**：项目内独立维护、有来源和版本的资料是知识库资产；临时中间结果不是自动入库资料。
- **增量与可恢复**：资料更新只处理变化内容；失败不能破坏上一个可检索版本。
- **逐步演进**：第一期不以 Git、权限、测试执行或复杂多格式解析作为交付依赖。
- **确定性外层、Agent 内层**：业务状态、快照、取消、路由、校验、正式落库和高风险审批由 SmartHub 控制；Agent 只在单次运行内调用已授权工具。
- **完整上下文优先**：需求提取首先保证 Agent 看到完整固定正文；正常规模输入直接进入首轮上下文，超长输入由服务端确定性分批并最终归并，函数调用不作为正文主传输通道。
- **最小权限与证据优先**：Prompt、模型、工具、MCP、联网和外部操作必须版本化并按风险授权；外部内容不能绕过固定证据与人工确认规则。
- **统一 Agent 框架、独立业务 Agent**：Phase 2～Phase 4 统一使用 Pi Agent Framework；各阶段创建职责单一、独立版本化的业务 Agent，不以一个万能 Agent 覆盖全部流程。
- **固定流水线、按阶段演进**：Phase 2 与 Phase 3 均采用职责隔离的固定双阶段 Agent 流水线；Phase 4 再引入明确角色、任务依赖和产物交接的通用多 Agent 协作。

## 4. 统一术语与资料边界

### 4.1 核心对象

```text
平台实例（单项目）
  └─ 当前项目（系统初始化，不由用户切换）
       ├─ 项目知识库（项目级共享）
       │    └─ 知识资产
       │         └─ 资产版本
       │              └─ Chunk / 索引版本
       └─ 项目版本（项目空间隔离边界）
            └─ 项目版本需求绑定
                 └─ 引用固定需求资产版本
```

| 对象 | 定义 |
|---|---|
| 项目 | 平台实例内唯一的资料、配置和智能分析归属边界，由系统初始化；当前版本不提供项目管理和切换能力。 |
| 项目版本 | 项目空间内需求评审及后续设计、执行、报告数据的强制隔离边界，状态为 `open`、`locked` 或 `archived`。只有 `open` 版本允许新增或替换需求绑定并发起新分析。 |
| 项目知识库 | 当前唯一项目下统一管理、同步和检索资料的集合。平台初始化时创建一个默认知识库。 |
| 知识资产 | 一份独立维护的项目资料逻辑实体，例如“支付模块重构需求”或“订单 API 规范”。 |
| 资产版本 | 知识资产某次不可变内容快照，记录来源、内容 Hash、时间和同步状态。 |
| Chunk | 资产版本经解析后用于检索与定位的结构化片段。 |
| 索引版本 | 同一知识库在固定解析、切分和 Embedding 配置下的可检索集合版本。 |
| 项目版本需求绑定 | 将项目版本与一个确定的需求 `assetVersionId` 关联的引用关系。它不复制知识资产内容，用于决定该项目版本可分析哪些需求版本。 |
| 需求评审运行 | 对固定需求资产、索引、检索、模型、Agent、Prompt、工具与权限快照执行的一次可取消、可追溯运行。 |
| Pi Agent Framework | SmartHub Phase 2～Phase 4 共用的 Agent 框架，提供模型交互、消息状态、工具循环、事件和取消传播等基础能力。 |
| 业务 Agent | 基于 Pi Agent Framework 创建的版本化业务执行单元，具有稳定 ID、类型、Prompt、模型配置、工具、权限和执行限制；不同阶段使用独立业务 Agent。 |
| `RequirementAnalysisWorkflow` | Phase 2 固定业务流程，按顺序执行需求点提取和需求评审两个独立 Agent，不支持动态多 Agent 编排。 |
| `RequirementPointExtractionAgent` | Phase 2 提取阶段 Agent，只提交需求点、固定证据和覆盖范围。 |
| `RequirementReviewAgent` | Phase 2 评审阶段 Agent，提交总体摘要和逐条对应需求点的分析；服务端生成 Finding ID。其只读问答模式用于追问。 |
| `TechnicalSolutionExtractionAgent` | Phase 3 提取 Agent，负责从固定方案正文提取并固化带 Evidence 的原子方案要点。 |
| `TechnicalSolutionReviewAgent` | Phase 3 评审 Agent，负责引用冻结需求点与方案要点提交覆盖、Finding、风险和问题。 |
| 多 Agent 工作流 | Phase 4 用于协调多个测试 Agent 的显式任务图，固定参与 Agent、输入、依赖、产物、审批和汇总规则，不依赖自由对话决定流程。 |
| 受控工具 / MCP 适配器 | 具有输入输出 Schema、权限、风险、超时、幂等和数据策略的确定性能力；MCP Tool 必须转换为统一工具描述后才能使用。 |
| AI 派生产物 | 后续 AI 产生的分析 findings、对话消息、方案草稿和任务中间结果。它们关联输入资产版本，但不会自动成为知识资产。 |

### 4.2 知识资产范围

以下独立维护的项目资料均属于项目知识库内容，并按资料类型、来源、版本和状态管理：

- 各版本需求文档、验收标准和业务规则；
- 技术方案、架构资料、接口文本/规范和数据字典；
- 测试规范、测试用例和测试报告；
- 缺陷复盘、问题解决方案和项目术语说明；
- 其他具有明确来源、维护责任和版本记录的项目说明资料。

第一期完整支持 UTF-8 Markdown 与纯文本接入。接口定义、测试用例和报告可先以 Markdown/纯文本形式维护；OpenAPI、Excel、PDF、Word 等专用格式解析器属于后续扩展，不影响统一资产模型。

### 4.3 统一边界

本产品不再以“分析工作区”和“正式知识库”区分两套资料库。资料是否进入知识库，取决于它是否已经被保存为**独立维护的项目资料版本**：

- 人工创建、导入或确认保存的需求、技术方案、API 说明、测试用例和报告，均为知识资产，可按通用同步流程进入检索。
- AI 分析结论、会话消息、临时草稿和任务中间结果不因产生而自动成为知识资产。
- 后续如将 AI 草稿人工保存为独立技术方案或报告版本，则该版本作为新的知识资产进入同步流程。
- 项目知识库、知识资产、模型来源和系统管理配置为项目级或系统级共享资源；需求评审及后续设计、执行、报告数据必须按 `projectVersionId` 隔离。
- 项目版本只通过绑定引用固定资产版本，不复制知识资产。知识资产产生新版本时，不得自动改变既有项目版本的绑定。
- 未创建或未选择项目版本时，需求分析入口只展示“新建项目版本”引导，不展示其他版本的需求、评审、运行、Finding 或问答数据。
- `projectId` 可作为服务端内部归属键保留，但由部署配置或系统初始化确定，不出现在普通用户的项目选择、创建流程中，也不由前端任意提交。

## 5. 产品阶段与范围

### 5.1 Phase 1：项目知识库构建与配置

**目标**：建立项目资料的接入、版本、增量同步、基础检索、配置和状态可观测能力，为后续分析提供可靠输入。

**本期范围**：

- 平台初始化唯一项目及其默认知识库，用户查看与配置当前项目知识库；本期不提供项目创建和项目切换；
- Markdown/纯文本资料通过网页/API 受控上传；未来 Wiki 等来源通过标准连接器接入；
- 统一知识资产类型、来源、逻辑路径、版本和状态管理；
- 内容校验、冲突策略、不可变资产版本和活动版本管理；
- 结构化切分、内容 Hash、增量 Embedding、持久化异步任务、失败重试和中断恢复；
- 知识库资料浏览、按状态/逻辑路径过滤、基础关键词/向量检索和固定版本原文定位；资料类型仅作为资产和检索证据元数据展示；
- 检索范围仅支持逻辑路径筛选；来源保留为资产和证据元数据，不作为筛选条件；
- Chunk、Embedding、检索参数和索引重建配置；
- 同步任务、错误、重试、索引版本和配置快照的可观测展示。

**本期明确不做**：

- AI 需求分析、AI 对话、原型图/HTML 原型解析；
- AI 技术方案生成或技术影响分析；
- Git、代码仓库、分支、Commit、Pull Request、静态分析和代码影响；
- 测试点/用例/脚本生成、Playwright、测试执行、CI/CD、日志诊断和自愈；
- 用户角色、细粒度权限、ACL、审批流、SSO 和审计治理；
- OpenAPI、Excel、PDF、Word 等专用格式解析器。

### 5.2 Phase 2：需求评审与大模型配置

**目标**：在 Phase 1 知识库稳定后，以 Pi Agent Framework 为统一框架交付固定的 `RequirementAnalysisWorkflow`。该流程将项目版本绑定的多份固定需求资产作为同一批输入：正常规模正文直接交给 `RequirementPointExtractionAgent` 全局理解，超长正文由服务端按结构确定性分批并最终归并；提取产物经服务端规范化 Evidence、生成覆盖证明并冻结后，再由 `RequirementReviewAgent` 生成可执行、可复核、可人工处置的评审结论。

**本期范围**：

- 创建、选择并切换项目版本；只有 `open` 项目版本允许绑定需求和发起新评审，`locked`、`archived` 版本只读；
- 将项目知识库中 `ready` 的固定需求资产版本绑定到当前项目版本；新项目版本可选择继承上一版本的有效需求绑定，但不继承评审、运行、Finding 和问答结果；
- 需求评审页支持上传 Markdown、纯文本和 ZIP 压缩包，复用 Phase 1 的校验、解析、索引流程，并在资产版本达到 `ready` 后自动绑定到当前项目版本；ZIP 中图片只作为附件保存，不参与本期正文解析；
- 从当前项目版本已绑定的全部固定需求资产版本创建联合评审，固定 `projectVersionId`、绑定集合、输入 Hash 集合、活动索引、检索范围和检索结果快照；
- 每个需求评审运行固定顺序启动 `RequirementPointExtractionAgent` 与 `RequirementReviewAgent` 两个独立执行实例：前者优先从首轮完整正文提取、去重和归并结构化需求点，只有超出模型安全预算时才接受确定性分批正文；后者仅基于冻结产物识别缺口、歧义、冲突、边界、验收风险和测试风险；
- 提取 Agent 每条需求点正常生成简洁 `title`，并提交 `description` 与 `sourceTexts` 原文线索；标题缺失时服务端兜底，模型不维护其他结构化槽位、归并字段、资产版本、Chunk、需求点/Evidence ID、引用或定位。服务端跨全部固定输入检索，保留最高分置信区间内全部 Evidence，对相同固定位置去重，并根据 `InputDeliveryManifest` 生成 coverage 和固定 locator；正常提取只使用结构化提交工具，完全无法建立 Evidence 时才开放定点补读；
- 评审 Agent 提交总体摘要和逐条需求点分析；每条分析只关联一个真实需求点。标题、类型、严重度、置信度、影响和建议由模型给出，服务端只生成 Finding ID、校验关联并对非关键展示字段容错，避免重复修正；
- 每个需求点至少关联一条固定证据；Finding 至少关联一个需求点，原文依据通过关联需求点的固定资产版本、Chunk、标题路径和原文位置间接追溯，不直接保存 Evidence 引用；缺失事实前提、歧义或风险须标记待确认、模型推测或外部参考；
- Finding 人工确认、驳回、解决、待跟进和补充评论，保留模型初始输出、历史运行和处置记录；
- 基于成功评审运行开展有固定上下文和证据引用的评审问答；
- 受控注册生成式模型来源、模型能力、模型配置版本、智能路由、重试、降级、健康检测和调用观测；
- Pi Agent Framework 分别负责两个阶段 Agent 的模型交互、消息状态、工具循环和取消传播；PostgreSQL Job/Worker 负责排队、租约、恢复、取消和最终业务状态；
- 固定 Pi Agent Framework/Runtime、两阶段 Agent 定义与执行、Prompt、工具集、MCP、网络策略、权限和执行限制版本，并记录模型与工具调用；
- 通过统一 Tool Runtime 受控使用内部检索、联网与 MCP 能力；工具按 `read`、`write-reversible`、`write-high-risk` 分级，写操作遵循幂等、补偿和人工确认策略；
- 对提示词注入、SSRF、越权工具调用、凭据泄露、迟到结果和无限 Agent 循环实施明确阻断与观测。

**本期产品非目标**：

- 技术方案生成、Git/代码分析、测试脚本生成、测试执行和完整组织权限治理；
- 面向普通用户的通用可视化 Prompt/Agent 编排、任意 Agent 发布、任意工具/MCP/联网端点注册；
- 动态多 Agent 协作、Agent 间自由委派、共享会话和任意工作流编排；第二期仅提供固定双阶段 `RequirementAnalysisWorkflow`；
- 浏览器录入任意外部密钥、Shell/代码执行环境，以及不受控外部写操作；
- AI 结果、问答或外部操作自动改写需求原文、正式知识资产、Finding 人工处置或活动索引。

上述产品非目标不影响第二期将 Pi Agent Framework 作为正式业务框架并运行固定的 `RequirementAnalysisWorkflow`，也不排除两个阶段 Agent 依赖受控 Prompt、Tool Runtime、联网、MCP 和外部操作执行器；所有依赖必须预注册、版本化、最小授权、可取消、可审计，并且不能绕过 SmartHub 业务状态和结果校验。

### 5.3 Phase 3：技术方案提取与评审 Agent

**目标**：在 Pi Agent Framework 上创建并启用固定双阶段流水线，先提取并冻结技术方案要点和 Evidence，再基于 Phase 2 已确认需求与冻结方案要点完成评审。

- `TechnicalSolutionExtractionAgent` 与 `TechnicalSolutionReviewAgent` 均使用独立稳定 ID、类型、Agent 定义、Prompt、工具集、权限和执行限制，不通过修改第二期 Agent 的 Prompt 来兼任；
- 每次评审依次启动两个独立会话，固定需求评审运行、技术方案资产版本、两套模型/Agent/Prompt/工具快照及提取检查点；
- 提取 Agent 提交方案要点与原文线索，服务端生成 ID 和 Evidence；评审 Agent 只引用冻结需求点与方案要点，服务端生成正式 Finding、引用、定位和覆盖统计；
- 复用 Pi Agent Framework、模型路由、Tool Runtime、MCP/联网治理、调用观测和人工确认基础能力；
- Phase 3 个人 Demo 只实现固定串行双阶段，不引入 Agent 自由委派、通用多 Agent 编排、Git、代码、Diff、部署或测试执行能力。

### 5.4 Phase 4：多 Agent 测试设计工作流

**目标**：由服务端 `TestDesignWorkflow` 编排四个职责独立的 Agent，以固定评审基线或固定知识资产为主依据，结合可选受控知识召回和历史用例，完成“依据 -> 测试点树 -> 测试用例 -> 测试数据需求 -> 覆盖审计 -> 新功能集与执行交接”的可追溯设计闭环。

第四期角色至少包括：

- `TestAnalysisAgent`：按 `basisMode` 解构固定需求/技术方案对象或完整知识资产输入，构造受控召回查询，并分析测试范围、风险、历史适用性与覆盖目标；
- `FunctionalTestDesignAgent`：使用等价类、边界值、判定表、状态迁移和场景法等方法形成正常、异常、边界、状态、权限和数据规则的测试点树候选；
- `NonFunctionalTestDesignAgent`：形成性能、稳定性、兼容性和安全测试点树候选，不编造缺失指标或支持矩阵；
- `TestCaseSynthesisAgent`：只读取人工批准的测试点树，将测试点具象化为可包含 UI、API 或二者组合执行方式的结构化用例，映射历史复用关系并定义测试数据需求；各方式拥有独立步骤/检查点，共享目标、前置、数据和清理。

测试依据必须明确为互斥的 `review_baseline` 或 `knowledge_assets`：前者固定同版本且引用链一致的成功需求/技术方案运行，后者显式固定一至多份 `ready` 知识资产版本、正文/Chunk、Hash、索引范围和投递清单，不要求 Phase 2/3 运行。两种模式都可通过 `disabled | selected_assets | fixed_index` 选择补充知识召回，但召回语料、索引与配置必须固定，禁止运行时读取 `latest`。

五阶段是内部产物链和页面流程，不是五个 Agent：`TestAnalysisAgent` 负责依据解构与受控召回，功能/非功能 Agent 并行发散测试点，服务端归并为可在线编辑和批准的 `TestPointTreeVersion`，综合 Agent 具象化用例并形成 `TestDataRequirementSet`，最后由服务端生成确定性 `CoverageAuditResult`。测试范围确认和测试点树批准是人工门禁；树归并与覆盖审计是服务端阶段。

多 Agent 工作流必须显式定义任务拓扑、参与 Agent 版本、输入输出 Schema、依赖、并发、超时、重试、审批、共享产物和汇总规则。Agent 间通过版本化产物和结构化交接记录协作，不允许依靠自由对话决定发布或高风险操作。第四期发布不可变本次功能 `TestCaseSetVersion`，通过项目级只读目录展示已发布用例及既有 `TestSuiteVersion`，保存冒烟候选、影响回归引用和标准/快速/直接全量 `TestExecutionHandoff`。既有套件不原地修改；第四期不创建 `TestPlanVersion`、不生成代码、不接入测试环境、不执行浏览器、接口、压测、故障注入或安全扫描，也不定义脚本编写、测试执行或结果分析 Agent。

### 5.5 Phase 5+：后续能力

以下通用产品能力后续单独规划。底层 Agent、Tool、联网或 MCP 适配器可以被前述阶段受控复用，但不代表对应通用产品能力已经交付：

- 测试计划、环境/构建绑定、冒烟/新功能/回归执行、结果证据和基于稳定性规则的冒烟套件版本升级；
- Git/代码影响分析、分支与变更集关联；
- 深度失败聚类、根因分析、质量报告、缺陷联动和自愈；
- 多知识库、用户/角色/ACL、组织级审批、审计、SSO 和企业治理；
- OpenAPI、Excel、PDF、Word、外部系统和更多资料来源适配；
- 通用 Prompt/Agent 可视化编排、Skill/Tool/MCP 市场、任意端点管理、多项目管理和跨项目自动化。

## 6. 跨阶段数据与证据约束

后续阶段必须复用 Phase 1 的资产模型，不得另建无法关联版本的资料容器；同时必须以项目版本作为项目空间业务数据的隔离边界。

- 检索结果至少返回 `projectId`、`knowledgeBaseId`、`indexVersionId`、`assetId`、`assetVersionId`、资料类型、来源、逻辑路径、标题路径、`chunkId` 和原文定位信息；页面必须按返回的 `assetVersionId` 打开证据原文；
- 需求评审、运行、Finding、问答及后续阶段产物必须保存 `projectVersionId`；需求评审还必须保存 `requirementBindingId`，服务端不得从“当前版本”或“最新版本”隐式推断作用域；
- 切换项目版本后只能读取该版本的绑定、评审、运行、Finding 和问答；跨版本比较必须由用户显式选择双方版本，不得在默认列表、统计或上下文中混合数据；
- AI 分析任务必须保存输入资产版本、检索范围、证据快照，以及 Pi Agent Framework/Runtime、按阶段记录的 Agent 定义与执行、模型、Prompt、工具集、MCP、网络、权限和执行限制版本；
- 多 Agent 工作流还必须保存 `workflowRunId`、任务拓扑、参与 Agent 与执行 ID、父子关系、依赖、交接产物版本、审批、汇总结果和终止原因；
- Agent 与工具事件是过程记录，不直接代表业务运行成功；只有服务端完成结构化 Schema、证据和一致性校验并原子保存结果后，运行才能成功；
- 联网、MCP 和外部内容均视为不可信数据，不能修改系统 Prompt、权限、路由、审批和终止策略；不能映射为固定项目证据时，只能作为外部参考或待确认信息；
- 模型调用、工具调用和外部操作确认必须关联运行并脱敏记录；取消、失租约或达到执行限制后的迟到结果不得进入正式结论；
- 资产版本更新后不覆盖历史引用；旧结论仍能按原快照查看，并可被标记为可能过期；
- 后续权限设计不得改变资产、版本、Chunk 和证据引用的稳定标识；
- Wiki、Git 与外部文档系统未来通过 Source Connector 接入，不得破坏 Phase 1 的上传、候选索引和固定版本证据语义。

## 7. 阶段核心页面

### 7.1 项目知识库页

- 查看项目默认知识库、资料数量、资料类型分布和索引状态；
- 按同步状态和逻辑路径浏览知识资产；资料类型和来源仅作为资产元数据展示；
- 查看资产版本、当前活动版本、最近成功同步时间和最近错误；
- 上传 Markdown/纯文本资料，并查看异步同步结果；
- 执行基础检索并定位至固定资产版本、标题路径和原文位置；
- 查看或重试失败同步任务。

### 7.2 知识库配置页

- 配置默认资料类型、逻辑路径规则和上传冲突策略；
- 配置 Markdown/纯文本解析、Chunk 大小、重叠和预处理版本；
- 选择部署端已注册的 Embedding 来源与模型，配置维度和基础检索参数；远程端点和密钥不进入页面或知识库配置；
- 显示草稿/已保存状态及配置变更影响；
- 对影响索引兼容性的配置发起受控重建，并展示旧索引持续可用、进度、失败或取消状态。

### 7.3 需求评审页

- 未创建或未选择项目版本时展示空状态和“新建项目版本”主操作，禁止加载需求分析工作台；
- 只展示当前项目版本绑定的需求，明确区分项目发布版本（如 `V3.6`）与需求资产版本（如 `V2.3`）；
- 支持从知识库加入既有 `ready` 需求版本，或上传 Markdown、纯文本、ZIP 并在解析完成后加入当前 `open` 项目版本；
- 从当前项目版本绑定的固定需求资产版本创建评审，展示项目版本、绑定、输入、索引、检索、模型、两阶段 Agent、Prompt、工具与权限快照；
- 展示真实排队、完整正文/分批正文投递、跨批归并、工具调用、结果提交、服务端校验、成功、失败和取消状态；
- 查看结构化摘要、跨文档归并的需求点、关联 Finding、风险统计、版本差异和固定证据，并按严重度、需求点证据可追溯性和处置状态过滤；
- 对 Finding 进行确认、驳回、解决或待跟进处置，保留模型初始结果和追加式处置历史；
- 围绕成功运行开展带证据引用的评审问答，不使用本地模拟结果替代真实失败；
- 展示联网、MCP、模型降级、工具拒绝、审批等待、执行限制和可能过期等真实状态。

### 7.4 AI 模型与路由页

- 查看部署侧已注册的生成式模型来源、模型能力、健康状态和脱敏检测结果；
- 配置默认模型、参数、结构化输出、智能路由、重试、降级与回退顺序，并生成不可变配置版本；
- 展示两阶段 Agent、Prompt、工具集、MCP 和网络策略版本摘要，不向普通用户开放任意端点、密钥或通用编排；
- 查看运行级实际模型、路由原因、降级、Token、耗时、Agent 回合和工具调用摘要。

### 7.5 技术方案评审页

- 在当前 `open` 项目版本中选择一个成功需求评审运行作为需求基线；
- 从知识库选择一份或多份 `ready` 的固定技术方案资产版本；
- 展示真实运行状态、需求覆盖、技术 Finding、风险、待确认问题和输入/模型/Agent 快照；
- 从 Finding 或覆盖项定位到固定需求原文或技术方案原文；
- 支持简单 Finding 处置、历史运行查看和 Markdown 报告导出；
- 个人 Demo 不提供技术方案在线改写、复杂审批、Git、代码或 Diff 分析。

### 7.6 测试设计页

- 提供项目级“测试设计 / 测试用例库 / 用例集”视图；用例库只读聚合已发布用例及固定来源，用例集明确区分本次新功能、冒烟、全量回归和功能域套件版本；
- 在当前 `open` 项目版本中选择“评审基线”或“知识库资料”：前者选择同一引用链上的成功需求/技术方案运行，后者选择一至多份 `ready` 固定知识资产版本且不要求评审运行；
- 可显式选择同一项目已发布 `TestCaseSetVersion` 中的用例，或固定的 `ready test_case` 知识资产版本；不自动使用 latest；
- 展示依据解构与召回、范围人工确认、功能/非功能测试点并行发散、测试点树归并与批准、用例具象化、测试数据需求和覆盖审计的连续流程；四个 Agent 节点、两个人工门禁和服务端阶段使用不同状态样式；
- 在树形编辑器中查看功能、性能、稳定性、兼容性和安全测试点，支持新增、移动、拆分、合并、删除、标记不适用、revision/ETag、Diff 和批准；批准后才允许具象化用例；
- 查看按“包含 UI / 包含 API”执行方式组织的结构化用例、测试数据需求、双向追溯矩阵、风险与待确认项；一条用例可包含 UI、API 或二者组合，各方式独立维护步骤/断言；数据需求只定义实体、特征、约束、数量、状态、隔离、重置和清理，不创建真实数据；
- 评审基线驱动项可追溯到冻结需求点/方案要点并经上游对象查看原文；知识库驱动项关联 `KnowledgeBasisItem` 并定位固定资产原文，但不宣称资料已评审；风险推导和通用实践项展示推导理由；
- 支持用例在线结构化修改、草稿保存、revision/ETag 冲突处理、字段级 Diff、逐条/批量审核；
- 支持历史用例适用性判定、默认批量处置、冲突/待确认例外确认、原样复用、复制并修改和来源对比；当前用例使用新 ID/修订，历史版本保持不可变；
- 审核通过且覆盖审计无 blocker 后发布机器可读 `TestCaseSetVersion`，导出同版本 JSON/Markdown/Excel，并生成版本化 `test_case` 知识资产展示投影；
- 本次功能集按新增、修改和原样复用统计；受影响回归只保存固定引用，不复制为功能集成员；
- 支持从当前功能集中确认冒烟候选，将既有冒烟基线与候选解析为去重后的固定组合快照，并生成标准“冒烟 -> 新功能 -> 影响回归 -> 全量回归”、快速和直接全量三种执行交接；
- 第四期不提供正式测试计划、脚本生成、Git/Patch、真实测试执行、日志/截图/Trace、冒烟基线发布或缺陷联动。

## 8. 阶段验收总览

### 8.1 第一阶段验收

第一阶段详细验收场景见 [第一期-项目知识库构建与配置需求文档.md](第一期-项目知识库构建与配置需求文档.md)。总体验收以以下事实为准：

1. 项目资料可以按统一知识资产模型接入、分类、版本化和同步；
2. 未变化内容不会重复产生活动 Chunk 或重复 Embedding；
3. 同步失败、取消或重建失败时，上一个活动索引仍可检索；
4. 检索结果可定位至确定资产版本与原文位置；
5. 配置变更可追踪，影响索引的变更通过异步重建生效；
6. 验收不依赖 AI、Git、测试执行、权限或外部系统能力。

### 8.2 第二阶段验收

第二阶段详细验收场景见 [第二期-需求评审与大模型配置需求文档.md](第二期-需求评审与大模型配置需求文档.md)。总体验收以以下事实为准：

1. 未创建或未选择项目版本时不能进入需求分析；创建 `open` 项目版本后，可将 `ready` 需求资产版本绑定到该版本，且 Review、Run、Finding 和问答只在同一 `projectVersionId` 下可见；
2. 每个评审运行按固定顺序启动需求点提取和需求评审两个独立 Agent 执行实例，并固定项目版本、需求绑定、需求、正文投递策略/模式/Manifest、索引、模型、Pi Agent Framework/Runtime、两阶段 Agent 定义、Prompt、工具、MCP、网络、权限和执行限制版本；后续配置变化不修改历史运行；
3. 两个阶段 Agent 只能调用运行快照内的受控工具；工具循环或 Agent 执行结束不直接代表评审成功；
4. 正常规模输入的全部固定正文首轮直接进入提取 Agent；超长输入按稳定结构分批直传并最终跨批归并，不静默截断、不退化为逐 Chunk 函数调用；正式 Finding 通过结构化 Schema、需求点关联和一致性校验，原文依据经服务端规范化的 Evidence 打开至固定资产版本和原文位置；
5. 模型、检索、工具、联网、MCP、审批或校验失败均显示真实状态，不回退为模拟结果、缓存答案或空白成功；
6. 人工处置追加保存且不覆盖模型初始输出；重新评审创建独立运行，旧运行和处置继续可查看；
7. 允许范围内的只读和可逆外部操作按策略执行，高风险操作未经逐次确认不得执行，越权、注入和越界网络请求被阻断并记录；
8. 取消、失租约、达到回合/Token/工具/超时限制会停止后续调用，迟到结果不得成为正式 Finding；
9. API、页面和普通日志不返回明文密钥、完整 Authorization、未经脱敏端点或敏感工具参数。

### 8.3 第三阶段验收

第三阶段详细验收场景见 [第三期-技术方案分析模块需求文档.md](第三期-技术方案分析模块需求文档.md)。个人 Demo 总体验收以以下事实为准：

1. 可从同一项目版本选择成功需求评审运行和固定技术方案资产版本，完成一次真实的“方案要点提取 -> 冻结结果评审”；
2. 结果可展示需求覆盖、主要技术 Finding、风险与待确认问题，不使用前端模拟结果替代失败；
3. Finding 与覆盖项可以定位到运行时固定的需求或技术方案原文；
4. 失败、取消和重新评审状态真实可见，新运行不覆盖历史；
5. Finding 简单处置和 Markdown 报告可用；
6. 验收不要求生产级准确率、复杂审批、Agent 自由协作、通用编排、Git、代码、Diff、部署或测试执行。

### 8.4 第四阶段验收

第四期详细验收见 [第四期-多Agent测试设计工作流需求文档.md](第四期-多Agent测试设计工作流需求文档.md)。总体验收以以下事实为准：

1. `review_baseline` 可固定引用关系一致的成功需求/技术方案运行；`knowledge_assets` 可只固定用户选择的 `ready` 知识资产版本并在没有 Phase 2/3 运行时创建，两种模式严格互斥且来源变化不修改当前运行；
2. 两种主依据模式都提供严格判别的固定知识补充召回；关闭时生成规范空快照，启用时不能越过 allowlist，也不能将相似资料自动升级为已确认需求；
3. 四个 Agent 沿五阶段产物链工作：测试分析完成依据解构，功能/非功能并行发散测试点，综合 Agent 只读取已批准树；树归并和覆盖审计由服务端完成；
4. 测试点树支持在线新增、移动、拆分、合并、删除、不适用、revision/ETag 和 Diff；树未批准时不得具象化用例，批准后修改会使下游候选过期；
5. 缺少性能指标、恢复目标或兼容矩阵时形成待确认和阻塞，不编造数值或支持承诺；
6. 每条用例的 `executionMethods[]` 至少包含 UI 或 API 之一，也可同时包含二者；每种方式具有独立必要字段、步骤、断言和就绪状态，共享目标/前置/数据/清理，组合用例同时命中两种筛选；测试点与用例允许零/一/多映射但必须可审计；
7. 历史用例必须先映射到测试点树，之后才可原样复用或复制修改；当前用例保存来源、Hash、Diff 和变更摘要，历史版本不覆盖；
8. 测试数据需求以结构化资产定义数据特征和准备约束，不创建真实数据；下一阶段可据此造数；
9. 覆盖审计由服务端按“依据 -> 测试点 -> 用例”关系计算，识别未覆盖、孤立、无 oracle、缺数据、重复和过期 Hash；Agent 自报覆盖不作为正式统计；
10. 在线修改生成不可变 revision 和字段级 Diff，乐观锁阻止并发覆盖，审核决定绑定具体 revision；用例或数据需求变化使旧覆盖审计失效，只有树已批准、当前用例已审核且就绪、审计集合 Hash 完全匹配并无 blocker 时才能发布；
11. 项目测试用例库只读聚合已发布用例和集合归属；当前功能集只含本次新增、修改和原样复用用例，影响回归/全量回归通过固定引用参与交接，不复制正文或改变覆盖分母；
12. 冒烟候选需人工确认；“当前冒烟基线 + 候选”生成去重、固定 Hash 的执行快照，历史冒烟版本不可变，标准/快速/直接全量交接引用明确版本且不创建执行计划或新冒烟版本；
13. 下一阶段 AI 可直接读取包含依据、召回、树、数据、审计 Hash 和集合成员引用的版本化 JSON Schema 及历史沿革，无需解析 Markdown 或回读知识库 `latest`/历史来源；JSON、Markdown、Excel 导出保持同一版本和 caseId；
14. 失败设计节点、树修订、重新具象化、取消和全量重跑具有独立恢复语义，旧运行和检查点不覆盖；
15. 验收不依赖真实造数、测试计划、脚本生成、Git、测试环境、真实执行、日志/截图/Trace、冒烟基线升级、失败诊断或自愈。

## 9. 依赖与前置条件

### 9.1 第一阶段前置条件

第一阶段仅需要：

- 可用于试点的 Markdown/纯文本项目资料；
- 已确定的资料类型分类和逻辑路径约定；
- 可访问的 Embedding 服务或本地 Embedding 运行环境；
- 受控上传存储或受控本地资料目录；
- 用于验证检索和同步行为的样例资料集。

Git API、CI/CD、测试环境、测试账号、`data-testid`、角色权限策略和外部缺陷系统均不是第一阶段前置条件。

### 9.2 第二阶段前置条件

第二阶段需要：

- Phase 1 可稳定提供 `ready` 需求资产版本、Chunk、活动索引、检索与固定证据定位；
- 项目版本服务可创建、查询和切换 `open/locked/archived` 版本，并能维护项目版本与固定需求资产版本的绑定；
- 至少一个部署侧受控注册、支持结构化输出的生成式模型及明确的数据传输和保留边界；
- 满足锁定 Pi Agent Framework 版本要求的 Node.js 运行环境，以及通过兼容性测试的 `PiAgentRuntimeAdapter`；
- 已创建、发布并启用的 `RequirementPointExtractionAgent` 与 `RequirementReviewAgent`，以及各自的 Prompt、默认工具集、模型配置、权限策略和执行限制版本；
- 如启用联网或 MCP，已注册允许的域名、MCP Server、凭据引用、数据发送范围和安全策略；
- 已定义外部操作风险等级、自动执行边界、人工确认门禁、幂等和补偿责任；
- 包含典型需求、预期 Finding、固定证据、工具调用、攻击样例和人工处置的评审质量验收集。

Git API、代码仓库、CI/CD、测试执行环境、组织级角色权限和外部工单系统不是第二阶段需求评审的必需前置条件；如通过受控 Tool/MCP 接入其中任一能力，只能在已注册、最小授权和专项验收范围内使用。

### 9.3 第三阶段前置条件

第三阶段个人 Demo 需要：

- 一期知识库可提供 `ready` 技术方案资产版本、固定正文、Chunk、活动索引和原文定位；
- 二期可提供同项目版本成功 ReviewRun、冻结需求点/Evidence、Finding 和人工处置；
- 至少一个可用生成式模型，并已分别发布技术方案提取与评审 Agent；
- 一组包含少量已知覆盖、遗漏和技术缺口的 Markdown/纯文本样例。

### 9.4 第四阶段前置条件

第四期需要：

- 至少满足一种依据模式：同一项目版本中引用关系一致的成功需求/技术方案运行，或一至多份当前项目知识库的 `ready` 固定资产版本；
- 四个测试设计工作流 Agent 均已创建、配置、通过模型门禁并发布；
- PostgreSQL Job/Worker 支持版本化 DAG、节点依赖、并行、租约、恢复、取消和 fencing；
- Phase 1 支持固定知识资产、索引、检索配置和召回结果快照，不依赖活动索引或 `latest`；
- 已定义测试点树、测试数据需求、测试用例、测试套件和执行交接版本化 Schema，以及树/用例在线编辑与审核规则；
- 验收资料中至少准备一个可复用的历史 `TestCaseSetVersion`、一个固定 `ready test_case` 资产版本；产品正常使用时历史用例不是必填；
- 验收执行交接时准备一个固定冒烟 `TestSuiteVersion`、一个固定全量回归 `TestSuiteVersion` 及其可读取成员；缺少对应基线时仍可发布功能集，但不能生成依赖该基线的交接策略；
- 包含功能、性能、稳定性、兼容性、安全、测试点树编辑、测试数据需求、覆盖审计、纯知识库输入、知识冲突/来源歧义、历史复用/修改/废弃/冲突、重复候选和缺失指标的固定验收集；
- 已确认的测试范围确认、测试点树批准、用例审核与测试产物发布责任人。

## 11. 待确认事项

### 11.1 第一阶段待确认

1. 当前唯一项目首期允许接入的 Markdown/纯文本资料规模和保留周期；
2. 资料类型、逻辑路径和维护责任的项目约定；
3. 首期选用的 Embedding 服务、模型、维度和模型数据存放边界；
4. 重复上传覆盖同一逻辑路径时的默认冲突策略，以及未来 Wiki 等连接器的接入优先级；
5. 第一阶段检索质量评测的样例问题、期望来源和验收阈值；
6. OpenAPI、Excel、PDF、Word 等专用格式解析器的后续接入优先级。

### 11.2 第二阶段待确认

1. Finding 严重度、处置时限、超长需求处理和关键词检索降级规则；
2. 首批生成模型、上下文窗口、数据传输边界、保留策略和路由降级顺序；
3. `RequirementPointExtractionAgent`、`RequirementReviewAgent`、Prompt、工具集和安全策略的维护责任、发布审批、回滚与兼容性测试流程；
4. 最大 Agent 回合、工具调用、Token、单工具结果、总超时和并发配额；
5. 首批联网域名、MCP Server、允许发送的数据范围和外部内容引用规则；
6. 可逆写操作自动执行边界、高风险写操作确认方式、确认人范围和补偿责任；
7. Finding 召回率、证据准确率、工具成功率、安全拒绝准确率和人工复核责任人；
8. 通用 Prompt/Agent 可视化编排、组织级权限审批、成本治理和多模态资料解析的后续阶段安排。

### 11.3 第三阶段待确认

1. 个人 Demo 首批技术方案模板和样例资料；
2. 单次最多选择的技术方案文件数和输入 Token 上限；
3. 技术 Finding 类型、严重度和 Markdown 报告章节是否需要继续精简；
4. 首批模型、最大运行时长、回合数和工具调用数。

### 11.4 第四阶段 Agent 待确认

1. 首批浏览器、操作系统、运行时、数据库和模型 Provider 兼容基线；
2. 固定知识召回模式、Top-K、相似度阈值、最大语料和重排策略；
3. 单次最大需求点、知识资产/Chunk/知识基线项、测试点树节点、候选用例、数据需求、并行专项、Token、回合和总运行时长；
4. 测试设计方法、测试点树模板、数据需求标签/就绪规范和 Excel 导出模板；
5. 评审基线覆盖、知识基线覆盖、已知 P0/P1 测试点召回、重复率、来源关系准确率和覆盖审计 blocker 的试点质量门禁；
6. 性能、稳定性和安全指标策略、模板、维护人与确认流程；
7. 测试范围确认、测试点树批准、批量用例评审和测试资产发布责任人；
8. 知识库模式首批允许的资产类型、资料优先级、默认范围模板和冲突处置规则；
9. 冒烟候选准入阈值、影响回归选择规则和三种执行策略的退出条件；
10. 冒烟/回归/功能域套件的维护责任人、版本命名和归档规则；
11. 后续执行阶段把候选晋级新冒烟版本所需的稳定性证据和人工批准规则。
