## 2. 背景、目标与范围

### 2.1 背景

一期已提供项目知识资产、不可变资产版本、Chunk、活动索引和固定证据定位能力。二期以一个项目版本绑定的多份需求资产版本为同一批固定输入，先跨文档提取、去重和归并需求点，再围绕需求点形成可复核、可人工处置的评审结论；不以“逐篇文档单独评审”为主流程。

### 2.2 本期目标

1. 以项目版本作为需求评审的强制工作空间，并固定项目版本、需求绑定、输入资产、检索范围、索引、模型和运行配置。
2. 从多份固定输入中提取可独立实现、测试或验收的结构化需求点；正常规模输入必须将完整固定正文直接交给提取 Agent，避免以逐 Chunk 函数调用代替全文理解，再识别缺口、歧义、冲突、边界、验收风险和测试风险。
3. 让每条项目事实可定位至固定资料版本；无法证明的结论必须明确标记为待确认、模型推测或外部参考。
4. 支持 Finding 的人工确认、驳回、解决、待跟进和评论，并保留原始 AI 输出与历史运行。
5. 提供受控的生成式模型来源、配置版本、路由、重试、降级和调用观测能力；凭据不进入浏览器、业务数据库明文字段或普通运行日志。
6. 基于 Pi Agent Framework 交付固定的 `RequirementAnalysisWorkflow`：先运行需求点提取 Agent，再运行需求评审 Agent；由 SmartHub 控制业务状态、校验、正式发布和人工处置。
7. 对工具、联网、MCP 和外部操作实行最小权限、风险分级、审批、取消和审计；模型不得绕过服务端策略。

### 2.3 本期交付范围

- 项目版本创建、选择、继承、锁定、归档及其需求资产版本绑定；
- Markdown、纯文本和 ZIP 的受控上传及复用一期入库流程；
- 多文档联合需求点提取、Finding 评审、固定证据定位、人工处置、历史查看与只读评审问答；
- 生成式模型来源、模型能力、评审模型配置版本、路由、重试、降级、检测和运行级观测；
- 平台级 MCP、Skill 与工具资源目录的登记、编辑、启停、删除及确定性引用校验；Skill 支持受控 ZIP 上传、不可变内容 Hash，以及由运行权限清单声明的包内 PowerShell 脚本和 GET/HEAD 网络访问；脚本与网络权限归属 Skill，不作为可独立登记或勾选的工具资源；内置和本地工具支持受控只读源码查看，资源登记或包上传不自动扩大 Agent 运行权限；
- 固定双阶段 Agent 流程、版本化 Prompt/工具/权限、Tool Runtime、联网/MCP 策略与外部操作确认；
- 顶部操作区、左侧输入文件目录、中间评审工作区、右侧问答区和 Markdown 报告导出。

### 2.4 非目标

本期不交付以下能力，验收不得依赖它们：

- 技术方案生成或评审、Git/代码/PR 分析、测试用例或脚本生成、测试执行、CI/CD、日志诊断和自愈；
- PDF、Word、Excel、HTML、图片、原型图等专用格式的正文解析与多模态评审；
- 需求原文富文本编辑、AI 改写、划词重写、User Story 转换、建议自动应用或自动写回知识库；
- Jira、PingCode、Webhook 等外部项目管理系统同步或跨项目工单联动；
- 多项目管理、项目选择器、跨项目资源共享和跨项目分析；当前平台实例只服务系统初始化的一个项目；
- 面向普通用户的通用 Prompt/Agent 编排、任意 Agent 发布，以及把目录中的任意工具/MCP/联网端点直接接入运行时或绕过服务端白名单；
- 动态多 Agent 协作、Agent 间自由委派、共享会话、任意 DAG 或工作流编排；
- 浏览器录入密钥、任意 Shell/代码执行环境、宿主文件系统访问和不受控外部操作；
- 完整的组织、角色、ACL、审批流、SSO、合规审计和成本结算体系。

固定的双阶段 `RequirementAnalysisWorkflow` 不属于通用多 Agent 协作：参与 Agent、执行顺序、输入交接和权限均由服务端预先定义，不支持动态扩展。

## 3. 核心对象与全局原则

### 3.1 核心对象

```text
平台实例（单项目）
  └─ 当前项目（系统初始化）
       ├─ 默认知识库（项目级共享）
       │    └─ 需求知识资产 → 不可变资产版本 → Chunk / 索引版本
       └─ 项目版本（项目空间隔离边界）
            └─ 项目版本需求绑定 → 固定 assetVersionId

需求评审（归属项目版本）
  └─ ReviewRun（固定输入与配置快照）
       ├─ RequirementAnalysisWorkflow
       │    ├─ RequirementPointExtractionAgent
       │    └─ RequirementReviewAgent
       ├─ 需求点、Finding、Evidence 与人工处置
       └─ 评审问答会话

模型与执行治理
  └─ 模型来源 → 模型定义 → 评审模型配置版本 / 路由策略
  └─ Agent 定义版本 → Prompt / 工具集 / MCP 与网络策略 / 执行限制
```

| 对象 | 定义与规则 |
|---|---|
| 项目版本（`ProjectVersion`） | 项目空间数据的强制隔离边界，状态为 `open`、`locked`、`archived`。仅 `open` 可维护需求绑定和创建新运行。 |
| 项目版本需求绑定 | 项目版本对一个固定需求 `assetVersionId` 的引用，不复制知识资产；资产产生新版本不会自动改变既有绑定。 |
| 需求评审（`Review`） | 在确定项目版本中，基于该版本有效需求绑定创建的逻辑实体，不替代原需求文档。 |
| 评审运行（`ReviewRun`） | 一次可取消、可追溯的固定输入执行尝试。重新评审创建新运行，历史运行不可覆盖；新运行可声明复用某个失败运行中已校验冻结的需求点提取检查点。 |
| `RequirementAnalysisWorkflow` | 二期固定需求分析业务流程，不是 Agent 定义；它规定“提取并冻结需求点，再评审”的顺序和发布门禁。 |
| `RequirementPointExtractionAgent` | 默认直接接收服务端组装的完整固定需求正文；超长输入接收确定性分段正文。每条需求点正常生成简洁 `title`，并提交 `description` 与属于自己的 `sourceTexts` 原文线索；标题缺失时服务端兜底，其余结构、Evidence、固定引用、定位与覆盖范围由服务端生成。 |
| `RequirementReviewAgent` | 只读取已冻结的需求点提取产物和证据快照，提交总体摘要和逐条对应需求点的分析；服务端生成 Finding ID 与正式引用结构。 |
| `ReviewQaAgent` | 绑定一个已成功完成的 ReviewRun 回答评审追问；拥有独立模型、Prompt、Skill、MCP、Tool 和发布版本，但不能修改正式评审结果或扩大固定 Evidence 白名单。 |
| Finding | 可人工处置的结构化评审结论，如缺口、歧义、冲突、边界或风险。 |
| Evidence | 需求点引用的固定资产版本、Chunk、内容 Hash、定位和摘录快照；Finding 仅通过关联需求点间接追溯。 |
| 评审模型配置 | 供后续运行使用的模型、参数、路由及降级策略的不可变版本。 |
| Agent 定义版本 | Agent 的类型、Prompt、允许工具、权限、执行限制和安全策略组成的不可变版本。 |
| Tool Runtime | 对注册工具执行参数、身份、权限、风险、审批、超时、取消、脱敏和审计的服务端运行层。 |

### 3.2 全局原则

- **单项目、项目版本隔离**：平台不提供项目切换；Review、Run、Finding、问答、统计和导出必须按 `projectVersionId` 隔离。
- **固定输入与可复现边界**：运行创建后不得悄然切换到最新资料、索引或配置；模型输出可非确定，但输入、路由、证据、Prompt 和最终结果必须可还原。
- **证据优先**：项目事实必须可映射至固定证据。证据不足时只能标记为待确认或模型推测，不能伪装为已证实事实。
- **人机分工**：AI 提供结构化问题、风险和建议；人工决定处置。系统不得自动修改需求、关闭 Finding 或发布知识资产。
- **业务流程外层、Agent 执行内层**：排队、租约、取消、路由、重试、Schema 校验、正式落库和人工处置由 SmartHub 控制；Agent 只在单次受控执行内调用已授权工具。
- **全文理解优先、工具辅助治理**：只要模型上下文预算允许，完整固定需求正文必须在首轮直接交给提取 Agent；工具用于补读、证据校验和结构化提交，不得把正常规模文档强制拆成逐 Chunk 工具往返。
- **最小权限与不信任外部内容**：工具、MCP、联网和外部写操作默认关闭，按 Agent 定义版本显式开放。文档、网页、MCP 和外部系统返回内容均为不可信数据，不得改变 Prompt、权限、路由或终止条件。

## 4. 用户工作台与主流程

### 4.1 创建并运行联合评审

```text
选择或新建 open 项目版本
  → 上传资料并等待 ready，或从知识库选择 ready 的需求资产版本
  → 将固定资产版本绑定到当前项目版本
  → 系统使用该版本全部有效绑定作为输入范围
  → 校验索引、模型、Agent、工具权限与上下文预算
  → 创建 queued ReviewRun 并固定运行快照
  → 服务端组装带资产/Chunk 边界的固定正文输入包
  → 正常规模全文直传；超长输入按固定批次注入并最终跨批归并
  → 提取 Agent 仅提交 description 与 sourceTexts 原文线索
  → 服务端生成需求点/Evidence ID 与引用，规范化并去重 Evidence、生成覆盖证明并冻结提取产物
  → 评审 Agent 基于冻结产物提交 Finding 和摘要
  → 服务端校验并原子发布正式结果
  → succeeded，等待人工处置
```

运行失败、取消或校验不通过时，系统保留过程记录、失败步骤和脱敏错误摘要；不得展示示例结果、模拟回答或“无问题”的伪成功结论。若需求点提取已完成独立校验和冻结而需求评审失败，用户可选择“重新需求评审”，创建新 ReviewRun 并复用、重新校验该冻结提取检查点，只执行需求评审；也可选择“全部重跑”，按当前项目版本和当前已发布的两个 Agent 配置从需求点提取开始。提取未冻结时只允许全部重跑。

### 4.2 三栏评审工作台

页面采用“顶部操作区 + 左侧文件目录 + 中间评审工作区 + 右侧评审问答区”。未创建或未选择项目版本时，只显示版本说明和“新建项目版本”主操作，不加载需求列表或评审数据。

| 区域 | 用户可见能力 |
|---|---|
| 顶部操作区 | 显示当前项目版本、固定输入文档数量、运行 ID、真实状态/进度、正文投递模式（完整直传/确定性分段）、输入 Token 与预算、检索或模型降级状态和输入快照；提供提取并评审、取消、重新需求评审、全部重跑和报告导出。重新需求评审仅在存在有效冻结提取检查点时可用；两种重跑都必须创建新 `ReviewRun`。 |
| 左侧文件目录 | 仅显示当前项目版本已绑定且 `ready` 的固定需求文档、逻辑路径和资产版本。点击只用于查看固定原文或承接证据定位；不提供逐文档评审。支持上传并加入当前版本、从知识库加入和折叠布局。 |
| 中间评审区 | 提供评审概览、原始文档、版本差异、需求点、证据引用五个视图。需求点视图只展示需求点、固定证据与关联 Finding 数量/跳转，不渲染完整 Finding 内容。 |
| 右侧问答区 | 仅对成功运行的固定输入、正式结果、证据快照、会话历史和授权只读工具提问；显示回答状态、引用、实际模型、重试/降级摘要和时间。折叠不清空会话。 |

原始文档按固定 `assetVersionId` 只读打开，Markdown 支持章节大纲、目录跳转、滚动同步和证据范围高亮。版本差异仅比较同一资产的两个固定版本，必须展示真实新增、删除和修改内容；无可比较版本时明确提示。

### 4.3 人工处置、历史与导出

- Finding 可确认、驳回、标记已解决、保持待确认并追加说明；原始 AI 内容和证据快照不可改写。
- 页面分别展示需求资产版本历史、评审运行历史、Finding 处置历史、Agent 对话和事件时间线，不混用为含义模糊的“历史”。
- Agent 对话展示模型可见消息、工具请求/参数摘要与返回摘要；事件时间线展示生命周期边界。同一 `ReviewRun` 发生 Worker 自动重试时，需求点提取与需求评审必须分别形成独立的 attempt 展示序列；切换 Agent 后只显示该 Agent 对应的状态、错误、对话、事件和降级，不能共用一组重试切换，后一次尝试也不得覆盖前一次。旧数据未独立保存对话时必须明确提示不可恢复。不得保存或展示 API Key、Authorization、签名、图片二进制和模型隐藏思维。
- 点击 Finding、需求点或 Evidence 时，按 `assetVersionId` 打开固定原文、滚动并高亮正式证据位置；无法读取或定位时保留上下文并显示错误，不能跳转到最新版本。
- 支持复制或导出 Markdown 报告。报告包含固定输入摘要、运行快照标识、正式统计、Finding、Evidence、降级说明和人工处置状态；默认不包含问答全文、候选结果、明文凭据或未脱敏执行日志。

## 5. 功能需求

### 5.1 需求评审

#### FR-201：项目版本、需求绑定与运行前置

- 每个 Review 和 ReviewRun 必须归属已存在的 `projectVersionId`；未选择版本或不存在有效需求绑定时，不加载评审数据、不允许启动运行。
- `open` 版本可新增、替换和移除需求绑定并启动运行；`locked`、`archived` 版本只允许查看历史。新版本可继承来源版本的有效绑定，但不得复制 Review、Run、Finding、问答或处置记录。
- 同一项目版本、同一需求资产最多有一条有效绑定。替换时用户显式选择新的 `ready assetVersionId`，新建绑定并将旧绑定标为 `superseded`；历史运行继续引用旧绑定。
- 仅 `open` 版本可执行受控物理删除；有运行中任务时先取消。删除不移除全局知识资产；存在需保留运行审计记录或被其他版本继承时禁止物理删除，仅允许归档。
- 用户可从默认知识库选择资料类型为 `requirement` 的 `ready` 资产版本加入当前项目版本。评审页支持 `.md`、`.txt`、`.zip` 上传，复用一期校验、解包、解析、索引和失败反馈；逻辑路径为 `版本文档/{项目版本名}/需求文档/{文件或 ZIP 内相对路径}`。ZIP 内图片作为附件保留但不参与正文分析，其他格式逐项跳过并反馈。
- 每次运行必须使用所选项目版本的**全部有效需求绑定**作为固定输入集合，不支持仅选择一个绑定绕过其他有效输入。运行前校验资产均为 `ready`、输入可读取、存在活动索引和可用评审模型配置。

#### FR-202：运行快照、状态与取消

- 创建运行时固定：服务端派生的 `projectId`、`projectVersionId`、全部有效 `requirementBindingId`、知识库、每份输入的资产/版本/内容 Hash/逻辑路径、`indexVersionId`、正文投递策略版本、投递模式、内容清单/批次/Token 预算、模型配置与实际路由、两阶段 Agent 定义与 Prompt/工具/MCP/网络/权限快照、Pi Framework/Runtime 版本、执行限制和触发时间。客户端不得提交或切换任意 `projectId`。
- 运行状态至少包括 `queued`、`running`、`succeeded`、`failed`、`cancelled`；页面进度必须来自服务端，至少覆盖输入校验、快照、正文输入包组装/投递、提取、Evidence 规范化、覆盖校验、冻结、评审、结果校验、正式保存和等待人工评审。
- 用户可取消未完成运行。取消、Worker 失租约、服务端关闭或达到执行限制时，取消信号必须传播至模型与工具；后续调用停止，迟到结果只能保留为过程记录，不能进入正式结果。
- 重新评审必须创建新的 `ReviewRun`，不得覆盖历史输入、需求点、Finding、Evidence 或人工处置。模型、Agent、Prompt、工具或索引更新仅影响后续运行。

#### FR-203：需求点、Finding 与结果校验

成功运行至少产生以下正式结果：

| 输出 | 要求 |
|---|---|
| AI 需求摘要 | 基于全部固定输入生成，并明确标记为 AI 摘要。 |
| 需求点 | 跨文档按可独立实现、测试或验收的粒度提取，包含稳定 ID、标题、说明、主体、动作、对象、条件、业务规则、异常、验收标准、归并信息与至少一条固定证据。 |
| Finding | 按缺口、歧义、冲突、边界、验收风险、测试风险分类，包含问题、影响、建议确认项、严重度、置信度和关联需求点。 |
| 评审统计 | 由已持久化的正式结果计算需求点、Finding、待确认、风险及可经需求点追溯原文的 Finding 数量。 |
| 版本差异 | 用户选择同一资产两个固定版本时，展示真实差异及受影响 Finding。 |

- Finding 严重度为 `blocker`、`high`、`medium`、`low`；Finding 必须关联至少一个需求点，原文依据通过该需求点的固定 Evidence 间接追溯。Finding 不保存或提交直接 Evidence 引用，缺失的事实前提、歧义或风险仍须说明待确认原因。
- 服务端必须校验两阶段提交的结构化 Schema、必填字段、引用可解析性、输入覆盖与关联关系。提取结果出现 Finding/评审摘要，或评审结果出现需求点/Evidence/覆盖范围时必须拒绝。
- 服务端必须先将全部固定需求资产规范化为 `RequirementInputPackage`：正文按文档、标题和 Chunk 设置不可伪造的边界标识，并附带资产版本、内容 Hash、Chunk ID、标题路径和定位信息。输入包属于运行快照；正文虽然直接进入模型上下文，仍按不可信数据处理，不能改变系统指令和工具权限。
- 当完整输入包不超过模型的安全输入预算时，必须使用 `full_context` 模式在提取 Agent 首轮直接交付全部固定正文，不得要求模型为了获得正常规模正文逐个调用 `knowledge.read_chunk`。输入预算必须预留 System/Task Prompt、工具 Schema、输出、修正回合和安全余量。
- 当完整输入包超过安全预算时，使用 `segmented_context` 模式，由服务端按固定文档顺序和标题/Chunk 边界生成可复现批次；每批直接注入正文并生成阶段性需求点，最后在保留来源 Evidence 的前提下执行一次跨批归并与完整性复核。不得静默截断、仅依赖检索 Top-K、让模型自行决定漏读范围，或退化为每个 Chunk 一次工具调用。连最小批次和最终归并上下文也无法容纳时，启动必须拒绝并展示资产、Token、批次数和拆分建议。
- 覆盖证明由服务端根据实际成功投递给模型的 `InputDeliveryManifest` 生成，记录每个资产/Chunk 的投递批次、内容 Hash、Token 数和投递状态；模型不得自行声明 `reviewedChunkIds` 作为覆盖事实。只有全部未排除正文均成功投递且最终归并完成，提取结果才能冻结。
- 提取 Agent 每个需求点正常生成简洁 `title`，并提交 `description` 与 `sourceTexts` 原文或高区分度原文线索，不提交其他结构化槽位、归并字段、资产版本、Chunk、需求点/Evidence ID、`evidenceRef(s)`、coverage 或 locator。标题缺失或空白时服务端根据描述兜底，不得因此拒绝提交。服务端跨本次全部固定输入执行精确、Markdown 可见文本、规范文本、省略片段和置信候选检索，从固定正文生成并去重 Evidence、定位和引用；精确原文的全部位置均保留，模糊匹配保留 `[max(0.45, 最高分 - 0.08), 最高分]` 区间内的全部证据。单条线索失败但该需求点已有其他有效 Evidence 时不得拒绝整次提交，只有需求点完全无 Evidence 时才进入定点修复。首次全文提取只开放结果提交，`knowledge.search/read_chunk` 仅在完全无法建立 Evidence 后开放。每个需求点至少关联一条有效 Evidence，每条 Finding 至少关联一个有效需求点。
- `description` 必须表达原子需求；不同主体、动作、前置条件、状态、异常、权限、数据约束或验收标准应拆分。相同描述的重复点及重复原文线索由服务端自动合并，模型无需维护归并组和理由。候选结果、普通模型文本、部分流式内容和 Agent 结束事件均不得直接成为正式结果。
- 评审 Agent 提交总体摘要和逐条分析；每条分析只通过一个 `requirementPointRef` 对应冻结需求点。标题、类型、严重度、置信度、分析内容、影响和建议由模型给出，Finding ID 与正式 `requirementPointRefs` 由服务端生成。展示字段偶发缺失或格式不规范时服务端兜底，不反复退回；需求点引用不存在或分析内容为空时必须拒绝。
- 关键词检索与 Reranker 只用于补充知识或定点修复，不是固定需求正文的主要投递通道。检索降级可按已保存策略继续但必须显示原因；固定需求版本不可读取或正文投递不完整时运行失败，不得只依赖模型记忆或检索摘要生成结论。

#### FR-204：固定证据与原文定位

- Evidence 至少保存 `assetId`、`assetVersionId`、`chunkId/chunkKey`、Chunk 内容 Hash、标题路径、行号或字符范围、引用摘录、`indexVersionId`、检索得分和降级状态。
- 评审来源和引用原文必须按固定 `assetVersionId` 打开；资料后续更新时不得自动跳转至最新版本。
- 证据引用视图按需求点展示资料、逻辑路径、版本、标题路径、定位和摘录；Finding 经其关联需求点聚合展示这些证据。点击后打开固定原文并高亮。原文选区只能反查正式保存的需求点—Evidence—Finding 关系，不能创建伪关联。
- 联网或 MCP 内容只有映射至本次允许的需求点 Evidence 范围并通过引用校验后，才能作为外部参考展示；不能写入 Finding 的直接 Evidence 字段。

#### FR-205：人工处置与历史查看

- Finding 初始状态为 `open`；人工可更新为 `confirmed`、`dismissed`、`resolved`、`needs_follow_up`。不可变动作与状态投影固定映射为：`confirm → confirmed`、`dismiss → dismissed`、`resolve → resolved`、`request_follow_up → needs_follow_up`、`reopen → open`；第二期不创建或维护外部任务实体。
- 每次处置追加保存动作、前后状态、说明、操作者显示信息、时间和并发版本。`dismiss`、`request_follow_up`、`reopen` 必须填写说明；不得改写模型原始标题、描述、严重度、置信度、关联需求点或既有处置记录。
- 页面支持按类型、严重度、需求点证据可追溯性和处置状态组合过滤，并显示未处理数量；Finding 卡片提供查看关联需求点证据、定位原文、处置、补充说明和发起追问入口。
- 当输入资产有新活动版本或运行索引不再活动时，历史运行显示“可能过期”；提示不得自动改变 Finding 状态、关闭 Finding 或触发重跑。跨项目版本比较必须显式选择双方版本和绑定。

#### FR-206：评审问答

- 问答必须绑定已成功完成的 `ReviewRun`，由独立且已发布的 `ReviewQaAgent` 执行；它不是新的评审阶段，也不能修改已发布结果。每轮必须固定实际使用的问答 Agent 配置版本。
- 问答上下文仅包括该运行的固定需求资产版本、检索 Evidence、正式结构化结果、会话历史及问答 Agent 发布版本授权的 Skill、MCP 和 Tool。用户可引用 Finding 或固定原文范围，引用至少保存资产版本、标题路径、定位和摘录 Hash。外部工具内容可以辅助解释，但不得成为 Evidence 引用或改变固定事实边界。
- 每轮保存问题、回答、模型配置/实际模型、Agent/Prompt/工具集版本、执行时间、用量和工具摘要、引用 Evidence 与失败摘要；读取历史或发送前重新校验访问权限。
- 生成中允许查看实时执行摘要，完成或失败后保留该轮的 Turn、模型公开输出、工具名称/调用 ID、脱敏参数与返回、状态和错误。不得展示模型隐藏思维链；固定需求正文只显示投递事实，不在问答轨迹中整份复制。
- 模型不可用、超时、证据不足或输出校验失败时显示真实脱敏原因，不得返回模拟答案。问答不自动进入知识库。

#### FR-207：过期与运行范围一致性

- 切换项目版本或历史运行时，前端必须取消旧请求、清空旧视图，再按新的 `projectVersionId + runId` 加载；服务端已运行任务继续归属原版本，不因页面切换迁移或取消。
- 左侧目录、概览、原文、需求点、证据、问答、统计和导出必须同时绑定选定项目版本与运行，不得以默认、最新或其他项目版本数据兜底。
- 分享或刷新链接后，应恢复其显式指向的项目版本、评审和运行；不存在或无权限时显示明确错误。

#### FR-208：真实状态与失败呈现

- 模型 429、临时 5xx 和连接错误按模型配置有限重试；重试耗尽后仅按 FR-304 的条件降级，并保留真实终止原因。不得误报为模型不支持工具调用。
- 配置、模型、检索、工具、Agent 或结果校验异常不得转换为“无问题”、空白成功、缓存结果或本地 fixture；页面保存、检测和运行状态以服务端结果为准。
- 运行记录可展示已完成消息、工具调用、步骤和错误摘要，并区分同一运行内的 Worker attempt 与人工重跑产生的新 `ReviewRun`；未采集正文时明确标注，不能伪造或回填。逐 Token 增量和无内容工具增量不逐条持久化，以避免无界膨胀。

#### FR-209：工作台路由与报告导出

- 页面 URL 或等价路由状态必须稳定表达 `projectVersionId`、`reviewId`、`runId`、当前视图及可选 `findingId/evidenceId`；推荐 `/versions/{projectVersionId}/requirement-reviews/{reviewId}/runs/{runId}`。唯一项目由服务端会话确定，不进入用户可切换路由。
- 左右两栏可折叠；窄屏可收纳为抽屉，但不得隐藏运行状态、需求点证据可追溯性或人工处置入口。
- 导出报告必须从指定项目版本和运行的正式持久化结果生成，并重新校验权限；不得导出候选输出、问答全文、明文凭据或未脱敏日志。

### 5.2 大模型配置与路由

#### FR-301：模型来源与安全边界

- 生成式模型配置与一期 Embedding/检索配置独立管理；修改生成模型配置不得触发索引重建。
- 首期仅支持部署环境注册的 OpenAI-compatible Chat Completions 或等价受控文本生成适配器。模型来源包含稳定 ID、显示名、协议、启用状态、部署侧端点与凭据引用、可用模型和健康状态。

#### FR-302：模型定义与能力声明

每个模型至少维护 `modelId`、显示名称、来源、启用状态、最大上下文长度、最大输出 Token、语言/文本能力、结构化 JSON 输出能力、工具调用能力、可配置推理等级、默认超时、最大重试、健康状态和最近一次脱敏检测结果。需求评审只能选择能容纳本次正文投递计划、支持结构化提交且健康状态满足要求的模型；工具调用探测通过不等于需求提取质量合格，历史运行仍保存实际模型、上下文预算与推理配置快照。

#### FR-303：评审模型配置版本

- “AI 模型与路由”页面支持模型配置草稿、未保存提示、保存和版本历史。
- 配置包含默认模型、温度、推理等级、最大输出 Token、上下文安全余量、超时、重试、结构化输出模式、智能路由开关、降级开关和候选回退模型顺序。
- 保存生成新的不可变配置版本；无变化不生成冗余版本。新版本只影响后续运行。
- 配置页只展示两阶段 Agent、Prompt、工具集、MCP 和网络策略的版本及摘要；普通用户不能编辑、发布或任意授权这些配置。

#### FR-304：路由、重试与降级

- 关闭智能路由时，新运行使用当前默认模型；开启时，系统依据模型能力、上下文长度、启用状态和健康状态选择模型，并记录选择理由。
- 主模型发生可重试错误时先按配置重试；仅当允许降级且候选模型满足输入长度和结构化输出能力时才切换回退模型。
- 运行、调用记录和最终结果必须展示实际模型、重试次数和降级原因。无可用模型时运行失败，不得回退为示例、缓存回答或旧结果。
- 路由、重试和降级由 SmartHub 在 Agent 执行边界外控制；Agent 不得自行选择模型、密钥或回退顺序。

#### FR-305：受控模型检测

- 配置页可对已注册模型执行受控连通性、长上下文理解、结构化输出和最小提交工具检测，使用部署侧凭据，不使用项目需求资料作为测试内容。
- 检测返回可用性、实际上下文/结构化/工具能力、推理配置、检测时间和脱敏错误摘要；不得回显密钥、请求头、完整端点或服务端原始堆栈。正式可用性还必须通过版本化黄金样本质量门禁。

#### FR-306：模型调用观测

每次模型调用至少记录运行/会话/执行 ID、配置版本、实际模型、路由和降级结果、开始/结束时间、耗时、输入/输出 Token（可用时）、重试次数、状态和脱敏错误摘要。本期仅提供评审运行级执行概览，不提供组织级账单、价格计算或配额分配。

### 5.3 Agent、工具与外部能力治理

#### FR-401：固定双阶段 Agent 流程

- `RequirementAnalysisWorkflow` 必须按顺序启动 `RequirementPointExtractionAgent` 与 `RequirementReviewAgent`，二者拥有不同的 Agent 定义、Pi session、执行 ID、Prompt、工具集、权限和执行限制。
- 提取 Agent 输入为服务端组装的 `RequirementInputPackage`、投递清单和范围约束。`full_context` 模式首轮直接包含全部正文；`segmented_context` 模式由 Orchestrator 逐批直接注入正文并在末尾触发跨批归并。提取输出为每个原子需求点的可选 `title`、必填 `description` 与 `sourceTexts`；标题缺失时服务端兜底，其余结构、Evidence、资产版本、Chunk、需求点/Evidence ID、`evidenceRefs`、正式 locator 与 coverage 由服务端生成。评审 Agent 输入仅为服务端校验冻结的提取产物，输出总体摘要和逐需求点分析。
- Context Assembler/Orchestrator 必须记录每个固定 Chunk 是否、在哪个批次、以哪个 Hash 成功进入模型可见上下文。提取 Agent 不能以普通文本、检索摘要或自行填写的 coverage 替代投递事实。投递不完整、分批结果未完成最终归并或 Evidence 无法回到固定正文时，结果提交必须被拒绝并返回可修复问题。
- 首次提交因无效摘录、结构错误或关联缺失被拒绝时，系统必须将具体校验项返回提取 Agent，并允许其在受限修复回合中使用 `knowledge.read_chunk` 定点补读后重新提交；修复回合仍不通过才终止。正常流程不得要求按目录页或所有 Chunk 执行工具调用。
- 两个 Agent 不共享消息历史。评审 Agent 不得读取新文档、创建新 Evidence、增删/合并/拆分/改写需求点；两个 Agent 都不得直接写 Finding、处置记录、知识资产或活动索引。
- 双阶段不要求每次人工重跑都从第一阶段开始。提取结果通过独立校验后必须连同 `InputDeliveryManifest`、Evidence、coverage 和提取执行记录冻结为阶段检查点；随后评审失败或取消时，可基于该检查点创建仅包含新评审执行的 ReviewRun。复用前服务端必须重新校验检查点，且新运行记录来源运行 ID；检查点缺失或失效时只能全部重跑。
- Agent 只能通过提交工具提交候选结果。只有两阶段结果通过服务端 Schema、Evidence、一致性和业务校验并原子保存后，`ReviewRun` 才能进入 `succeeded`。Agent 结束、工具循环结束或普通文本输出不代表运行成功。
- Pi Agent Framework 负责单 Agent 的模型交互、消息状态、工具循环、流式事件和取消传播；PostgreSQL Job/Worker 负责排队、租约、恢复、重试、取消和最终业务状态。

#### FR-402：Agent、Prompt 与执行限制版本

- 每个 Agent 定义包含稳定 ID、类型、不可变版本、系统指令摘要、Prompt 模板版本、模型配置引用、工具集、权限、MCP/网络策略、外部操作策略、执行限制、启用状态和创建时间。
- Prompt、工具描述、权限、正文投递策略、上下文预算、推理等级或执行限制变更必须生成新版本；已创建运行继续使用其固定快照。Pi Framework/Runtime 依赖也必须锁定明确版本并经过兼容性测试后升级。
- 每个定义必须设置最大回合数、最大工具调用数、单工具结果长度、总 Token 预算、保留输出 Token、安全余量、正文投递模式阈值、分批上限和总执行超时。推理等级默认使用模型/场景配置，不得由运行时无记录地固定关闭。达到限制时终止后续执行并显示真实原因，候选结果不得标记为成功。

#### FR-403：统一工具注册与执行

- 所有工具转换为统一 Tool Descriptor，至少声明稳定名称与版本、`builtin/local/http/mcp/sandbox` 类型、输入/输出 Schema、权限、`read/network-read/code-execution/write-reversible/write-high-risk` 风险等级、超时、幂等性、重试、结果大小限制和数据发送范围；重复调用默认拒绝，只有显式授权、固定快照、只读且幂等的工具可重放一次已成功结果。
- Tool Runtime 每次调用前校验工具属于运行快照、参数符合 Schema、调用身份与权限有效、目标在允许范围、审批有效且取消信号未触发。普通读取额度耗尽不得占用候选结果提交和有限修正的保留额度。
- 提取 Agent 可使用知识库检索、Chunk/原文定点补读、批量 Evidence 预校验和 `requirement-points.submit_result`；这些工具不得成为正常规模正文的强制读取链路。评审 Agent 默认仅使用 `review.submit_result`。通用 Shell、任意宿主路径、未声明脚本和未注册动态工具默认禁用；管理员信任的不可变 Skill 包可通过 `skill-runtime.json` 声明相对路径 PowerShell 脚本，管理员选择该 Skill 发布后，服务端自动把声明的脚本能力固化为内部运行权限，无需另选工具。

#### FR-404：联网与 MCP

- 联网仅可访问部署侧允许的协议、域名、端口和数据范围；默认阻止内网、回环、云元数据、文件协议、越界重定向和凭据转发。
- Skill 自主联网必须在 `skill-runtime.json` 中逐项声明 HTTP/HTTPS Origin、GET/HEAD 方法和超时；管理员选择该 Skill 发布后，服务端自动固化对应网络只读权限，无需另选工具；请求不得携带模型提供的认证头，不跟随重定向，响应不得超过平台上限。
- MCP Server 由部署环境预注册并固定配置版本；发现的工具必须转换为 Tool Descriptor 后才能使用，名称或返回内容不能自动获得权限。
- 发送到联网/MCP 的数据最小化并记录数据策略。外部响应保存来源、获取时间、工具版本和必要摘要；不能映射固定项目 Evidence 时，仅作为外部参考或待确认信息展示。

#### FR-405：外部操作与人工确认

- `read` 与受限 `network-read` 工具可按运行权限自动执行。`code-execution` 只允许管理员信任、内容 Hash 固定且脚本清单明确的 Skill，由管理员在 Agent 发布时显式授权；`write-reversible` 仅在 Agent 定义允许、目标受限、具备幂等键和补偿方式时自动执行或请求确认；`write-high-risk` 必须逐次人工确认。
- 确认记录至少保存运行、工具、参数摘要/Hash、风险、确认人显示信息、时间、有效期和结果。参数变化、拒绝、超时或取消后确认失效并阻止执行。
- 模型不得通过拆分参数、改用其他工具或联网/MCP 间接调用规避审批。外部操作不得自动修改需求原文、正式知识资产、Finding 处置或活动索引。

#### FR-406：执行记录、审计与终止

- Agent 执行记录至少包含执行 ID、运行/消息 ID、Agent 类型与定义版本、Framework/Runtime/Prompt/工具/MCP/网络策略版本、开始/结束时间、回合数、工具数、Token 汇总、终止原因和脱敏错误摘要。
- 工具调用记录至少包含名称/版本、调用 ID、脱敏参数与返回摘要、风险、权限/审批结果、耗时、状态、重试和错误摘要。图片二进制、签名和平台凭据不进入运行记录，大结果保存受控引用或 Hash。
- 页面按“模型调用—工具执行—结果提交—服务端校验”展示真实步骤；不保存、展示或伪造模型私有推理和进度。

## 6. 数据快照与一致性规则

### 6.1 最小记录字段

| 实体 | 最小字段 |
|---|---|
| 项目版本及绑定 | 项目/版本 ID、状态、来源版本、固定 `assetVersionId`、绑定状态、创建人与时间。 |
| Review 与 ReviewRun | `reviewId`、`runId`、项目版本、绑定/输入资产/Hash 集合、索引快照、`RequirementInputPackage`/`InputDeliveryManifest` 摘要、投递模式/批次/Token 预算、状态、进度、模型配置与实际路由、两阶段 `agentDefinitions`/`agentExecutions`、权限和限制快照、起止时间、错误摘要。 |
| 需求点、Finding、Evidence | 稳定 ID、所属运行、需求点来源与 Evidence、Finding 需求点关联/分类/严重度/置信度/初始输出、Evidence 固定定位与摘录。 |
| 人工处置与问答 | 处置前后状态、说明、操作者、时间；问答内容、原文/证据引用、模型与 Agent 快照、用量、工具摘要和失败摘要。 |
| 模型、Agent 与调用记录 | 模型配置版本、Agent 定义版本、Agent 执行、模型调用、工具调用、审批记录及其版本、路由、权限、脱敏摘要和时间。 |

### 6.2 一致性规则

1. 运行创建时项目版本必须为 `open`，且存在全部可读取的有效需求绑定、活动索引和可用模型配置。
2. 创建后，输入绑定、资产版本、内容 Hash、索引、检索、模型、Agent、Prompt、工具、MCP、网络、权限和限制快照不可原地修改。
3. 所有查询、统计、问答和导出必须校验 `projectVersionId` 与 `runId`；不得跨版本混用、默认到最新或回退到其他运行。
4. 成功运行必须具有完整的正文投递证明：每份资产和每个未排除 Chunk 均在 `InputDeliveryManifest` 中记录成功投递、内容 Hash、Token 数与所属批次；`segmented_context` 还必须记录全部批次完成和最终跨批归并。未投递范围、上下文预算耗尽或资产不可读时运行失败，不得标记为完整。
5. 成功运行的需求点必须具有经服务端从固定正文规范化、可打开的 Evidence；Finding 必须通过其关联需求点间接追溯这些 Evidence。定位失效时明确提示，不能跳转最新资料。
6. 需求点必须保持原子化槽位和可追溯归并信息；相同主体、动作和对象的重复候选只有在归并组、理由和全部来源 Evidence 一致时才可冻结。
7. 提取候选在服务端校验前不得展示或复用；校验后的冻结提取检查点可在需求点/Evidence 视图中只读查看并供仅评审重跑使用，但在评审候选通过并原子发布前，不得生成正式 Finding、成功统计或可导出正式报告。
8. 人工处置只追加，不得篡改模型初始输出、Evidence 或历史处置。
9. 取消、失租约或达到限制后的迟到模型/工具结果必须丢弃或仅保存为过程记录，不能进入正式结果。
10. 工具调用必须匹配固定 Tool Descriptor 与权限快照；新发现的 MCP 工具、参数或目标不得扩大权限。
11. 外部内容不得改变系统 Prompt、权限、模型路由、审批或终止条件；其项目事实属性由固定 Evidence 映射和服务端校验决定。
12. 导出只读取指定运行的正式结果，并排除候选输出、明文凭据与未脱敏日志。



### AC-201：项目版本、绑定与固定输入

**操作**：未创建项目版本时进入需求分析；创建 `open` 版本，从知识库加入历史需求版本并上传含 Markdown、纯文本、图片和不支持格式的 ZIP；完成入库后启动评审，再锁定版本并尝试新运行。

**预期**：未创建版本时仅显示创建引导；支持正文入库并绑定、图片仅作附件、不支持格式逐项反馈；运行快照包含该版本全部有效绑定、资产版本、Hash、索引和两阶段 Agent 配置；锁定后拒绝新绑定和运行；后续上传新资产版本不改变历史运行原文和 Evidence。

### AC-202：结构化结果与证据定位

**操作**：使用包含业务规则、缺失项和关联资料的固定测试集完成评审，打开概览和证据引用，并从 Finding 进入关联需求点的原文定位。

**预期**：需求点按可独立实现、测试或验收的粒度展示；模型只提交 `description` 与 `sourceTexts`，相同描述由服务端合并并保留全部来源 Evidence。正常规模样本的全部固定正文在首轮直接进入模型上下文；每份资产/Chunk 的投递 Hash、Token、模式和覆盖状态均可审计，Evidence 由服务端规范化定位。Finding 仅关联需求点，原文依据经关联需求点的 Evidence 打开指定 `assetVersionId` 并定位原文；关联需求点缺少证据时明确提示，不能伪装为直接 Evidence 或项目事实。

### AC-203：人工处置不覆盖历史

**操作**：对 `open` Finding 依次执行确认、驳回或解决并填写说明，然后重新评审。

**预期**：每次处置产生独立、按时间可追溯的记录；原始 Finding 和 Evidence 的持久化内容不变；新运行有新 ID 与独立结果，旧运行和处置仍可读取。

### AC-204：取消、失败与检索降级

**操作**：以可控模型/工具桩分别触发提取阶段失败、提取成功后评审阶段失败、运行中取消和混合检索降级；对评审阶段失败分别执行“重新需求评审”和“全部重跑”。

**预期**：取消信号传播至模型和工具，运行变为 `cancelled`，迟到结果不发布；模型失败为 `failed` 且展示脱敏摘要；评审阶段失败保留只读需求点/Evidence 和冻结检查点，“重新需求评审”创建只执行评审的新运行，“全部重跑”创建从提取开始的新运行，原失败运行均不覆盖；提取失败不显示仅评审入口；降级原因出现在运行和 Evidence 中；无活动索引时拒绝启动。

### AC-205：模型配置、路由与降级

**操作**：保存新配置版本，启动运行；配置主模型出现可重试故障，并分别启用/禁用允许降级。

**预期**：保存仅生成后续运行使用的新版本；关闭路由时使用默认模型；仅在允许降级且回退模型能力满足时切换；调用记录显示实际模型、重试和原因；页面/API/日志均无密钥、完整端点或 Authorization。

### AC-206：模型检测与输出校验

**操作**：检测一个已注册模型，并使用返回非法提取或评审 Schema 的模型桩启动评审。

**预期**：检测展示可用性、上下文窗口、结构化能力、推理配置、时间和脱敏错误；正文投递不完整、伪造资产/Chunk/Evidence、原子字段缺失或无归并理由的非法输出均在明确结果校验阶段失败，不产生成功统计、正式需求点或可处置 Finding。模型只会输出普通文本或只会调用工具但无法处理完整上下文，均不得仅凭一次工具探测认定满足需求提取质量。

### AC-207：双阶段执行与冻结交接

**操作**：分别用可完整容纳和必须分段的固定多文档样本运行评审，并在运行期间发布新的 Prompt、正文投递策略或工具版本；再令提取成功、评审失败，发布新的需求评审 Agent 版本后只重跑评审。

**预期**：首次完整运行产生两个不同 session/execution。正常规模输入以 `full_context` 首轮直接交付全部正文；超长输入以 `segmented_context` 按固定批次直接注入并完成跨批归并，不退化为逐 Chunk 工具循环。投递清单、Evidence、原子性校验完成后冻结，评审只读取冻结产物且不含提取消息历史；新版本不影响已创建运行的快照。仅评审重跑产生新 runId，记录来源运行 ID，复用并重新校验原冻结提取结果和提取执行记录，只新增评审 execution，并使用重跑时当前已发布的需求评审 Agent；跨阶段非法字段被拒绝；预算不足时显示可解释失败；仅服务端校验并原子保存后运行成功。

### AC-208：工具、联网、MCP 与审批边界

**操作**：使用受控桩测试允许的只读工具、Skill 清单内/外脚本、Skill 清单内/外网络 Origin、越界网络目标、未注册 MCP 工具、可逆写工具、高风险写工具和提示词注入响应；测试参数变化、审批拒绝和取消。

**预期**：未声明脚本、越界 Origin、非 GET/HEAD、重定向、未注册工具和非法参数从未被实际调用；脚本使用受限环境、相对路径、参数数组、超时/取消和结果大小限制，服务端秘密环境变量不传入；外部内容不能改变 Prompt、工具集、路由或审批；审批绑定参数 Hash，参数变化后失效；拒绝、超时或取消停止后续调用；调用/审批记录已脱敏且完整。

### AC-209：三栏工作台、路由与导出

**操作**：在多文档成功运行中切换项目版本和历史运行，按严重度筛选，进行 Finding/原文/需求点/Evidence 双向定位，引用原文提问，刷新固定路由并导出报告。

**预期**：所有区域恢复并始终绑定显式 `projectVersionId + reviewId + runId`，切换版本时不混入旧数据；Evidence 定位到精确固定版本；问答使用独立发布的 `ReviewQaAgent` 模型、Prompt、Skill、MCP、Tool 快照，展示配置版本、引用、实际模型和降级状态且不修改原文/Findings；脚本、网页或 MCP 返回内容不能进入 Evidence 引用；导出包含正式输入、Finding、Evidence、降级和处置状态，排除候选结果、问答全文和敏感日志。

## 8. 前置条件、待确认事项与后续衔接

### 8.1 前置条件

- 一期知识库能提供需求资产版本、Chunk、活动索引和固定证据定位；
- 项目版本服务支持创建、查询、锁定、归档、受控删除和需求绑定；
- 部署环境已注册至少一个支持结构化输出的生成式模型；
- Pi Agent Framework 版本与 Node.js 环境完成兼容性测试，并已集成运行时适配器；
- 两阶段 Agent、Prompt、默认只读工具集、执行限制和权限策略均已发布启用；
- 如启用联网/MCP/外部操作，已完成 Server 注册、白名单、凭据托管、数据边界、注入防护和审批策略评审；
- 已准备包含预期问题、Evidence、工具调用、安全攻击和人工处置的试点评估集。

### 8.2 待确认事项

1. Finding 严重度定义、默认处置时限和后续工单对接边界；
2. 各首发模型的安全输入预算、保留输出/修正余量、单批上限和最大批次数；
3. 首批模型来源、上下文窗口、数据传输与保留策略；
4. 检索降级时是否允许继续运行及可信度展示规则；
5. 两阶段 Agent、Prompt、工具和安全策略的维护责任、发布、回滚与兼容性流程；
6. 最大回合、工具调用、Token、单工具结果、总超时和并发配额；
7. 首批允许联网域名、MCP Server、可发送数据范围与外部引用规则；
8. 可逆写自动执行边界、高风险写逐次确认方式、确认人范围和补偿责任；
9. 试点评估集及需求点召回、Evidence 准确、完整正文直传相对旧工具读取基线的质量/调用成本提升和安全拒绝准确率的度量口径。

### 8.3 后续衔接

二期交付的是可复用的 Agent 执行与治理底座，以及固定双阶段的需求评审闭环；不交付通用 Agent 创建平台或多 Agent 编排平台。Phase 3 应在同一底座上创建独立的 `TechnicalSolutionAnalysisAgent`；Phase 4 再通过显式工作流协调多个测试 Agent。AI 评审结果和问答仅为派生产物，只有人工保存为独立资料版本后，才可按一期资产流程进入知识库。
