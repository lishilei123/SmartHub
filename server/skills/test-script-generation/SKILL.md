# Test script generation

1. Read the frozen TestCase v3, selected `executionMethod`, server-derived assertion anchors, and the relevant `execution/` workspace files.
1a. Reuse existing Workspace implementation and `/exploration/context.json` first. For a UI Case, call the Runtime-authorized `browser.*` tools only when those sources do not provide the minimum facts needed to implement a stable flow. Browser tools may be called repeatedly after each relevant interaction; they are not a mandatory ritual.
2. If this is an API Case without a Binding, first read `/exploration/context.json`, then query the Run-frozen Knowledge index for API documentation only when needed, and then read `execution/api/`, `execution/helpers/`, `execution/fixtures/` and `execution/tests/api/`. Prefer a relevant, validated, same-environment observation over exploring the endpoint from zero, but treat inherited, stale or mismatched observations as needing validation.
3. Exploration Context is runtime-observed knowledge, not Requirement truth. If it conflicts with API documentation, preserve the difference and identify it as possible documentation drift, environment-version drift, product behavior, or invalid exploration; never silently let either source rewrite the TestCase intent.
4. UI Cases must still perform and assert the real UI flow. An observed Endpoint may help understanding and shared-client implementation, but direct API calls cannot replace UI input, interaction, navigation, or page-result verification.
4a. Browser element actions accept only refs returned by the current controlled Session. Prefer `browser.get_locator` results that use role, label, placeholder, text or test id. Never invent a selector, use arbitrary JavaScript/evaluate, navigate to an unapproved origin, or treat a Browser observation as PASS/FAIL.
5. Implement an API Case with Playwright Test's built-in `request` fixture by default. Shared API clients must receive an `APIRequestContext` from the Case or a governed fixture; never create or import axios, superagent, undici, node:http, node:https, fetch polyfills, Postman/Newman, Python HTTP clients, RestAssured, or another API Runner.
6. Reuse an operation-oriented client such as `AuthClient.login/logout/refreshToken` across Cases; never create one client per Case. Keep request construction and reusable operations in the client, while keeping business assertions and every `smarthub:assert` anchor next to the Case entry.
7. The Playwright `page` and `request` fixtures both use the current ExecutionRun BaseURL. Use relative URLs and never hard-code a Host or replace it with an Exploration/API-documentation origin. A mixed UI/API test may use `request` for setup or cleanup, but a UI Case must still use `page` for the tested UI action and assertion; API setup cannot replace UI intent.
7a. For an ordinary signed-in UI Case that uses `request` for setup or cleanup, import the entry's `test` and `expect` from `@smarthub/playwright-test`. This governed fixture bridges the Run-scoped same-origin localStorage Bearer token only into its isolated `request` context, blocks cross-origin calls and redirects, and never adds the token to page traffic. Keep `APIRequestContext` type-only imports from `@playwright/test`. Do not use this fixture for login/logout, anonymous, expired-session, role-switching, account-isolation or other authentication-sensitive Cases.
8. Submit `entryFile` plus only the workspace files that must be added or changed. The Playwright title must end with the stable symbol `[<frozen Case ID>]`, for example `test('创建项目 [TC_PROJECT_CREATE_001]', ...)`; this symbol is the Binding `entrySymbol`. One Binding must resolve to exactly one Case-owned spec and one such title. Cases may share support files such as `api/auth-client.ts`, but never an entry spec.
8a. Wrap meaningful business operations in Playwright `test.step` with short, stable, non-sensitive titles. Use observable operation names such as `POST /api/orders`, `点击提交订单`, `重新查询订单` or `验证最终状态`; never include request/response bodies, query values, credentials, tokens, cookies, personal data, or selector dumps. The native JSON Reporter is the execution-event source; do not parse or manufacture events from stdout.
9. Implement every `expectedResults` item exactly once through the server-derived assertion anchors. Preserve its expected semantics; do not weaken, omit, invert, or replace business assertions. For an API rejection, never use only `expect(response.ok()).toBeFalsy()` (or an equivalent boolean check), and never replace it with an HTTP status that the frozen Expected Result did not specify. Assert the frozen business error field, success semantics, persistent invariant, or continued operability instead. A routing 404 or method 405 is not proof that a business validation rule worked.
9a. For repeat-delete, idempotency, recovery, or rejection Cases without a frozen response status/message, prove the result through durable observations: the target remains absent or unchanged, control data remains queryable, and a subsequent supported operation still succeeds. For UI rejection Cases, do not require a Toast, error copy, or regular-expression text match unless the frozen Expected Result requires that exact observable message; refresh or re-enter and verify the persistent UI state.
9b. For a negative UI state-transition Case, never substitute a visible legal forward, rollback, or neighboring action for the frozen illegal target action. Scope all action and state locators to the intended entity. If that entity does not expose the illegal transition at all, verify that the corresponding button, menu item, or option is absent within the entity and then refresh or re-enter to prove its persisted state is unchanged; do not click a different legal action to manufacture a failure.
10. Do not invent credentials, environment values, business rules, APIs, selectors, thresholds, or expected results. Authentication comes only from frozen Test Data, an existing governed fixture, the current Environment, or Runtime Secret references. Never recover redacted values or write Authorization, Cookie, Token, Password, Session, API Key or personal data into Workspace source.
10a. Reuse an existing authenticated Playwright fixture and `storageState` for ordinary signed-in business Cases when the Workspace already provides one. Runtime supplies an ephemeral Run-scoped auth-state directory through Playwright config metadata; state files must stay there. Login success/failure, logout, anonymous access, session/token/cookie expiry, role switching, account isolation, login security, and multi-session Cases must use a fresh, anonymous, isolated-role, or custom context and must not consume the shared default authenticated state. Do not create an account, login route, locator, or credential convention when the current Workspace and frozen inputs do not provide it.
10b. Realize or verify every precondition through frozen Test Data, a governed fixture, an explicit setup/cleanup operation backed by trusted contract evidence, or a runtime-observed check. A guard that only fails when data is absent does not realize a precondition. When a trusted setup API, fixture, or legal UI flow exists, create uniquely identified per-Case records and state through known legal transitions, operate only on those records, and clean them up within the isolated Case. Never select the first or any matching record from a mutable global list for a stateful test: another concurrent Task may change it. Symbols such as `T1`, `T2`, `K`, `P1` or `U1` in a Case describe test data roles; they do not prove those records already exist in the target environment. Do not submit a runnable candidate that merely hard-codes such symbols into filters or assertions without creating/resolving the corresponding data.
10c. Every Service retry is a fresh validation invocation. Before submitting an API candidate in that invocation, re-read `/exploration/context.json`, a relevant `execution/api|helpers|fixtures|tests/api` file, or a frozen Knowledge chunk after search. Prior Session memory, a search without `knowledge.read_chunk`, or repeated submissions do not satisfy the current contract-evidence gate.
10d. Dashboard, report, and aggregate-consistency Cases must not assume mutable global seed counts. When a trusted UI flow, governed fixture, or same-origin setup contract is available, create the minimal isolated records needed for each required category, derive expectations from those records or observable source data, and clean them up.
11. Do not include shell commands, package installation, dynamic imports, Node runtime access, arbitrary network utilities, database access, or Runner instructions. Browser Tools are controlled exploration only and cannot execute the submitted test.
12. Submit only `entryFile`, the files added or changed, and an optional short `summary`. Do not submit Task/Run IDs, schema version, Hash, Snapshot, Binding, Revision, Stage or package metadata. The Service binds the current task and validates paths, the reachable relative dependency closure, AST safety, UI/API fixture intent, assertion coverage, package provenance, Binding scope and readiness before any Runner launch.

This Skill cannot execute code, invoke Runner, call another Agent, change the workflow Stage, or expand the Tool whitelist.
