# Test design repair

1. Read `agent_workspace/planning_agent/current-test-cases.json`, including its root-level `scenarioClaims`, the frozen Requirement Release, the server-provided Audit blockers, and the exact `baseCandidateSha256` in the task. The Hash binds this Patch to the Service-owned complete Candidate Snapshot.
2. Repair only blockers whose `resolution` is `agent_repair`, such as an uncovered Requirement, duplicate, invalid Requirement reference, or `TEST_CASE_OVER_MERGED`. Preserve unrelated correct cases, stable temporary refs where their semantic intent remains stable, dimension-specific `executionSpec`, Proposals, frozen history, and data relationships. Submit `test-design-repair/v2` Patch fields only: `baseCandidateSha256`, changed `upsertCases`, permitted `removeCaseRefs`, affected data upserts/removals, and affected dimension updates. Do not re-submit the complete candidate.
3. For `TEST_CASE_OVER_MERGED`, use `blocker.details.scenarioRefs`, `reasons`, and `suggestedSplitCount` together with the referenced claims. Split so every resulting Case has one principal Atomic Test Intent and one independently decidable oracle. Place updated Claim metadata in the affected Case's `coverageClaims`; each `state_transition` Claim keeps exactly one `transition:{from,to}` edge; never combine rollback destinations or represent an edge list in one Claim. Retain correct Requirement refs, move or duplicate DataRequirement caseRefs only when truly needed, repair dependencies, and do not modify Proposals. `removeCaseRefs` may remove only a new Candidate, never a frozen historical reuse Case. Do not delete valid scenarios, weaken coverage, change Requirements, invent Expected Results, or alter a frozen source/Proposal operation only to pass the audit.
4. Preserve legitimate aggregation when all claims express one `crud_lifecycle` or `cross_channel_consistency` intent. Do not split CRUD preparation/query/update observation into mechanical single-step Cases, and do not split a UI/API consistency Case merely because it crosses entrances.
5. Do not resolve `human_decision`, `manual_edit`, or business-policy gaps. Missing thresholds, stability duration, browser/OS/viewport/version matrices, permissions, timeout rules, URL, selector, API path, environment, reset method, or business decisions must remain Findings or Confirmation Items. Execution-contract confirmations use `impactStage=handoff`; they prevent handoff/execution but do not change an otherwise valid business TestCase.
6. Recheck coverage, coverageClaims references and atomicity, dimensions, semantic Expected Results, UI/API readiness, data readiness, dependency cycles, duplicates, and aggregation before submitting. If the base Hash is stale, reread the current candidate; never apply a Patch to another Candidate version.

The server permits at most one controlled automatic repair, and controls Audit execution, formal IDs, revisions, versions, hashes, publication, and Workspace projection. ScenarioClaim remains run-scoped audit metadata and cannot change Stage or permissions.
