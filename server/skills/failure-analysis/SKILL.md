# Failure analysis

1. Read the frozen task, current ScriptRevision, one or more terminal attempts, current Binding and only the artifact metadata or excerpts supplied in the read-only workspace.
2. Distinguish product behavior, script implementation, selector drift, environment, test data, flakiness, assertion mismatch, timeout, and unknown causes. Do not infer a root cause without cited observations.
2a. If the failure comes from a Toast, message text, status code, or other gate added by the script but not required by the frozen Expected Result or Verification Check, classify it as `script_defect` so the implementation can be repaired. Use `assertion_mismatch` only when the protected assertion itself conflicts with the frozen expected semantics; an unsupported auxiliary assertion must not block repair.
2b. Distinguish unavailable external test data from a script that failed to realize self-contained preconditions. Use `test_data_defect` only when no frozen Binding, governed fixture, successful setup, or trusted creation path is available. If the supplied Workspace or Exploration Context provides a trusted creation path but the script merely guards on mutable seed/global data, classify `script_defect` so setup and cleanup can be repaired.
2c. Before submitting `test_data_defect` for a mutable seed/global-data guard, use the read-only Workspace search and read tools to check for a trusted helper, API Case, fixture, or UI setup that creates the same entity/state. If such a path is supplied but the current script did not use it, classify `script_defect`; do not stop at the missing guard data.
2c.1. If a script selects the first or any matching record from a mutable global list to satisfy a stateful precondition, and another task or business action can change that record, classify the resulting API/UI state race as `script_defect` when a trusted creation path exists. The script must create a uniquely identified record, prepare its state through known legal transitions, operate only on that record, and clean it up; this is not an external `test_data_defect`.
2d. If a frozen result requires confirmation before mutation, the script registered a native-dialog observer before acting on the correct target, the observer remained false after the click, and the terminal evidence stays on the correct business page without an observed modal, confirmation copy, or confirm/cancel control, classify `product_defect`: that is already direct evidence that the required confirmation interaction was not provided. Do not require the script to continue until the entity is changed or deleted. Direct mutation or deletion without confirmation is also `product_defect`. Classify `script_defect` only when Trace or terminal-page evidence actually shows another confirmation control that the script failed to bind; do not return `unknown` merely because the protected assertion stopped later steps.
2e. If the current script treats entity visibility, a constant flag, click completion, or another non-confirmation observation as proof that confirmation appeared, classify the resulting failure as `script_defect`. A protected confirmation assertion must be grounded in an observed dialog, modal, confirmation copy, or confirm/cancel control before it can support product classification.
2f. If a frozen step requires editing an entity, the script located the correct entity and attempted the edit, but terminal evidence remains on the correct business page and its observed landmarks/controls contain no edit, rename, save, modal, or dialog entry at all, classify `product_defect`: the required product capability is absent. Do not return `unknown` merely because no update request was emitted. Use `script_defect` only when immutable evidence shows a real edit entry that the script failed to operate.
2g. If an authenticated UI script imports from `@playwright/test` and obtains same-origin API access through `page.request` instead of receiving the governed `request` fixture from `@smarthub/playwright-test`, classify a failure at that auxiliary request or its unfrozen `response.ok()` gate as `script_defect` before any protected business assertion runs. A conflict between the Trace HTTP summary and `response.ok()` does not make this `unknown`: misuse of the authentication bridge is directly observable in the frozen ScriptRevision.
3. Describe one concise key observation supported by the current task's immutable terminal attempts or supplied artifacts. Do not submit Attempt or Artifact IDs; the Service owns those relations. Never cite a running attempt or external fact.
4. Do not decide `repairable`, `recommendedAction`, repair count, or the next workflow Stage. The Service derives policy from the validated category and current task state.
5. Do not propose changing the formal TestCase, Expected Result, verification semantics, assertion meaning, test objective, or requirement rules.
6. Submit only `category`, a short `reason`, and concise `evidence`. Do not mirror Run, Task, ScriptRevision, Attempt, Artifact, configuration, Hash or Snapshot fields. The Service validates the classification, binds current formal facts and applies deterministic repair policy.

This Skill cannot execute code, invoke Runner or another Agent, access shell, network, database, or change workflow state.
