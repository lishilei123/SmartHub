# Test case design

1. Treat Runtime-provided `requirementRelease.content` as the frozen Requirement Release and primary business-fact source. It contains Requirement, Evidence, and Clarification. Read only relevant user material and the explicitly frozen historical snapshot from `/workspace`.
2. Reuse Workspace and Knowledge content that has already been read into the current Planning Session. When the same content hash and needed range remain visible in Context, do not read them again merely because the workflow advanced or Self Review started.
3. Use every relevant entry in Runtime-provided `knowledgeReferences.hits` as an advisory risk reference during Case design and the final Self Review. These references are not formal product facts and do not force Case decomposition or one Case per hit.
4. When the provided references and current Context do not resolve a named risk or fact gap, autonomously call `knowledge.search` with the smallest useful query. Call `knowledge.read_chunk` only when a search hit needs fuller context. If results are weak or off-target, revise the query and continue searching. Do not call Knowledge tools once per Requirement or merely to satisfy a process ritual.
5. Requirement defines product facts but does not bound the test space. First cover core Requirement behavior directly, then actively explore valuable normal, exception, boundary, invalid-input, invalid-state, permission, duplicate-operation, concurrency, idempotency, recovery, query-correctness, consistency, performance, stability, compatibility, security, historical-defect, and Knowledge-derived risk scenarios.
6. `requirementRefs` is direct traceability only. When the expected behavior comes directly from a Requirement, include its real ID. For legitimate risk exploration without a direct Requirement behavior basis, submit `requirementRefs: []`. Never attach an unrelated Requirement merely to increase Coverage.
7. Exploration does not authorize invented business rules. Do not invent limits, thresholds, permissions, state machines, error codes, messages, interfaces, URLs, selectors, accounts, credentials, environments, or data. When concrete behavior is unknown, assert only defensible safety, stability, consistency, authorization, and recoverability baselines, or defer technical facts to TestExecution.
8. Consider functional, performance, stability, compatibility, and security as thinking directions, not Schema gates. Generate only valuable cases; do not pad every dimension, use a minimum Case count, multiply Requirements by a quota, or submit applicability explanations.
9. A Case should have one clear, independently reviewable Test Intent. Keep a natural business loop together when its steps jointly prove one outcome. For example, `Create → Read → Update → Read → Delete → Read` may remain one Case when the shared login, test data, business context, and resource ID jointly prove one CRUD lifecycle. Likewise, a valid `todo → in_progress → completed` state path may remain one Case when it proves one complete workflow. Test Intent—not Requirement count, step count, or interface count—is the decomposition unit.
9a. When a Case changes durable business state—Create, Update, Delete, state transition, persisted configuration, cross-page data, or asynchronous final state—its `expectedResults` must describe the final observable state, not merely “操作成功”. Re-read/query/refresh/re-enter as appropriate and verify stable business fields or absence. Do not add a long read-back chain to field-format, required-field, visibility, tooltip, immediate client validation, or other non-persistent Cases merely to increase a closure metric. Never invent an endpoint, selector, field, state value, delay, or account to manufacture this loop.
10. Never equate membership in a valid enum with permission to supply that value in every operation or lifecycle phase. For a state field, reason jointly about the declared enum, current state, transition rules, and current operation. When a Requirement defines both the state set and a state machine, do not prove enum validity by directly creating a resource in every state; prefer reaching `todo`, `in_progress`, and `completed` through the allowed path. A non-state enum such as `priority` may cover `high`, `medium`, and `low` directly when no operation or lifecycle constraint says otherwise.
11. For an explicit state machine, Self Review must cover each meaningful allowed path and inspect reverse and skipped edges that the formal Requirement directly makes illegal. From `todo → in_progress → completed`, independently meaningful checks include `todo → completed`, `in_progress → todo`, `completed → in_progress`, and `completed → todo`; a rollback Case must prove the attempted transition is rejected and the persisted state remains unchanged, with `requirementRefs` pointing to the formal transition-order Requirement. Do not generate a mathematical Requirement × state-combination matrix; add only business-meaningful transitions that can fail independently.
12. Proactively split a scenario when it represents a distinct risk hypothesis or can fail independently from the normal loop. An illegal transition, illegal enum value, illegal operation, or materially different input path such as empty versus whitespace-only text deserves a separate Case or an explicit parameterized Case when its implementation path may differ. Do not split merely to increase Case count.
13. Treat query correctness as its own risk when appropriate. When controlled data already includes matching and non-matching records, a filter or search Case must prove that the intended records are returned, every returned record satisfies the currently defined condition, and the explicitly prepared non-matching records are absent; “result is non-empty” is insufficient. For example, if Task A contains a unique keyword and Task B does not, searching that keyword must return A and exclude B. Do not invent fuzzy matching, case sensitivity, trimming, tokenization, or searched fields when the Requirement does not define them. Add a separate combination-query Case only when the combined predicates have a plausible independent failure mode. For aggregates or dashboards, reconcile displayed totals against controlled source records and recheck after at least one create, state-change, or delete mutation when the Requirement supports those operations.
14. SmartHub 只设计 Agent Test。每个 Case 必须使用 `executionMethods: [agent]` 并提供 `agentTestSpec`；不得生成 UI/API 或脚本执行 Case。
14a. Agent Test 在正常、异常、边界、权限与业务闭环基础上，按资料适用性探索 Task Completion、Tool Selection、Tool Argument、Tool Sequence、Forbidden Action、Business Outcome、Context Handling、Prompt Injection、Authorization、Safety、Timeout、Tool/MCP Failure 与 Non-deterministic Stability。没有 Tool、Prompt、Workflow 或 MCP 资料时不得猜测其名称、参数或顺序。
14b. `agentTestSpec` 表达可观察约束而非完整 Trace：使用 required/forbidden tools/actions、argumentAssertions、`BEFORE`/`AFTER` sequenceConstraints、business/artifact/semantic/safety assertions 和 executionConstraints。不得写死 Step1=A、Step2=B、Step3=C；被测 Agent 合理增加未禁止步骤不能单独导致失败。
14c. `expectedOutcome` 必须是可审阅的业务结果；确定性约束与 semantic/safety criteria 分开。仅资料明确时才填写 Tool 名、参数路径、Artifact 或业务字段。`repeatCount` 只在非确定性稳定性值得独立验证时大于 1；不得虚构 timeout、maxSteps 或 maxCost，使用 Runtime 提供的默认约束。
15. Before submission, perform one internal Self Review in the same Planning Session after the natural business-loop Cases are designed. Recheck the Requirement, answered Clarification, relevant Workspace already in Context, frozen historical Cases, and all relevant `knowledgeReferences.hits` for uncovered exception paths, boundary conditions, invalid inputs, explicit state-machine legal paths and directly implied illegal reverse/skipped transitions, duplicate operations, query positive/negative accuracy, data consistency, permission risks, historical defects, and explicit Knowledge risks.
16. For each Self Review finding, compare its Test Intent against both the Candidate Delta and preserved frozen historical Cases. If the intent can fail independently and no existing Case covers it, add a separate Case. If it is already covered, cannot fail independently, or has no defensible expected result, do not add a Case merely to increase quantity.
17. A Case has one natural-language `preconditions`, `steps`, and `expectedResults` set. `executionMethods` 必须恰为 `[agent]` 并携带 `agentTestSpec`。不要提交 endpoint、authentication、被测 Agent 配置、readiness、data-governance、Coverage、Finding、Confirmation 或 Proposal 字段；连接映射由 ProjectVersion 下的 Agent Under Test 正式配置负责。
18. Submit `test-case-design/v3` with root fields `schemaVersion` and `cases` only. Every flat Case contains `ref`, `schemaVersion=test-case/v3`, `title`, `dimension`, `priority`, `requirementRefs`, `executionMethods`, `preconditions`, `steps`, `expectedResults`, and Agent Case additionally contains `agentTestSpec`.
19. Treat `cases[]` as the current Candidate Delta, never as the complete library. If `historical-test-cases.json` exists, read it only as needed to understand existing coverage and affected scenarios. Submit only new or genuinely changed cases; do not resubmit unchanged history and do not emit reuse/update/create/deprecate lifecycle actions. `cases: []` is valid when no historical scenario needs a change.
20. Omission is not deletion. Any frozen historical Case absent from the Candidate remains in the effective set; only the Service matches intersections and owns formal lifecycle decisions.
21. Historical `requirementRefs` belong to the source Requirement Release. Use them only to understand historical intent; never assume that the same `RP-xxx` identifies the same Requirement in the current Release. Submit direct trace only with IDs from the Runtime-provided current Requirement Release. Cross-release mapping is exclusively Service-owned.
22. Finish Self Review by confirming that valid enum membership was not mistaken for arbitrary lifecycle input permission, explicit state-machine edges were reviewed, normal business loops were not mechanically fragmented, independent Agent risks were not hidden inside an oversized happy-path Case, constraints describe partial order rather than a fabricated complete Trace, invisible Evidence was not treated as absence, direct Requirement trace is explicit, extended cases are not falsely traced, expected results contain no fabricated product rule, refs are unique, and every new submitted Case has steps, expected results, exactly `[agent]`, and a valid `agentTestSpec`.

The Service owns formal IDs, revisions, hashes, history matching, review, publication, traceability persistence, and Workspace projection. This Skill cannot change Workflow state.
