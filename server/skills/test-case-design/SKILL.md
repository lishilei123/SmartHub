# Test case design

1. Read the formal Requirement Release completely, relevant clarification/test-focus context, and `agent_workspace/planning_agent/historical-test-cases.json` when present. Use only its frozen Case IDs and Revisions.
2. For every in-scope Requirement, actively expand scenarios across role, permission, state, precondition, input equivalence class, boundary, normal/exception path, operation path, expected result, cleanup, and UI/API differences. One Requirement may produce many cases; never use a mechanical 1:1 mapping.
3. Apply **Atomic Test Intent**: one TestCase may have multiple preparation and operation steps, but normally has exactly one principal intent and one independently decidable Pass/Fail conclusion. Split when state-transition edges differ; positive and negative paths differ; illegal edges can fail independently; subjects/fields differ; query capability differs; role/permission expected results differ; or an independent input class, boundary, or oracle would represent a separate defect. A `state_transition` ScenarioClaim must declare exactly one `transition: { from, to }`; completed→todo and completed→in_progress are distinct Claims and distinct Cases. Do not split preparation steps that serve one lifecycle intent.
4. A complete CRUD lifecycle may remain one Case when create/query/update/query only proves one persistence-and-observability conclusion. `crud_lifecycle` and `cross_channel_consistency` may aggregate their own steps; UI create plus API observation is not mechanically two Cases. Never mix an independent ordinary intent into such a Case.
5. Every case must include one or more direct `requirementRefs` from the frozen Requirement Release. A case may cover multiple closely related Requirements. Use temporary case `ref` values. Submit each `cases[]` item as a flat `test-case/v2` object: `ref`, `schemaVersion`, `title`, `requirementRefs`, and `executionSpec` are sibling fields. Never use a `{ ref, content: {...} }` wrapper. Dependencies and `dataRequirements[].caseRefs` must use those refs; leave `dataRequirementIds` empty because the server owns formal relationships.
6. Submit root-level `scenarioClaims` for the current Candidate. Each functional/security Case needs at least one claim with a unique `ref`, its temporary `caseRef`, a nonempty subset of that Case's `requirementRefs`, `kind`, `subject`, `variant`, `polarity`, and a concrete independently judgeable `oracle`. `state_transition` additionally requires one nonempty `transition.from` and one nonempty `transition.to`; arrays or combined alternatives are invalid. An oracle must independently decide Pass/Fail: do not use `获得可观察结果`、`功能可用` or `查询成功`; for filters use distinguishable data and assert target values match while non-target values do not mix in. For Dashboard counts, compare against independently prepared/read source data; do not merely check that fields exist. Optional `knowledgeRefs` may show which retrieved test method or risk pattern was adopted; they never create a Requirement or prove a business rule. ScenarioClaim is temporary audit metadata, not TestPoint: no Stage, formal ID, Revision, Version, Library, review, Workspace asset, or Execution Handoff membership.
7. Emit `test-case/v2` and one dimension-specific `executionSpec` per case. Functional/security use `kind=functional` with UI or API steps/checks/preconditions/data/readiness/hint. Performance uses `method=performance_tool`; stability uses `method=long_running`; compatibility uses `method=environment_matrix` with a UI/API base method.
8. Performance thresholds must carry a released requirement or confirmed project-config `sourceRef`. Missing thresholds, stability duration/recovery criteria, compatibility matrix, URL, selector, API path, environment, or reset method must use null/empty values with `needs_confirmation` plus readiness reason where applicable. The Service is the sole formal producer of aggregated Execution Handoff Confirmation Items, so do not create per-Case Confirmation Items for these execution-contract gaps. This blocks automatic handoff/execution, not semantic TestCase review or library publication. Never invent endpoints, selectors, credentials, accounts, test data, thresholds, durations, browsers, systems, viewports, versions, or environment values.
9. Produce one complete `proposals` list and cover every candidate case. Use `reuse` when frozen content remains valid, `update` only for actually affected cases while preserving source Case ID, `create` only when no historical case can cover the Requirement scenarios, `deprecate` for no-longer-applicable cases, and `reference` for design context excluded from this release. Include source Case ID/Revision when required, candidate ref when required, requirement refs, reason, and calibrated confidence.
10. Follow the invariant: reuse does not copy, update does not replace the Case ID, create alone receives a new Case ID, and removal is deprecation. You propose semantics only; never allocate IDs/Revisions/Hashes or modify the formal library.
11. Define data needs separately with constraints, quantity, state, isolation, sensitivity, cleanup, readiness, case refs, and Requirement refs. Never include production secrets or personal data.
12. Self-review Requirement coverage, ScenarioClaim references, atomicity, duplicate/state/query/subject/oracle aggregation, proposal completeness, invalid frozen sources, dimension/spec mismatch, dependency cycles, semantic Expected Results, execution readiness, and test-data readiness before submitting one complete candidate. Knowledge methods may expand applicable scenarios, but cannot invent business Expected Results, permissions, defaults, thresholds, errors, or state rules.

Do not create formal TestCase IDs, revisions, versions, hashes, publications, database updates, or Workspace writes. This Skill cannot change Workflow Stage.
