# Test case design

1. Read the formal Requirement Release completely, relevant clarification/test-focus context, and `agent_workspace/planning_agent/historical-test-cases.json` when present. It is a frozen Service snapshot: use its Case IDs/Revisions only for `historicalChanges`; never copy unchanged Case bodies into the submission.
2. Before generating cases, submit one root-level `dimensionAssessments` record for **each** of functional, performance, stability, compatibility, and security. Each record declares `applicable`, a Requirement-supported `reason` with `requirementRefs`, identified `risks`, and scenario-family descriptions in `scenarioClaims`. Applicable dimensions must have corresponding cases; an inapplicable dimension must not be padded with a case, but must cite why the frozen Requirement makes it inapplicable. This is candidate-only coverage evidence, never a new human review stage.
3. For every in-scope Requirement, actively expand scenarios across normal and exception paths, role/permission, state transition, input/data boundary, repeat/idempotency, concurrency/race, consistency, timeout/retry/recovery, browser/device/OS/protocol/version compatibility, authentication/authorization/injection/sensitive-data exposure, capacity/response/resource use, long-running/failure recovery, UI/API consistency, and applicable historical defect/case impact. One Requirement may produce many cases; never use a mechanical 1:1 mapping.
4. Apply **Atomic Test Intent**: one TestCase may have multiple preparation and operation steps, but normally has exactly one principal intent and one independently decidable Pass/Fail conclusion. Split when state-transition edges differ; positive and negative paths differ; illegal edges can fail independently; subjects/fields differ; query capability differs; role/permission expected results differ; or an independent input class, boundary, or oracle would represent a separate defect. A `state_transition` ScenarioClaim must declare exactly one `transition: { from, to }`; completed→todo and completed→in_progress are distinct Claims and distinct Cases. Do not split preparation steps that serve one lifecycle intent.
5. A complete CRUD lifecycle may remain one Case when create/query/update/query only proves one persistence-and-observability conclusion. `crud_lifecycle` and `cross_channel_consistency` may aggregate their own steps; UI create plus API observation is not mechanically two Cases. Never mix an independent ordinary intent into such a Case.
6. Every submitted case must include one or more direct `requirementRefs` from the frozen Requirement Release. A case may cover multiple closely related Requirements. Use temporary case `ref` values. Submit each `cases[]` item as a flat `test-case/v2` object: `ref`, `schemaVersion`, `title`, `requirementRefs`, and `executionSpec` are sibling fields. Never use a `{ ref, content: {...} }` wrapper. In `test-case-design/v2`, `cases[]` contains only new Cases and the complete new body for `historicalChanges.update`; dependencies and `dataRequirements[].caseRefs` must use these refs; leave `dataRequirementIds` empty because the server owns formal relationships. When this version explicitly inherits a frozen historical snapshot and every Case is unchanged, `cases: []` is valid: do not fabricate a Case body, because the Service restores every frozen Case, reuse Proposal and ScenarioClaim. Without such a frozen inherited snapshot, an empty array is rejected by the Service.
7. Put Claim metadata in each functional/security Case's `coverageClaims[]`. Each claim has a unique `ref`, `kind`, `subject`, `variant`, `polarity`, and a concrete independently judgeable `oracle`; do not repeat `caseRef` or `requirementRefs` because the Service derives both from the containing Case. `state_transition` additionally requires one nonempty `transition.from` and one nonempty `transition.to`; arrays or combined alternatives are invalid. An oracle must independently decide Pass/Fail: do not use `获得可观察结果`、`功能可用` or `查询成功`; for filters use distinguishable data and assert target values match while non-target values do not mix in. For Dashboard counts, compare against independently prepared/read source data; do not merely check that fields exist. Optional `knowledgeRefs` may show which retrieved test method or risk pattern was adopted; they never create a Requirement or prove a business rule. Do not submit root-level `scenarioClaims`; the Service derives normalized ScenarioClaims from each Case's inline `coverageClaims[]`. ScenarioClaim is temporary audit metadata, not TestPoint: no Stage, formal ID, Revision, Version, Library, review, Workspace asset, or Execution Handoff membership.
8. Emit `test-case/v2` and one dimension-specific `executionSpec` compatibility projection per case. For functional/security, `executionMethods[]` is the real source. Every method selected in `design.executionMethods` must appear in at least one applicable Case; when both UI and API apply, include two independent configurations and do not share or overwrite their steps. Missing execution-only facts do not remove a selected method: keep its configuration and use empty strings for unknown UI entry or API method/path. Do not change the TestCase candidate state only because these execution-stage fields are empty. `executionSpec` only names one of those methods for compatibility. Performance uses `method=performance_tool`; stability uses `method=long_running`; compatibility uses `method=environment_matrix` with a UI/API base method.
9. Performance thresholds must carry a released requirement or confirmed project-config `sourceRef`. Missing thresholds, stability duration/recovery criteria, compatibility matrix, URL, selector, API path, environment, or reset method must use null/empty values. For required string fields such as UI entry and API method/path, submit an empty string rather than inventing a placeholder. The Service preserves those empty values; do not create Confirmation Items for execution-only gaps during TestCase design. They do not block TestCase review or library publication and are validated and supplemented only when creating the Test Execution. Never invent endpoints, selectors, credentials, accounts, test data, thresholds, durations, browsers, systems, viewports, versions, or environment values.
10. Use `historicalChanges[]` only for actual historical `update`, `deprecate`, or `reference` decisions. Every entry has frozen `sourceCaseId`, `sourceRevision`, `reason`, and calibrated `confidence`; only `update` includes the matching new `candidateRef`. Omit unchanged history entirely: the Service restores its frozen body/data and derives `reuse`. Do not submit `reuse` or `create` Proposals in v2. The Service automatically accepts unchanged reuse and accepts create/update only after the current TestCase Revision is approved; deprecate and necessary reference remain explicit human decisions.
11. Follow the invariant: omitted history becomes Service-derived reuse, update does not replace the Case ID, Service-derived create alone receives a new Case ID, and removal is deprecation. You propose semantics only; never allocate IDs/Revisions/Hashes or modify the formal library.
12. Define data needs separately with constraints, quantity, state, isolation, sensitivity, cleanup, readiness, case refs, and Requirement refs. Never include production secrets or personal data.
13. Self-review Requirement coverage, DimensionAssessment evidence, inline coverageClaims, atomicity, duplicate/state/query/subject/oracle aggregation, historicalChanges sources, dimension/spec mismatch, dependency cycles, semantic Expected Results, execution readiness, and test-data readiness before submitting `test-case-design/v2`. Knowledge methods may expand applicable scenarios, but cannot invent business Expected Results, permissions, defaults, thresholds, errors, or state rules.

Do not create formal TestCase IDs, revisions, versions, hashes, publications, database updates, or Workspace writes. This Skill cannot change Workflow Stage.
