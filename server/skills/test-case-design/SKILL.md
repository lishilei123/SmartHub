# Test case design

1. Treat Runtime-provided `requirementRelease.content` as the frozen Requirement Release and primary business-fact source. It contains Requirement, Evidence, and Clarification. Read only relevant user material and the explicitly frozen historical snapshot from `/workspace`.
2. Reuse Workspace and Knowledge content that has already been read into the current Planning Session. When the same content hash and needed range remain visible in Context, do not read them again merely because the workflow advanced or Self Review started.
3. Use every relevant entry in Runtime-provided `knowledgeReferences.hits` as an advisory risk reference during Case design and the final Self Review. These references are not formal product facts and do not force Case decomposition or one Case per hit.
4. When the provided references and current Context do not resolve a named risk or fact gap, autonomously call `knowledge.search` with the smallest useful query. Call `knowledge.read_chunk` only when a search hit needs fuller context. If results are weak or off-target, revise the query and continue searching. Do not call Knowledge tools once per Requirement or merely to satisfy a process ritual.
5. Requirement defines product facts but does not bound the test space. First cover core Requirement behavior directly, then actively explore valuable normal, exception, boundary, invalid-input, invalid-state, permission, duplicate-operation, concurrency, idempotency, recovery, query-correctness, consistency, performance, stability, compatibility, security, historical-defect, and Knowledge-derived risk scenarios.
6. `requirementRefs` is direct traceability only. When the expected behavior comes directly from a Requirement, include its real ID. For legitimate risk exploration without a direct Requirement behavior basis, submit `requirementRefs: []`. Never attach an unrelated Requirement merely to increase Coverage.
7. Exploration does not authorize invented business rules. Do not invent limits, thresholds, permissions, state machines, error codes, messages, interfaces, URLs, selectors, accounts, credentials, environments, or data. When concrete behavior is unknown, assert only defensible safety, stability, consistency, authorization, and recoverability baselines, or defer technical facts to TestExecution.
8. Consider functional, performance, stability, compatibility, and security as thinking directions, not Schema gates. Generate only valuable cases; do not pad every dimension, use a minimum Case count, multiply Requirements by a quota, or submit applicability explanations.
9. A Case should have one clear, independently reviewable Test Intent. Keep a natural business loop together when its steps jointly prove one outcome. For example, `Create → Read → Update → Read → Delete → Read` may remain one Case when the shared login, test data, business context, and resource ID jointly prove one CRUD lifecycle. Likewise, a valid `todo → in_progress → completed` state path may remain one Case when it proves one complete workflow. Test Intent—not Requirement count, step count, or interface count—is the decomposition unit.
10. Proactively split a scenario when it represents a distinct risk hypothesis or can fail independently from the normal loop. Independent illegal transitions such as `todo → completed`, `completed → in_progress`, and `completed → todo`; an illegal enum value; an illegal operation; or materially different input paths such as empty versus whitespace-only text deserve separate Cases or an explicit parameterized Case when their implementation paths may differ. Do not split merely to increase Case count.
11. Treat query correctness as its own risk when appropriate. A filter Case must prove that intended records are present, every returned record satisfies the condition, and non-matching records are absent; “result is non-empty” is insufficient. Add a separate combination-query Case only when the combined predicates have a plausible independent failure mode. For aggregates or dashboards, reconcile displayed totals against controlled source records and recheck after at least one create, state-change, or delete mutation when the Requirement supports those operations.
12. Before submission, perform one internal Self Review in the same Planning Session after the natural business-loop Cases are designed. Recheck the Requirement, answered Clarification, relevant Workspace already in Context, frozen historical Cases, and all relevant `knowledgeReferences.hits` for uncovered exception paths, boundary conditions, invalid inputs, invalid state transitions, duplicate operations, query accuracy, data consistency, permission risks, historical defects, and explicit Knowledge risks.
13. For each Self Review finding, compare its Test Intent against both the Candidate Delta and preserved frozen historical Cases. If the intent can fail independently and no existing Case covers it, add a separate Case. If it is already covered, cannot fail independently, or has no defensible expected result, do not add a Case merely to increase quantity.
14. A Case has one natural-language `preconditions`, `steps`, and `expectedResults` set. `executionMethods` is exactly `ui`, `api`, or both. Do not submit separate UI/API steps or any selector, endpoint, automation, readiness, data-governance, Coverage, Finding, Confirmation, or Proposal fields.
15. Submit `test-case-design/v3` with root fields `schemaVersion` and `cases` only. Every flat Case contains exactly `ref`, `schemaVersion=test-case/v3`, `title`, `dimension`, `priority`, `requirementRefs`, `executionMethods`, `preconditions`, `steps`, and `expectedResults`.
16. Treat `cases[]` as the current Candidate Delta, never as the complete library. If `historical-test-cases.json` exists, read it only as needed to understand existing coverage and affected scenarios. Submit only new or genuinely changed cases; do not resubmit unchanged history and do not emit reuse/update/create/deprecate lifecycle actions. `cases: []` is valid when no historical scenario needs a change.
17. Omission is not deletion. Any frozen historical Case absent from the Candidate remains in the effective set; only the Service matches intersections and owns formal lifecycle decisions.
18. Historical `requirementRefs` belong to the source Requirement Release. Use them only to understand historical intent; never assume that the same `RP-xxx` identifies the same Requirement in the current Release. Submit direct trace only with IDs from the Runtime-provided current Requirement Release. Cross-release mapping is exclusively Service-owned.
19. Finish Self Review by confirming that normal business loops were not mechanically fragmented, independent risks were not hidden inside an oversized happy-path Case, direct Requirement trace is explicit, extended cases are not falsely traced, expected results contain no fabricated product rule, refs are unique, and every submitted Case has steps, expected results, and at least one UI/API execution method.

The Service owns formal IDs, revisions, hashes, history matching, review, publication, traceability persistence, and Workspace projection. This Skill cannot change Workflow state.
