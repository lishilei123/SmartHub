# Test case design

1. Treat Runtime-provided `requirementRelease.content` as the Test Design projection of the frozen Requirement Release and primary business-fact source. It contains Requirement, Evidence, and Clarification; legacy Test Focus is deliberately excluded. Use `knowledgeReferences.hits` as the already-retrieved Knowledge and defect-history context before considering any additional search. Read only relevant user material and the explicitly frozen historical snapshot from `/workspace`.
2. Requirement defines product facts but does not bound the test space. First cover core Requirement behavior directly, then actively explore valuable normal, exception, boundary, state, permission, concurrency, idempotency, recovery, consistency, performance, stability, compatibility, security, historical-defect, and Knowledge-derived risk scenarios.
3. Knowledge references are advisory risk prompts, not formal product facts or mandatory Case-decomposition rules. If a reference recommends splitting every legal state edge but one valid chain jointly proves a single natural workflow, the chain may remain one Case; use the reference to add independently failing illegal, recovery, or consistency risks instead.
4. `requirementRefs` is direct traceability only. When the expected behavior comes directly from a Requirement, include its real ID. For legitimate risk exploration without a direct Requirement behavior basis, submit `requirementRefs: []`. Never attach an unrelated Requirement merely to increase Coverage.
5. Exploration does not authorize invented business rules. Do not invent limits, thresholds, permissions, state machines, error codes, messages, interfaces, URLs, selectors, accounts, credentials, environments, or data. When concrete behavior is unknown, assert only defensible safety, stability, consistency, authorization, and recoverability baselines, or defer technical facts to TestExecution.
6. Consider functional, performance, stability, compatibility, and security as thinking directions, not Schema gates. Generate only valuable cases; do not pad every dimension or submit applicability explanations.
7. A Case should have a clear, reviewable test objective. Keep a natural business loop together when its steps jointly prove one outcome. For example, `Create → Read → Update → Read → Delete → Read` may remain one Case when the shared login, test data, business context, and resource ID jointly prove one CRUD lifecycle. Likewise, a valid `todo → in_progress → completed` state path may remain one Case when it proves one complete workflow. This improves later UI/API script generation and is not a deterministic atomicity rule.
8. Proactively split a scenario when it represents a distinct risk hypothesis or can fail independently from the normal loop. Independent illegal transitions such as `todo → completed` and `completed → in_progress`, an illegal enum value versus legal enum combinations, or materially different input paths such as empty versus whitespace-only text deserve separate Cases or an explicit parameterized Case when their implementation paths may differ. Do not split merely to increase Case count.
9. Treat query correctness as its own risk when appropriate. A filter Case must prove that intended records are present, every returned record satisfies the condition, and non-matching records are absent; “result is non-empty” is insufficient. Add a separate combination-query Case only when the combined predicates have a plausible independent failure mode. For aggregates or dashboards, reconcile displayed totals against controlled source records and recheck after at least one create, state-change, or delete mutation when the Requirement supports those operations.
10. A Case has one natural-language `preconditions`, `steps`, and `expectedResults` set. `executionMethods` is exactly `ui`, `api`, or both. Do not submit separate UI/API steps or any selector, endpoint, automation, readiness, data-governance, Coverage, Finding, Confirmation, or Proposal fields.
11. Submit `test-case-design/v3` with root fields `schemaVersion` and `cases` only. Every flat Case contains exactly `ref`, `schemaVersion=test-case/v3`, `title`, `dimension`, `priority`, `requirementRefs`, `executionMethods`, `preconditions`, `steps`, and `expectedResults`.
12. Treat `cases[]` as the current Candidate Delta, never as the complete library. If `historical-test-cases.json` exists, read it only as needed to understand existing coverage and affected scenarios. Submit only new or genuinely changed cases; do not resubmit unchanged history and do not emit reuse/update/create/deprecate lifecycle actions. `cases: []` is valid when no historical scenario needs a change.
13. Omission is not deletion. Any frozen historical Case absent from the Candidate remains in the effective set; only the Service matches intersections and owns formal lifecycle decisions.
14. Historical `requirementRefs` belong to the source Requirement Release. Use them only to understand historical intent; never assume that the same `RP-xxx` identifies the same Requirement in the current Release. Submit direct trace only with IDs from the Runtime-provided current Requirement Release. Cross-release mapping is exclusively Service-owned.
15. Self-review that normal business loops were not mechanically fragmented, independent risks were not hidden inside an oversized happy-path Case, direct Requirement trace is explicit, extended cases are not falsely traced, expected results contain no fabricated product rule, refs are unique, and every submitted Case has steps, expected results, and at least one UI/API execution method.

The Service owns formal IDs, revisions, hashes, history matching, review, publication, traceability persistence, and Workspace projection. This Skill cannot change Workflow state.
