# Script repair

1. Read the frozen TestCase, current script, validated diagnosis, failed terminal attempts, and supplied artifact evidence from the read-only workspace.
1a. If the evidence does not resolve an implementation fact such as a changed element ref or locator, use the current invocation's controlled Browser Tools to inspect the minimum necessary live state. Re-snapshot after interactions when needed; do not replay the whole business flow mechanically.
2. Repair only implementation details justified by the diagnosis, such as locators, waits, navigation, Playwright `request`/`APIRequestContext` request construction, serialization, governed headers, or test-data assembly. API repair may not introduce another HTTP client or Runner.
3. Preserve every protected assertion anchor, matcher, modifier, expected semantics hash, verification-check mapping, case objective, and formal expected result.
3a. A protected assertion that proves a persistent business loop—such as create then read, update then refresh/re-enter, delete then confirm absence, or asynchronous final state—cannot be removed, bypassed, replaced with transport-only success, or moved behind a condition merely to make execution pass.
3b. When the diagnosis identifies an auxiliary Toast, message-text, or HTTP-status gate that is not required by the frozen Expected Result, remove that unsupported implementation gate and preserve or add the durable protected verification after refresh, re-entry, or a supported follow-up query. This repairs the script without weakening formal semantics.
3c. When a negative state-transition script substituted another legal action or used a page-wide state-text locator, repair it within the intended entity scope. Use only the real frozen target action; if the illegal target is not exposed for that entity, verify the target control is absent there and refresh or re-enter to prove the persisted state remains unchanged. Never click a legal neighboring action merely because it is available.
3d. When an aggregate or dashboard script failed because it only guarded on mutable seed/global data, and the supplied evidence includes a trusted creation path, repair the setup to create the minimal isolated records for every required category, derive the expected aggregate from controlled or observable source data, and clean up those records.
3e. When immutable HTTP evidence shows an auxiliary, non-frozen endpoint returns routing 404/405, remove that invalid call or replace it with a list/query contract already proven by the supplied Exploration Context or Workspace, while preserving the same protected persistent business invariant. Proximity to an assertion anchor does not make an invented route protected.
3f. When a confirmation assertion was satisfied by entity visibility, a constant flag, or click completion, remove that substitute and bind the observation only to a real dialog, modal, confirmation copy, or confirm/cancel control. If no real confirmation exists, let the protected assertion fail as product evidence; never manufacture confirmation to make the script pass.
3g. When the diagnosis identifies a mutable-global-record race, replace first/arbitrary-record selection with per-Case setup that creates a uniquely identified entity, prepares the required state through known legal transitions, operates only on that entity, and cleans it up in `finally`. Do not serialize the whole Worker or add waits to conceal shared-data coupling.
3h. When an authenticated UI Case needs same-origin API data for setup or source reconciliation, import `test`/`expect` from `@smarthub/playwright-test` and receive its governed `request` fixture in the test parameters. Never substitute `page.request`: localStorage authentication is not the governed Bearer bridge. If the diagnosis identifies `response.ok()` as an unfrozen auxiliary gate, remove that gate while retaining response parsing and the protected Dashboard or persistent-state reconciliation. A second repair must materially change the diagnosed implementation and must not resubmit identical source.
4. Repair the persistent Execution Workspace entry and any directly related Page Object, helper, fixture or API client only when the diagnosis supports an automation defect. Keep the protected entry assertion semantics unchanged. For example, an expected HTTP 403 cannot be changed to 200 to make a run pass. Do not add shell commands, dependencies, dynamic imports, Node runtime access, arbitrary network access, database calls, or Runner instructions.
4a. Preserve meaningful `test.step` operation boundaries used by the native Playwright JSON Reporter. A repair may correct a non-sensitive step title when implementation changes, but cannot remove business operations from the structured timeline or add secrets, payload values, personal data, or raw output to it.
5. Do not broaden scope or repair product behavior, formal TestCase content, assertion meaning, or requirement rules merely to make execution pass.
5a. Browser Observation is runtime evidence, not Requirement Truth and not a Runner result. It may justify an implementation repair, but cannot justify changing an Expected Result, deleting a verification step, or declaring PASS/FAIL.
6. Submit `entryFile`, only changed entry/support files, and an optional short `summary`. Do not submit parent Revision, Diagnosis, Task, repair count, schema version, Hash, Snapshot or package metadata. The Service binds the current parent and diagnosis, rebuilds and freezes the reachable Workspace dependency closure, and enforces parent adjacency, hashes, AST safety, assertion inheritance, repair count, and package provenance.

This Skill cannot execute the candidate, invoke Runner or another Agent, change Stage, or bypass the two-repair limit.
